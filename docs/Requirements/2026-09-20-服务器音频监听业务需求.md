## 1. 背景与目标

### 1.1 背景

服务器常常在播放内容 —— 音乐、播客、视频、直播。人在同一局域网内时,希望用手机或另一台电脑直接听服务器正在播放的声音,不必把扬声器搬到身边,也不必先把文件下载下来。

主场景是"挂着听":睡前、做家务、走路时把手机当收音机。**要的体验是"点开就近乎实时"** —— 所以取舍把**低延迟放在第一位**;锁屏与切后台能否继续,取决于系统对后台页面的限制,本模块不承诺(见 §2.5、§6.6)。

能力定位:这是**实时通道**,不是媒体库。文件中心只管文件的字节传输(见其 §1.3),声音的采集、编码与推送归本模块。

### 1.2 业务范围

| 域 | 说明 |
| --- | --- |
| 系统声音采集 | 采集服务器默认播放设备的输出(回环采集,不占用麦克风);采集期间不改动服务器本机音量与静音状态 |
| 音频编码 | WebM 容器 + Opus 编码,64kbps,见 §2.3 |
| 分片推送 | 声音切成固定时长的小片(默认 100ms),采到即推;客户端**不回拉历史**,任何一次(重)连接都从直播边缘起播 |
| 网页收听 | 门户模块页:一个主按钮开始/停止,播放特效、音量、状态与参数展示 |
| 实时优先 | 停止/暂停/断网之后重新接入,一律从服务器**当前**的声音接着听(不复听旧内容) |
| 按需采集 | 没有在线听众即停止采集并释放音频设备(不常驻占用、不空转) |
| 状态查询 | 采集是否进行中、当前听众列表、格式参数 |
| 权限 | 门户模块权限点 `serverAudioStream`;未登录 401、未授权 403、无可用设备(帧通知) |
| 生命周期 | 断线自动重连、设备失效收敛到空闲态、服务停止时干净收尾 |

### 1.3 非目标(本期明确不做)

* **麦克风采集**:只采集系统输出(回环),不做输入设备录音
* **画面**:只做声音,不做视频画面与屏幕共享
* **免登录收听**:必须登录且被授予模块权限 —— 服务器声音可能含会议、语音等敏感内容,采集能力本身也属系统级资源
* **存档与回放**:不做录音落盘、时间轴回拖、历史回听;断网/暂停期间的内容也不补发
* **后台/锁屏连续收听**:平台对后台页面的限制与本传输无关,本期不为此做专门设计(如实告知用户)
* **多路混音与独立声道**:同一时刻只有一路采集源(默认播放设备)
* **iOS 与 Safari 支持**:本期只做安卓;iOS 需要第二条出口(MP4 容器 + AAC 编码),见 §10.3
* **原生客户端**:仅网页;不提供独立 App 与桌面播放器
* **多码率自适应**:单一码率,不按网络状况切换
* **公开分享收听链接**:不做"把声音分享给未登录访客"的链接形态
* **指定进程的声音**:见 §10.3

## 2. 全局约定

### 2.1 模块接入姿态

| 项 | 取值 |
| --- | --- |
| 模块名 | 服务器音频 |
| 权限点 code | `serverAudioStream`(门户模块,type=0) |
| 侧边栏入口 | 由权限点的 `url` 与 `index` 驱动,排用户主页与文件中心之后(取值见 §10.2) |
| 前端页面路由 | `/portal/server-audio-stream`(kebab 目录名即路由名,同 `systemManager` → `/portal/system-manager` 既例) |
| 前端模块目录 | `frontend/src/modules/server-audio-stream/index.vue` |
| 接口前缀 | `/zimo/api/serverAudioStream` |
| 服务端模块文件 | `modules/module_server_audio_stream.{h,cpp}` |
| 前端接口封装 | `frontend/src/api/audio.js`(WS 传输层);API 基址集中在 `frontend/src/api/base.js` |
| 出口 | 两条:推流 `GET …/ws`(WebSocket 升级)、状态 `GET …/status`(普通 HTTP) |
| 权限默认可见角色 | 开发者权限(`developer`);其余角色由管理员在授权弹窗按需授予 |

### 2.2 会话与鉴权

* **三段判定**:
  1. **升级快判**(同步):只验 `zm_session` 形态(存在且是十六进制串),不查库;不通过即拒绝升级;
  2. **引导完整判定**(异步):会话有效性 + 账号状态 + `serverAudioStream` 权限;不通过 → 下发 `auth_failed` 帧后关闭连接;
  3. **周期复检**:每 30 秒对在线连接重跑一次完整判定 —— 推流下客户端不再周期性发请求,**权限撤销/账号停用/异地登出只能靠复检收敛**(实测删会话后 ≤50 秒断开)。
* 权限判定在**服务端**:前端隐藏入口只是体验,不作为门禁(直接连端点同样被拒)
* 播放页在 80/443、接口在 39441,同站跨端口;升级请求与状态查询都带 Cookie(`credentials: 'include'`)
* 鉴权成本与听众数无关:一次建连三次判定(升级/引导/复检),不再"每个片请求都鉴权"

### 2.3 音频格式与分片

采集侧统一为 **48kHz / 立体声 / 16bit 交错**(非立体声源先混单再复制到左右),出口固定为 WebM 容器 + Opus 编码(安卓 Chrome 与同内核浏览器原生支持,无需第二条出口):

| 项 | 取值 |
| --- | --- |
| 容器 | WebM(EBML:头部 + 轨道 + 连续 Cluster) |
| 编码 | Opus(现有 libopus) |
| 码率 | 64 kbps |
| 编码帧长 | 20 ms |
| 分片时长 | 5 帧 = 100 ms |
| 传输 | WebSocket 推送(每成一片即推一帧,约 10 帧/秒) |

* 分片时长以**编码帧对齐**为准(上表是目标值),真实值由建连时下发的流描述返回,客户端不写死
* 时间戳单调递增,起点为采集开始时刻;片号(seq)从 1 起,进程重启后归零
* 片序与时间轴一一对应:**第 N 片覆盖采集时间 `[(N−1)×片长, N×片长)`** —— 客户端据此把片落到时间轴,也据此折算延迟
* 二进制帧头带**显式起始片号**(不靠"按帧数自增"推断),补发与跳号时不会错位

### 2.4 采集与资源占用原则(核心约束)

三条原则按优先级排列,后文决策都从这里推导:

1. **按需**:只有在有人听的时候才采集。**没有在线连接**(且过了 15 秒宽限,覆盖"刚建连还没同步"的窗口)时,采集线程自行停止并释放音频设备与编码器;暂停中的连接仍算"有听众",但暂停超过 60 秒即断开,避免一个挂着的暂停把设备长期占住。
2. **如实**:采集启动失败(无默认播放设备、设备被独占、格式不受支持)时如实下发错误帧,不做"假装正在播放"的静默降级;"暂时拉不起来"(设备正在释放、采集刚起)与"确实没有设备"必须分开报。
3. **可收尾**:服务停止、设备失效、无人收听三条路径都必须收敛到"无残留线程、无残留设备句柄";不以牺牲进程正常退出来换音频连续。

### 2.5 性能与实时性(基线)

| 指标 | 目标 |
| --- | --- |
| 端到端延迟 | 安卓/桌面典型 200~500ms(受分片时长与播放器缓冲下限约束,几十毫秒不可达;局域网实测读数约 300ms) |
| 起播时间 | 点击到出声 ≤ 3s(实测 1~2s) |
| 断线恢复 | 网络/服务恢复后 ≤5s 回到播放(实测约 1s);重连退避上限 2 秒并监听网络恢复事件 |
| 带宽 | 单路 ≈ 8KB/s(64kbps);16 路 ≈ 1Mbps |
| 服务端内存 | **起播缓冲 1 秒(约 10 片)**;与听众数无关。单连接在页面被冻结期间的发送积压以心跳超时(120 秒)为上界 |
| 采集开销 | 采集 + 编码 + 封装为单线程,典型单核占用 < 5% |
| 后台/锁屏 | **不承诺**:页面被系统冻结即断流,回前台自动重连并接回直播边缘(平台限制,与传输方案无关) |

### 2.6 并发与线程纪律(约束)

* 采集、编码、封存在**同一个采集线程**(全进程唯一)
* **推送路径**:采集线程的回调里只做"成簇入缓冲 + 锁内登记待推片",真正的 socket 写入排进**每条连接自己所属的事件循环** —— 采集线程回调不得阻塞(否则音频抖动),且补发与实时推送若跨线程直发会乱序(乱序片会让 MSE 追加失败或留空洞)
* 事件循环线程上**没有等待**:状态接口即取即回;推送只入队不阻塞
* 服务端**持有每连接对象**(连接即听众):键为 `uid:client`,连接关闭即离场
* 关闭顺序:断开全部连接 → 停采集线程(join 并释放设备)→ 销毁模块 → 销毁网络层

## 3. 功能需求

### 3.1 建连与引导(取流描述与初始化段)

* 端点:`GET /zimo/api/serverAudioStream/ws`(同一 HTTPS 监听器与证书,cookie 随升级请求携带)
* 升级通过后,客户端立即发 `sync`;**引导**(完整鉴权 + 懒启动采集 + 等首片就绪 ≤1s)完成后下发:
  1. `meta` 帧(text):`{streamId, segmentMs, sampleRate, channels, bitrate, baseSeq}`
  2. 初始化段(binary 类型 0):WebM 头,起始片号 = 元数据里的 `baseSeq`
  3. 起播补发批(binary 类型 1):从 `baseSeq` 起 3 片(≈300ms,媒体元素进入播放态的最低需求),随后转实时推送
* **起播只回退 3 片,不回补历史**:要的是"点开就近乎实时",不是"补听错过的那段";服务端因此不保留可供回头的历史(缓冲窗口 1 秒)
* 换流识别:采集重启/服务重启后 `streamId` 变化,客户端据此重建媒体源并丢弃旧缓冲
* 引导失败:鉴权不过 → `auth_failed` 帧 + 关闭;设备类失败 → `error` 帧(`AUDIO_BUSY` = 暂时不可用,让客户端退避重试;`AUDIO_NO_DEVICE` = 确实没有设备,如实提示并停下)
* 同一时刻多次建连不重复启动采集(采集启动幂等;**正在启动中**与**正在收尾**必须区分对待,后者等待、前者等待其就绪,不能当成"设备正在释放"把后来的听众踢掉)

### 3.2 实时推送与控制帧

* 采集每成一片(100ms)立即向所有在线且未暂停的连接推一帧(单片一批,≈0.9KB)
* 客户端 → 服务端的控制帧:

| 帧 | 含义 |
| --- | --- |
| `sync{client}` | 建连后 / 重连后 / 暂停恢复后:一律"从直播边缘重定基"(不带片号,服务端不做历史补发) |
| `pause` | 暂停:服务端停止推送,连接保留(仍照常应答心跳) |
| `pong{seq,pos}` | 心跳应答:`seq` = 已收到的最新片号,`pos` = 播放头所在片号(服务端据此算落后量) |

* 服务端 → 客户端的控制帧:`ping`(每 15 秒)、`meta`、`error`、`auth_failed`
* **停止 = 关闭连接**(没有 stop 帧):连接关闭即离场
* 服务端不做"客户端落后即补发历史"的反馈:落后由客户端自己收敛(§6.4),补历史与"实时优先"相冲突

### 3.3 状态与听众列表

* 端点:GET `/zimo/api/serverAudioStream/status`(需会话 + 权限)
* 返回:采集状态 + 格式参数 + 听众信息

```
{
  capturing: true,
  streamId: "...",
  sampleRate: 48000, channels: 2, bitrate: 64000,
  segmentDurationMs: 100,
  segmentWindowSec: 1,
  bufferFillSec: 1.0,
  listenerCount: 2,
  listeners: [                     // 仅开发者/管理员可见;普通用户不下发本字段
    { uid, account, nickname, ip, client, level, sinceMs, lastSeenMs, paused, lagMs }
  ]
}
```

* `lagMs` = **该听众上报那一刻**算好的落后量(服务端拿"收到上报时的直播边缘"减客户端上报的播放头片号),**-1 = 尚未上报**(刚建连或页面被冻结;界面显示"未上报",不能显示成一个假的大数)
* **可见范围分级**:仅有 `serverAudioStream` 权限的用户只拿到 `listenerCount`(界面显示"当前 N 个会话在收听");`developer` 与管理员额外拿到 `listeners` 明细 —— 避免普通用户看到他人的账号与内网地址
* 列表口径:**当前在线连接**;连接关闭立即移出
* **本接口不计入活跃度**:它只做观察,不延长任何人的在线时长(否则"挂着页面不播"会让采集永不停止)
* 取实时快照(锁内读取),不做缓存;不下发任何凭据类信息

### 3.4 分片协议

```
binary 帧 = [类型 u8][起始片号 u64 LE][载荷]
  类型 0 = 初始化段;类型 1 = 分片批 [片数 u32 LE][每片:长度 u32 LE + 字节]
每个片 = 一个 WebM Cluster(可独立解析的封装单元)
片号 seq 单调递增;片内时间戳连续,不重叠不留空
```

* 单片的音频内容为定长(§2.3),因此片长恒定,客户端可据片长直接推算播放时间轴
* 片内时标用毫秒(WebM 的 TimecodeScale = 1ms),片间时标严格接续
* 片按固定的容器/编码/采样率/声道打包,同一会话内不变(格式变化即换流,由 `streamId` 标识)

### 3.5 落后、跳片与背压

* 服务端**不维护每听众队列、不排队、不丢帧、不主动断开慢客户端**:它只按直播边缘推
* 客户端**收到多少追加多少、永不丢片**(丢片会在时间轴上留空洞,播放头走到空洞处会永久停住),落后只靠"把播放头前跳到 边缘 − 余量"收敛
* 起播缓冲窗口固定 1 秒(§2.5):服务端不保留可回头的历史;"落后很久"的场景不存在补发路径,一律由客户端回到直播边缘
* 播放暂停 = 服务端停推、连接保留:**恢复播放一律回到直播边缘**(不听暂停期间的内容),暂停超 60 秒由服务端断开并释放设备
* 单连接在页面被冻结期间产生的发送积压,以心跳超时(120 秒)为上界

### 3.6 设备与格式适配

* 采集对象:系统**默认播放设备**(渲染端点)的回环输出
* 混音格式与目标格式不一致时(常见于 44.1kHz/96kHz 声卡、HDMI 输出),按顺序尝试:

| 步骤 | 做法 | 失败后 |
| --- | --- | --- |
| 1 | 询问音频引擎能否以 48kHz 接受"混音声道/位深"的格式 | 下一步 |
| 2 | 依次尝试 48kHz/2ch/16bit → 48kHz/2ch/32bit 浮点 → 48kHz/1ch/16bit | 下一步 |
| 3 | 请求引擎在混音格式与 48kHz 之间插入采样率转换(默认质量) | 下一步 |
| 4 | 采集启动失败 → 下发 `AUDIO_NO_DEVICE` 帧并断开 | — |

* 位深兼容:16bit PCM、32bit PCM、32bit 浮点三种输入都要能转成 16bit 交错立体声(浮点需限幅到 [-1,1])
* 声道兼容:单声道/多声道源混单(均值)后复制到左右
* **静音照常出片**:引擎标记为静音的包按静音编码,时间轴与片序不间断 —— 播放端的时间轴跟数据走,静音期间若不产片,播放会停在缓冲末尾并把落后量永久累加;客户端也不得把"这段时间没有声音"当作断线
* 采集启动后首片必定在 200ms 内产出(静音也出片),§3.1 的"等首片"因此有界
* 设备失效(拔出/禁用/格式变更):停止采集、释放设备、回空闲态,对全部连接下发 `AUDIO_DEVICE_LOST` 后断开;前端按 §6.5 处置

### 3.7 连接与收尾

* 推流是**长连接**:连接关闭即离场;客户端断网时服务端靠心跳判活(120 秒无应答断开)
* 服务停止:断开全部连接 → 停采集线程 → 释放设备与编码器 → 销毁模块
* 服务停止不保证客户端把已缓冲内容播完(客户端缓存里已有的会继续播到缓冲耗尽)

### 3.8 并发收听

* 不设硬性并发上限:每条连接只多一份"在自己事件循环上发送 + 一小份发送积压",采集成本与人数无关
* 参考容量:单路 ≈ 8KB/s,16 路 ≈ 1Mbps,受服务器上行带宽约束
* 听众列表经 `/status` 暴露(§3.3),本期不做管理端界面

## 4. 通用规则

### 4.1 错误语义

| 通道 | 情形 | 表现 | 前端处置 |
| --- | --- | --- | --- |
| 升级 | 未携带/形态非法的会话 cookie | 升级被拒 | 跳登录(带回跳) |
| 帧 | 会话失效 / 账号停用 / 强制改密 | `auth_failed{code,message}` 后断开 | 提示并跳登录 |
| 帧 | 无 `serverAudioStream` 权限 | `auth_failed{code=PERM_DENIED}` 后断开 | 提示"权限不足",停止播放 |
| 帧 | 暂时拉不起来(设备正在释放 / 采集刚起 / 启动超时) | `error{code=AUDIO_BUSY}` 后断开 | **退避重试**,不要报成"没有设备" |
| 帧 | 确实没有可用设备 / 采集中途设备失效 | `error{code=AUDIO_NO_DEVICE}` / `AUDIO_DEVICE_LOST}` | 提示"服务器无可用音频设备",回空闲(可重试) |
| 连接 | 网络中断 / 心跳超时 / 服务重启 | 连接关闭 | 退避重连(上限 2 秒),恢复后从直播边缘续接 |
| HTTP | `/status` 401 / 403 | 与其余业务接口同形 `{code,message}` | 同左 |

* 控制帧为 JSON;媒体面只有 `meta` 与两种 binary 帧
* 权限被收回在**下一次复检**(≤30 秒)内生效,前端必须按 §6.5 收敛,不能靠"只看建连结果"

### 4.2 不变量

| # | 不变量 |
| --- | --- |
| I1 | 没有在线连接(且过宽限期)时不采集(设备与编码器已释放) |
| I2 | 同一时刻只有一条采集线程、一份设备句柄 |
| I3 | 同一片号返回的内容对所有人一致(分片一经生成即冻结,不因听众而变) |
| I4 | 停止与启动路径幂等:重复调用不产生第二条采集线程 |
| I5 | 服务进程退出后不残留线程与设备占用 |
| I6 | 片内容与片号一一对应,不重复不跳号(重启除外) |
| I7 | 同一连接的所有帧(补发 + 实时)按片号单调有序送达(发送排进该连接自己的事件循环) |

## 5. 服务端需求

### 5.1 模块结构

| 项 | 说明 |
| --- | --- |
| 模块类 | `ServerAudioStreamModule`(业务层) |
| 装配 | 与文件中心同层:门户 `CreateModules()` 创建,注入会话/权限/门禁模块,在 `RegisterRoutes()` 中注册端点 |
| 权限点登记 | 启动时幂等登记 `serverAudioStream`(type=0、module=portal、url=`/portal/server-audio-stream`),默认授予 `developer` |
| 端点 | `GET …/ws`(WebSocket)、`GET …/status`(普通 HTTP);不依赖流式响应能力 |
| 依赖 | Opus 编码库(公共库已含静态库)、WASAPI(系统自带)、基座 WebSocket 注册能力;不引入新依赖 |
| 编码与封装位置 | 采集线程内完成(需在时限内产出片);不得占用事件循环线程 |

### 5.2 采集线程与产出管线

| 项 | 要求 |
| --- | --- |
| 启动时机 | 首次建连引导时(懒启动),失败即下发错误帧 |
| 等待方式 | 事件驱动(音频引擎的缓冲就绪事件)+ 200ms 超时兜底 |
| 超时分支职责 | 探测设备是否仍可用;检查是否已无在线连接 → 自行停止 |
| 逐包处理 | 取包 → 静音也编码 → 转 16bit 交错立体声 → 送编码器 → 按片长聚合成片 |
| 片产出 | 每满一片:写容器封装 → 分配片号 → 写入起播缓冲 → 登记待推片 → 锁外入队 |
| 采集异常 | 包查询失败(设备失效)→ 记日志、清空缓冲、释放资源、回空闲态,并通知全部连接 |
| 结束收尾 | 停止引擎 → 释放设备/事件/编码器 → 锁内标记空闲(幂等) |

### 5.3 起播缓冲与连接注册表

* **起播缓冲**(全进程一份):按片号保存最近 1 秒(约 10 片)的片,超出即丢最旧;持有"最小可用片号、直播边缘片号、写索引"
* 只有一份缓冲:出口唯一,同一片号对所有听众内容一致
* **连接注册表**:键为 `uid:client`,记录连接对象、所属事件循环、账号信息、播放头/落后量、暂停状态、已推送到哪一片;连接关闭即移除(同键的新连接顶掉旧的,旧连接的迟到回调不得误删新条目)
* 推送路径(锁内登记、锁外入队):锁内确定"该连接还没收到哪些片"并更新游标,锁外只把闭包排进该连接的事件循环
* 以上状态均由一把模块锁保护;缓冲只读访问在锁内完成拷贝,避免长时间持锁

### 5.4 生命周期纪律(必须遵守)

| # | 纪律 | 原因 |
| --- | --- | --- |
| L1 | 采集、编码、封装都在采集线程内完成 | 事件循环上不得有耗时工作 |
| L2 | 采集线程回调里**不做网络 I/O**,只登记 + 入队 | 阻塞采集线程会直接变成音频抖动 |
| L3 | **不在持锁时发送**:锁内只排队,发送在各连接的事件循环 | 持锁发送会把事件循环一起卡住 |
| L4 | 采集资源由采集线程在锁内释放并置空 | 释放与状态标记同锁,避免"看着还活着但资源已释放"的窗口 |
| L5 | 停采信号要主动唤醒等待中的采集线程 | 否则最长要等到 200ms 超时才停 |
| L6 | 关停顺序:先断开连接、停采集线程并 join,再销毁模块与网络层 | 采集线程是唯一在后台碰音频设备与缓冲的角色 |
| L7 | 起播缓冲一经生成即只读 | 保证同一片号对所有听众内容一致(§4.2 I3) |
| L8 | "告诉客户端原因"的控制帧与关闭动作必须排进**同一个循环任务** | 先排队列再当场关闭,会让关闭帧抢先,客户端看不到原因 |

## 6. 前端页面需求

### 6.1 页面形态(`/portal/server-audio-stream`)

单屏一页,手机与桌面同一套布局(桌面居中约束宽度,不出现横向滚动):

```
┌──────────────────────────────────────┐
│            ╭────────────╮            │
│         ╱   播放特效区    ╲           │
│        │    ┌────────┐     │          │
│        │    │  ▶ / ■ │     │          │  ← 主按钮(圆盘 + 图标,点击开始/停止)
│        │    └────────┘     │          │
│         ╲                ╱           │
│            ╰────────────╯            │
│              聆听服务器                │  ← 状态行
├──────────────────────────────────────┤
│ 48kHz · 64kbps · 立体声 · 延迟 320ms   │  ← 参数行
│ 当前 2 个会话在收听(张三 / 我的手机)   │  ← 听众列表
│ 音量 ────────────●──────  [100]       │  ← 音量滑杆(本地记忆)
└──────────────────────────────────────┘
```

* 特效区尺寸按容器尺寸 × 设备像素比计算,窗口尺寸变化或状态文案增减时重算(圆环必须与主按钮同心)
* 主按钮图标随状态:可播放 ▶ / 播放中 ■ / 连接中 / 错误态(断线重连、无设备)⚠
* 状态行文案:`聆听服务器`(空闲)/ `连接中…` / `正在播放` / `连接中断,重连中…`(附原因)/ `服务器无可用音频设备`

### 6.2 播放链路

```
WebSocket 推流(带 Cookie 升级,事件驱动)
  → 交给 <audio> 元素的 MediaSource(appendBuffer)
  → 浏览器解码播放(与普通音频播放同一条路)
  → 音量由元素音量控制;MediaSession 提供锁屏控制
```

* **音频不在页面里解码**:交给媒体元素,这是"切到别的模块仍能继续播"的前提(网页自己解码的路径会被系统挂起)
* 播放元素用 `<audio>`;若某浏览器只对 `<video>` 生效,则退回无画面的 `<video>`(不设画面、`playsinline`)
* 必须在用户手势内调用 `play()`(浏览器自动播放策略)
* 收到新 `streamId`(换流)时:清空缓冲、重建媒体源并重新起播

### 6.3 兼容性门禁

* 前置条件:安全上下文(HTTPS)+ 支持 MSE + 支持 WebSocket
* 判定用**能力检测**而非浏览器名:`MediaSource.isTypeSupported('audio/webm; codecs="opus"')`
* 不支持:页面直接显示"不支持的浏览器",不显示开始按钮
* 验收目标:安卓 Chrome(含同内核的国产浏览器);桌面 Chrome / Edge / Firefox 走同一条路可用,但本期不做专门适配与验收

### 6.4 播放状态机与缓冲策略

| 状态 | 触发 | 界面 |
| --- | --- | --- |
| idle | 初始 / 用户停止 / 无设备 | 聆听服务器 |
| connecting | 点击开始后 | 连接中… |
| playing | 媒体元素开始出声 | 正在播放 |
| reconnecting | 连接中断 / 收不到帧(非主动停止) | 连接中断,重连中…(附原因) |
| no-device | 设备类错误帧 | 服务器无可用音频设备 |

缓冲策略(推流下的控制量只有"播放头落后直播边缘多少"):

| 规则 | 做法 | 说明 |
| --- | --- | --- |
| 全量追加 | 收到的片按序全部写入缓冲,**永不丢片** | 丢片会留时间轴空洞,播放头走到空洞处会永久停住 |
| 落后前跳 | 落后超过"余量 + 1.5s"时,把播放头前跳到 `边缘 − 余量`(落点在已缓冲区间内) | 推流下落后量不会自己收回,这一跳是**稳态控制**而不是补救;跳过的内容不补听 |
| 周期裁剪 | 每 30 秒裁掉"播放头 − 10 秒"之前的旧数据 | 内存与收听时长解耦 |
| 余量自适应 | 余量下限 0.2 秒;网络抖动大时自动加厚(上限 2 秒),连续 45 秒不卡再收回 | 0.2 秒是"再低就开始脆"的位置 |

* 断线/暂停恢复:重建媒体源 + `sync`,**从直播边缘续接**(不补断网与暂停期间的内容);连接关闭后退避重连(1s 起 ×2,**上限 2 秒**),并监听网络恢复事件立即重试
* 起播:点击到出声 ≤3s;媒体元素需要手里有两三片数据才肯持续出声,这是余量下限的来源
* 页面不因切后台主动停止播放(不主动放弃);何时被系统挂起由浏览器决定

### 6.5 错误与权限变化的处置

| 情形 | 前端行为 |
| --- | --- |
| 连接中断 / 收不到帧(>10s) | 退避重连(上限 2s),状态行显示原因;媒体元素继续播完已缓冲内容 |
| `auth_failed`(会话失效/账号停用) | 提示"会话已失效",跳登录(带回跳) |
| `auth_failed`(无权限) | 提示"权限不足/权限已被取消",**立即停止播放**并释放媒体元素 |
| `error(AUDIO_BUSY)` | 退避重连(设备正在释放/采集刚起,稍后即可) |
| `error(AUDIO_NO_DEVICE / AUDIO_DEVICE_LOST)` | 状态置无设备,提示"服务器无可用音频设备",回到空闲(可重试) |
| 换流(`streamId` 变化) | 重建媒体源并跳回直播边缘;仅在提示行说明一次 |

### 6.6 后台与锁屏(如实告知)

* 播放期间必须设置 MediaSession 元数据与动作:标题(如"服务器音频")、播放/暂停/停止;锁屏与通知栏可见、可控
* **不承诺锁屏/切后台连续收听**:页面被系统冻结时会断流(与传输方案无关),回前台自动重连并接回直播边缘;界面文案不得写成"锁屏也能继续听"
* 切到别的模块(页面常驻、仅被隐藏)时继续播放,不做主动降级
* 不做进度条与拖动(直播流无终点);时长信息不下发
* 页面被系统回收、浏览器被完全关闭、手机重启后不会继续(不做常驻与自启)

### 6.7 播放特效

* 特效区在播放中呈现律动效果,停止时复位;圆环与主按钮同心
* **特效不得破坏播放**:优先采用不需要接入音频数据的形式(按播放时间驱动的律动/呼吸动画);不要把声音接进 WebAudio 做分析(如 `createMediaElementSource`)—— 页面被系统挂起时 WebAudio 会被中断,连带把声音一起停掉
* 用户偏好"减少动态效果"(`prefers-reduced-motion: reduce`)时不做动画,其余功能不变

### 6.8 交互细节

| 元素 | 行为 |
| --- | --- |
| 主按钮 | 点击开始/停止(同一按钮切换);停止 = 关闭连接即离场 |
| 音量滑杆 | 0~100,作用于媒体元素音量,**本地记忆**(localStorage,默认 100);移动端也可用系统音量键 |
| 参数行 | `48kHz · 64kbps · 立体声 · 延迟 Nms`;延迟 = 已收到的最新片结束时刻 − 本地已播位置,每秒刷新(界面读数比真实端到端少算最后一跳的几十毫秒) |
| 听众列表 | 每 5s 轮询 `/status` 更新;`lagMs = -1` 显示"未上报",暂停中的连接显示"已暂停";未播放时显示"未在收听" |
| 侧边栏图标 | 为 `serverAudioStream` 增加模块图标映射(默认网格图标不达意) |

### 6.9 前端接口封装

* `frontend/src/api/audio.js` 提供:`openAudioWs({...})`(建连并分发帧)、`wsSend(obj)`(控制帧)、`audioApi.status()`(状态与听众列表)、`newClientId()`、`goLogin()`
* 二进制帧自行解帧(首字节类型 + 起始片号);`splitBatch()` 复用于分片批
* API 基址集中在 `frontend/src/api/base.js`,端口可用构建期变量覆盖(测试环境副本据此换端口)
* 前端记录并上报 `client` 标识,便于服务端区分同一账号的多端

## 7. 数据与配置需求

* **不新增数据库表**:起播缓冲、连接注册表、片号全在内存;进程重启即回到空闲态,无需持久化
* 分片**不落盘**:不做磁盘缓存与归档(§1.3 不做存档)
* 需要持久化的只有权限点本身(落在 `user.db` 的 `permissions` 表,与文件中心同机制)
* 采样率、码率、片长、缓冲窗口、心跳与超时等均为编译期常量,本期不开放运行时配置
* 收听行为**不写业务审计日志**(属实时通道,不落库);采集启停与设备失败原因记运行日志,听众只记"进入"与"离场"各一条(避免刷屏)

## 8. 与相邻模块的边界

* 文件中心负责"文件的字节",本模块负责"正在播放的声音",两者不重叠
* 复用基座能力:会话鉴权、模块权限、工作池、WebSocket 路由注册、同站跨端口的跨域放行
* 不依赖文件中心的数据与目录结构;本模块不读写文件空间

## 9. 主流方案对照与取舍依据

本节记录"这类需求当前怎么做"的调研结论,取舍结果落在 §10.1。

### 9.1 对照表

| 方案 | 代表实现 | 局域网延迟 | 手机后台/锁屏 | 浏览器支持面 | 服务端成本 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| WebRTC(WHEP,Opus/UDP) | MediaMTX、Pion、Cloudflare Stream | 20~100ms | **被系统挂起**:iOS 切后台约 1s 即断(WebKit 226163) | 全平台(桌面与移动) | 高:需引入 WebRTC 栈(ICE/DTLS/SRTP)、新增 UDP 端口 | 不采用:服务端成本与现有部署不符 |
| WebSocket + WebCodecs + WebAudio | 自建(语音 AI 类项目的通行做法) | 100ms 起(TCP 队头阻塞) | **被系统挂起**:AudioContext 在 iOS 后台被中断(WebKit 237878/281955) | Chrome/Edge/Android 较好,Safari 16.4+ 可用 | 中:需自研拆帧/排播/丢帧恢复 | 本期不采用:延迟收益约 100~200ms,但要换掉整条播放链路(双路径回退、放弃媒体元素能力),与"200~500ms 够用"的目标不成比例 |
| **媒体元素 + MSE(WebM/Opus)** | LL-DASH/CMAF 系实践;各类网页音乐播放器 | 200ms~1s | **可后台/锁屏**:判据是"元素里有可解码的音轨且未静音",由浏览器播放线程继续(实际是否被系统冻结仍取决于平台) | 安卓 Chrome 与桌面 Chrome/Edge/Firefox 均支持 MSE 与 WebM/Opus | 中:需自研分片封装,不引入新依赖 | **采用**(§10.1) |
| 原生 HLS(含低延迟 HLS) | Apple 生态标准,各类直播产品 | LL-HLS 约 1~2s | 可后台(Apple 原生最优) | Chrome/Firefox 需引入 hls.js;Safari 原生 | 高:播放列表 + 部分片 + 多码率 + 打包 | 不采用:延迟更高、实现成本更大 |
| Icecast / Ogg 连续流 | 网络电台 | 1~5s(浏览器缓冲不可控) | 可后台 | **Safari 不支持 Ogg/Opus** | 低 | 不采用:延迟不可控 |
| Snapcast + Snapweb(WebSocket + WebAudio) | Snapcast 多房间同步 | 默认 1s 缓冲(面向多房间同步,非低延迟) | 不可后台(浏览器端走 WebAudio) | 好 | 中 | 不采用:为多房间同步设计;其"按片调度"思路可借鉴 |
| WebTransport / MoQ | moq.dev | 150ms~ | 不可后台(仍走 WebAudio/WebCodecs) | Safari 26.4 起可用但仍有缺陷,标准尚未定稿 | 高:需 HTTP/3/QUIC 服务端 | 暂不采用:前沿但未成熟,留作后续观察 |

### 9.2 结论

1. **传输层选 WebSocket 推流**:采集一产片即推、无轮询往返、连接可探活;拉取式(按片 HTTP 请求)在弱网下的续约丢失、静默假死、每片一次鉴权三类问题都在结构上消除。
2. **播放仍交给媒体元素 + MSE**:它保留了"切到别的模块继续播"的能力,且不引入新依赖;WebCodecs/WebAudio 那条路延迟更低约 100~200ms,但要换掉整条播放链路,本期不做(§9.1)。
3. **取舍为延迟优先**:低延迟通道与"后台/锁屏连续"在本代浏览器上不可兼得;用户选定"点开就近乎实时",因此后台/锁屏如实告知不承诺,断开恢复一律回到直播边缘。
4. 服务端只保留 **1 秒起播缓冲**:既然不回补历史,就不需要保留可回头的窗口;这也让"内存与收听时长无关"更容易保证。
5. 本期只做安卓,因此不需要第二条出口(MP4 容器 + AAC 编码,那是 iOS 才需要的);将来若要支持 iOS,按 §9.1 的对照结论补一条出口即可,补之前需先确认目标系统上的 AAC 编码器可用。
