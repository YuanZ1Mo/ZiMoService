## 1. 背景与目标

### 1.1 背景

平台需提供统一文件存储与分发能力,承载公共资源(如发布件、说明文档)与个人私有文件(个人空间)。文件中心作为门户下的一个模块接入,与用户系统共用会话、鉴权与模块权限体系。

现有实现说明:仓库中不存在可复用的文件中心实现(旧 `FileHubModule` 的 JRPC 入口已随门户重构移除,自测计划已标注废弃)。本模块为**全新实现**,数据落独立库 `filehub.db`,与 `user.db` 物理隔离。

### 1.2 业务范围

| 域 | 说明 |
| --- | --- |
| 双空间浏览 | 公共空间(space=0)与个人空间(space=uid)两级模型;面包屑导航、排序、筛选 |
| 搜索 | 当前文件夹及子文件夹内按名称模糊搜索(目录名 + 文件名),结果携带完整相对路径 |
| 目录/文件常规操作 | 新建文件夹、重命名、移动(可跨空间)、复制(可跨空间)、删除(含批量删除) |
| 回收站 | 删除为软删除(进回收站,物理文件不动);回收站列表、恢复、彻底删除、清空;保留 30 天,占用配额 |
| 上传 | 单文件上传、多文件上传、文件夹(递归建目录)上传、队列化、上传进度展示、失败重试、取消上传 |
| 下载 | 单文件直链下载(可触发浏览器/IDM)、Range 断点续传、>4GB 大文件 |
| 打包下载 | 多选/整目录 zip 打包下载(在公共空间/个人空间内的缓存目录以 `uid_时间戳` 为压缩名先压缩好再按直链下载;压缩包装缓存,最后访问后空闲 3 小时/超 24 小时由缓存回收清理) |
| 传输任务队列 | 上传/下载统一入库记录,提供队列历史与结果轮询,多文件下载时未产生直链时显示打包中且可以取消(单文件直链下载不建任务,理由见 §3.9.3) |
| 分享 | 文件/目录生成分享链接(含二维码),默认免登录访问(可选提取码、有效期、次数上限、仅登录可见);分享下载日志 |
| 文件中心管理 | 手动触发文件系统与数据库一致性同步(以磁盘为准修复漂移) |
| 后台维护 | 每日一致性校验、回收站保留期清理、分享下载日志清理、传输任务清理 |
| 审计 | 上传、打包、下载行为记入该模块的数据库的业务日志 |

### 1.3 非目标(本期明确不做)

* 文件内容全文检索(仅按名称匹配)
* 在线预览与缩略图(图片/视频/PDF/Office 预览、视频转码、封面抽取)
* 文件版本历史(取舍见 §8.3)
* 回收站的**保留期自定义**(本期固定 30 天,不提供按用户/按空间的差异化配置)
* 桌面/移动端同步客户端、WebDAV 挂载、FTP/S3 等外部存储策略
* 视频/音频在线播放(远程音频流由音频模块承担,文件中心只负责字节下载)
* 多人协同编辑、评论、@提醒
* 传输加密以外的内容级加密(分享加密压缩包、服务端静态加密)

## 2. 全局约定

### 2.1 空间模型

* **公共空间**(space=0):共享资源池,所有登录用户可浏览与下载
* **个人空间**(space=uid):每位登录用户一个,仅本人可见、操作
* 注册用户首次访问个人空间时懒创建(文件系统目录 + 数据库空间根行,幂等)
* 空间语义:空间切换是页面的第一级导航

空间根行(`spaces` 表)与空间根目录(文件系统)一一对应:

| space | 物理目录 | 数据库根行 |
| --- | --- | --- |
| 0 | `space\0` | 首次建库时创建 |
| uid | `space\<uid>` | 该用户首次访问时懒创建 |

### 2.2 会话与鉴权

* 所有业务接口(除分享公开面与下载令牌直链)须携带有效会话;401 → 前端统一跳登录
* 接口鉴权沿用用户系统 `AuthAndTouch`;页面与 API 跨端口同站,Cookie 同站点传输
* 模块门禁:接口直调需命中该用户可见模块清单,未授权返回 403(防绕过前端隐藏直接调接口)

#### 2.2.1 权限点分层(沿用用户系统现行模型)

`permissions` 表的 `type` 字段区分两类权限点,文件中心两个权限点分属两类:

| type | 含义 | 约束 | 作用 |
| --- | --- | --- | --- |
| `0` | **门户模块** | 必须有所属 `url` 与非 0 `index` | 决定**侧边栏入口**可见性;`index` 仅用于排序(现版本侧边栏已不显示序号) |
| `1` | **功能权限** | `url` 为空、`index=0` | 不进侧边栏;决定**子功能显隐与 API 访问**(如系统管理内的子标签) |

#### 2.2.2 本期新增的两个权限点

用户系统在权限点重构中已**移除**原预留的 `filehub` / `filehubAdmin`,故本期按新模型**新增**这两条(不是"启用预留"):

| code | 名称 | type | module | url | index | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| `filehub` | 文件中心 | `0` 门户模块 | `filehub` | `/portal/filehub` | `2` | 侧边栏入口(index=2,排在用户主页 1 之后、系统管理 -1 之前) |
| `filehubAdmin` | 文件中心管理 | `1` 功能权限 | `system` | *(空)* | `0` | 不进门户清单;作为系统管理页的子标签 + 其 API 的授权点 |

> **与用户系统的对应关系**:`systemManager`(门户入口,type=0,index=-1)对应"系统管理"侧边栏入口;`userManage`(功能权限,type=1)对应"用户管理"子标签。文件中心的 `filehubAdmin` 与 `userManage` **完全同型** —— 都是挂在 `system` 域下的功能权限点。
> `permissions.module` 是**功能域**:`systemManager` / `userManage` / `filehubAdmin` 三者的 `module` 均为 `system`。
> **前端消费方式**(现行机制):`/portal/home` 接口下发**有效权限码全集**(含功能权限点),前端存入会话(`stores/session.js` 的 `permissions`),子标签按权限码显隐 —— 系统管理页的子标签列表形如 `{key:'users', perm:'userManage'}`;文件中心管理按同一模式追加 `{key:'filehub-admin', perm:'filehubAdmin'}`。无该权限时子标签不渲染,且服务端 API 返回 403(双重拦截)。
> **默认可见性**:`filehub`(门户模块)对所有角色开放 —— 三个内置角色的 `permission_codes` 增加 `filehub`;`filehubAdmin`(功能权限)默认仅 developer/admin 拥有(与 `userManage` 一致),可通过单人授权单独授予。
> **关于用哪个点守接口**:文件中心**不设独立的功能权限点**,门户点 `filehub` 同时充当 API 门禁点(与用户系统不同 —— 那边 `systemManager` 管入口、`userManage` 管 API)。原因是文件中心没有"能进模块但不该用某子功能"的场景:能看见入口就该能用。`filehubAdmin` 则只用来守管理端接口。

### 2.3 角色与写权限

| 空间 | 读 | 写(建/改/删) | 回收站 |
| --- | --- | --- | --- |
| 公共空间 | 任意登录用户 | 任意用户 | **只看/只管自己删的**(§3.7.2) |
| 个人空间 | 仅本人 | 仅本人(`space == 登录 uid`) | 仅本人(等价于"自己删的") |

> 个人空间规则写死:任何接口对个人空间目标都校验 `opUid == space`,无豁免分支。
> 公共空间"任意用户可写"为**已确认取定的策略**(风险与备选方案见 §8.4);回收站按"谁删的谁管"划分,既保留了误删自救能力,又避免"任一人清空、全员不可恢复"。
> 全量回收站(跨用户查看与整体清空)收归管理端 `filehubAdmin`,见 §3.13。

### 2.4 路径与数据一致性原则(核心约束)

* **路径一律由数据库 id 沿 parent 链组装**,不接受客户端原始路径 → 路径穿越在机制层消失
* 写操作顺序:**鉴权/冲突检查(DB)→ 文件系统 → DB → 审计日志**;DB 失败回滚文件系统;同名冲突在锁内做最终裁决,后到者 409,不触碰先到者物理文件
* 文件系统是事实源,数据库是索引:状态漂移由一致性校验以磁盘为准修复
* 支持以 `.` 开头的隐藏文件/目录(视为普通条目)
* **可见树约定**:所有常规操作(浏览/搜索/上传/新建/改名/移动/复制/分享/下载)只作用于 `deleted=0` 的可见条目;回收站条目只能通过 §6.4 的回收站接口操作。位于回收站内的条目(自身 `deleted=1`,或祖先链上有 `deleted=1`)**不可**被常规接口寻址,命中即返回 404(与"不存在"同构,不泄露回收站内容)

物理路径映射规则:

```
公共空间条目:  <exe>\modules\filehub\space\0\<沿 parent 链的 name 逐级拼接>
个人空间条目:  <exe>\modules\filehub\space\<uid>\<沿 parent 链的 name 逐级拼接>
```

* 物理目录名与逻辑名**严格一致**(可被运维直接浏览、备份、镜像;一致性校验才有意义)
* 名称已按 §4.1 校验(不含路径分隔符),拼接后不存在穿越
* 物理路径长度上限:拼接结果 ≤ 240 字符(为 `\\?\` 前缀与临时后缀留余量),超限拒绝创建并返回 `PATH_TOO_LONG`;服务端拼接物理路径统一加 `\\?\` 前缀绕过 Windows `MAX_PATH` 限制

### 2.5 存储与库

* 文件本体:`<exe 同目录>\modules\filehub\space\<space>\...`(0=公共,uid=个人)
* 缓存文件夹(打包、上传分片等其他临时操作):`<exe 同目录>\modules\filehub\space_cache\<space>\...`(0=公共,uid=个人,即每个空间独立缓冲区)
  * 打包产物:`space_cache\<space>\zip\<uid>_<时间戳>_<随机串>.zip`
  * 上传分片:`space_cache\<space>\chunk\<upload_id>\<分片序号>.part`
* 数据库:`<exe 同目录>\db\filehub\filehub.db`
* 模块/权限:user.db

### 2.6 页面组织与前端形态

* 文件中心为门户下的**嵌入模块**,由服务端模块清单驱动,见门户契约;无权限用户侧边栏不渲染、接口 403
* 业务 API 走 RESTful 端口(39441 `/zimo/api`)
* 前端模块目录(`modules/` 下一级目录 = 门户模块,与权限点 code 的 kebab-case 一一对应):
  * 文件中心:`frontend/src/modules/filehub/index.vue`,由 `import.meta.glob` 自动挂载,路由 `/portal/filehub`
  * 文件中心管理:`frontend/src/modules/system-manager/FileHubAdmin.vue`(系统管理的子页,不占顶层模块目录),路由 `/portal/system-manager/filehub-admin`
  * 说明:系统管理的模块目录已由 `user-manager` 更名为 **`system-manager`**(与门户权限点 `systemManager` 的 kebab-case 对齐);文件中心管理页挂在其下,不单独占顶层模块目录
* **分享页例外**:`/s/{token}` 为**免登录页面**,需加入服务端门禁白名单(`IsWhitelistPagePath`)与前端路由(`meta.public`);该页不在门户壳内,为独立全屏页

### 2.7 并发与锁模型

* **目录级写锁**:键 = `(space, parent_id)`。同一目录下的新建/重命名/移动入/移动出/删除**串行化**执行,冲突裁决(§2.4)在该锁内完成
* 跨目录操作(移动、复制)按 `(space, dir_id)` 升序加锁,避免死锁;跨空间移动按 `(space, dir_id)` 字典序加锁
* 锁为**进程内**结构(单进程部署);实现上采用按目录散列的互斥量,不引入全局大锁
* 文件内容写入采用"**临时文件 + 原子改名入位**":上传/复制过程中读到的是完整旧文件或完整新文件,不存在半成品可见窗口
* 长耗时操作(打包、目录复制、目录删除)在**工作池**执行,不占用事件循环;其持有的目录锁按"单目录事务"粒度短持有,不整段持锁

### 2.8 性能指标(基线)

> 口径:单机部署(单服务进程 + 本地 SQLite);延迟为 P95;吞吐为持续值。

| 指标 | 基线 | 说明 |
| --- | --- | --- |
| 列目录接口 P95 | ≤ 200ms | 单目录 1000 条以内(含面包屑) |
| 搜索接口 P95 | ≤ 800ms | 单空间 10 万条目、递归子目录、关键词命中 ≤ 500 条 |
| 单文件下载吞吐 | ≥ 500MB/s | 局域网直连;不占工作池,但读盘在事件循环上(见 §3.9.3) |
| 单文件上传吞吐 | ≥ 200MB/s | 分片写入,校验和计算并行 |
| 打包吞吐 | ≥ 100MB/s | 可按扩展名跳过已压缩格式 |
| 并发上传任务 | ≥ 20 | 单用户并发上限 3(前端队列) |
| 并发直链下载 | ≥ 100 | **需设全局闸门**(不只是令牌级的 ≤5 连接);Windows 下读盘在事件循环上,并发过高会连带拖慢所有接口 |
| 并发打包任务 | ≤ 2 | 超出排队。工作池**自动扩容**(初始线程数只是起点,上限 `ZM_POOL_MAX_THREADS = 128`),因此限的是**同时进行的任务数**,不是线程数 |
| 单目录条目上限 | **不设硬上限** | 列表已分页,技术上无需限制;真瓶颈在打包(独立 5000 条上限)与一致性同步 |
| 单文件大小上限 | 20GB | 可配置;分片上传支撑 |
| 单次打包条目上限 | 5000 个 / 20GB | 超出拒绝并提示分批 |

## 3. 功能需求

### 3.1 浏览(列表)

**入口与结构**

* 页面顶部为空间切换(公共空间 / 我的空间),切换空间回到该空间根目录
* 内容区为当前目录的条目列表 + 面包屑;面包屑由服务端沿 parent 链返回祖先数组(含每级 id 与名称),点击任意层级可直接跳转
* 目录与文件**同表同列**(见 §5.3),列表中目录恒排在文件之前,组内再按当前排序规则排列

**列表字段**

| 列 | 说明 |
| --- | --- |
| 名称 | 目录/文件显示名;文件带扩展名图标 |
| 类型 | 目录 / 文件(含扩展名归类:文档/图片/视频/音频/压缩包/其他) |
| 大小 | 文件为字节数(前端人性化格式);目录显示直接子项数(`items`),总计大小不实时计算,经"统计"接口按需获取 |
| 修改时间 | `update_time`,前端按本地时区展示 |
| 创建者 | 公共空间展示 `owner_uid` 对应昵称(同步补建的条目为 0,展示"系统");个人空间不展示 |

**排序与筛选**

* 排序字段:名称 / 大小 / 修改时间 / 类型;升序 / 降序,目录恒在前
* 名称排序规则:按 Unicode 码点序(与文件系统 `FindFirstFile` 顺序无关,以 DB 排序为准);前端可对当前页做本地二次排序
* 筛选:按类型(目录/文档/图片/视频/音频/压缩包/其他)、按修改时间(今天/近 7 天/近 30 天/自定义区间)

**分页**

* 默认一次返回最多 200 条;支持 `page`(≥1)+ `size`(1~1000)
* 前端默认无限滚动追加(每次 200 条),滚动到底自动加载下一页;条目总数随首页响应返回

**空状态与异常**

* 空目录:展示"此目录为空"空状态与"上传文件"引导按钮
* 目录在磁盘上被外部删除:列表仍按 DB 返回,点击进入/下载时返回 404,前端提示并建议触发一致性同步

**其他约定**

* 支持以 `.` 开头的隐藏条目,作为普通条目参与列表、排序、搜索(不做隐藏/显示开关)
* 目录的 `update_time` 在其直接子项增删改时同步刷新(父目录时间戳随动),便于前端做增量刷新

### 3.2 搜索

* 范围:**当前目录及其全部子目录**(递归),仅限当前空间
* 匹配:名称**模糊匹配**(`LIKE %关键词%`),不区分大小写(ASCII);不支持通配符与正则
* 关键词:1~64 字符,去首尾空白;空关键词直接返回空结果(不发全量查询)
* 结果字段:名称、类型、大小、修改时间、完整相对路径(相对空间根,逐级可点击跳转)、所在目录 id
* 结果上限 500 条;达上限时响应标记 `truncated=true`,前端提示"结果过多,请缩小范围"
* 排序:默认按"所在层级由近及远,同级按修改时间倒序";支持切换为按名称/大小/时间排序
* 权限:个人空间仅本人可搜;公共空间任意登录用户可搜
* 实现约束:递归子树用 `WITH RECURSIVE` 从 `dir_id` 展开(走 `(space, parent_id)` 索引),再对 `nodes.name` 做 `LIKE`;**不引入全文索引**
* 高亮:前端对结果名称中的命中片段做高亮(服务端不下发额外标记)

### 3.3 新建文件夹

* 位置:当前目录下
* 名称校验:见 §4.1
* 冲突:同级同名(含大小写差异)→ 409 `NAME_EXISTS`
* 上限:**单目录不设条目数上限**(列表已分页);路径深度达 32 层 → 400 `PATH_TOO_DEEP`
* 行为:先在 DB 事务内做冲突检查与插入,再创建物理目录;物理创建失败则删除 DB 行
* 返回:新建目录的 `{id, name, create_time}`
* 单次只建一级(不做 `a/b/c` 一次建多级);文件夹上传的内部建目录走 §3.8 的 `dirs/ensure_batch` 接口

### 3.4 重命名

* 对象:单个目录或文件(不支持批量重命名)
* 名称校验:同 §4.1
* 冲突:同级同名(排除自身)→ 409 `NAME_EXISTS`
* 文件重命名不限制扩展名(允许改名成任意合法名称),前端在改动扩展名时给出二次确认提示
* 目录重命名**不触碰子孙记录**:路径由 parent 链组装,故子孙的 `parent_id` 与名称均无需变更;仅更新该行 `name` 与 `update_time`,并同步刷新父目录 `update_time`
* 写序:DB 改名(事务)→ 文件系统改名(同空间同盘,原子 `MoveFile`)→ 失败回滚 DB;物理改名失败(如文件被占用)返回 409 `FILE_LOCKED`

### 3.5 移动

* 对象:目录 / 文件,支持多选批量
* 目标:任意空间内的任意目录(可跨空间);目标必须为目录且存在
* 合法性校验(逐条预检,全部通过才执行):
  * 目标目录不能是自身
  * 目标目录不能是待移动目录的子孙(**环路检测**:沿目标目录的 parent 链上溯,命中任一待移动目录 id 即拒绝 400 `MOVE_INTO_SELF`)
  * 批量移动中含"祖先与子孙同时被移动"时,自动折叠为只移动祖先(子孙随行)
  * 移动集合内部不得互相冲突(同一目标下重名)
* 冲突:目标目录已存在同名条目 → 按 `conflict` 参数处理(默认 `ask`:409 `NAME_EXISTS` + 冲突清单);用户在前端选择后可按 `skip`/`rename`/`overwrite` 重试整批
* **批量操作的粒度分两个阶段**(这一点容易混):
  * **冲突裁决** —— **整批**:发现任一冲突就整批拒绝、一个都不动。理由:用户选了 `ask`,应当先看到完整冲突清单再决定,而不是被先改一半
  * **执行** —— **逐条**:裁决通过后逐条执行,某条物理操作失败(被占用等)只标记该条失败、其余继续,响应 `{success:[], failed:[{id,name,code}]}`
  * 两阶段不矛盾:"不做部分成功"指的是**执行阶段不回滚已成功的条目**,不是"整批全成全败"
* 权限:源条目可读可删(个人空间源 → 仅本人),目标空间可写(个人空间目标 → 仅本人)
* 跨空间移动**只改 `space`**:`owner_uid` 语义恒为"创建者",不因移动而改写(否则"谁创建的"这一信息会在搬运中丢失);"谁搬进来的"由审计日志记录
* 因此 `owner_uid` 可能与 `space` 不一致(例:用户 A 的个人文件被 A 移入公共空间后,`space=0` 而 `owner_uid=A`)——这是预期行为,列表的"创建者"列展示的正是后者
* **移动时改哪些字段(顶层与子孙不同)**:
  * **顶层条目**(用户选中的那些):`space` 与 `parent_id` 都要改 —— 换了空间,也换了父目录
  * **子孙条目**:只改 `space`,`parent_id` 不动 —— 它们跟着父目录走,自身的父子关系没变
  * 事务内用 `WITH RECURSIVE` 展开子树,两类行分开 UPDATE
* 物理实现在 DB 之前:若后续 DB 更新失败,**必须把已搬动的物理文件搬回原位**;搬不回去则记错并交给一致性同步修复(这是"先物理后 DB"顺序的固有代价,回滚路径不能省)
* 物理实现:同盘走 `MoveFileEx`(原子);不同盘或跨空间走"复制 + 校验 + 删除",失败回滚(DB 与已产生的物理副本一并清理)
* 审计:记录每条的源路径与目标路径

### 3.6 复制

* 对象:目录 / 文件,支持多选批量
* 目标:任意空间内的任意目录(可跨空间)
* 合法性校验:同 §3.5 的环路检测(复制到自身子孙同样拒绝);复制目录到其子孙会导致无限展开
* 冲突策略(请求参数 `conflict`,四选一):
  | 值 | 行为 |
  | --- | --- |
  | `ask`(默认) | 服务端不自行裁决,返回 409 + 冲突清单,由前端弹窗让用户选择 |
  | `skip` | 跳过冲突项,保留已有,返回成功与跳过清单 |
  | `rename` | 冲突项自动重命名:`name (1).ext`、`name (2).ext`,依次递增直至无冲突 |
  | `overwrite` | 覆盖(仅对**文件**生效;目标为目录时按 `rename` 处理,不做目录合并) |
* 复制目录 = 递归复制全部子孙:DB 事务内用 `WITH RECURSIVE` 复制子树行(id 重新分配),物理层递归 `CopyFile`
* 空目录同样被复制(不丢层级)
* 规模阈值:待复制条目数 > 500 或总字节 > 1GB 时,**转为传输任务异步执行**(§3.11),接口立即返回 `task_no`,前端在任务面板展示进度;阈值内为同步执行
* 硬上限:单次复制的源条目数 ≤ 2000(§4.1 的批量参数上限),超出 400 `BATCH_TOO_LARGE`;展开后的子孙数不受此限(由目标空间配额与磁盘容量约束)
* 配额:目标空间为个人空间时校验配额(§4.5)
* 审计:记录源路径、目标路径、条目数、字节数

### 3.7 删除与回收站

#### 3.7.1 删除(进回收站)

* 对象:目录 / 文件,支持多选批量与整目录删除
* **删除为软删除**:条目进入回收站,**物理文件保持原位不动**
* 目录删除以**整棵子树**为单位:
  * 只对被删的**顶层条目**置软删标记(`nodes.deleted=1`、`delete_time`、`origin_parent_id` 记下原父目录)
  * 子孙行**不逐个改写**:它们随祖先的软删而不可达(列表从空间根沿 `parent_id` 展开,走不到被软删的目录)
  * 这样一次删除目录只写 1 行,不受子树规模影响;代价是"子树内条目是否在回收站"要按**祖先链**判断,见 §5.3 的查询约定
* 同名再创建:软删的条目**不占用**同级名称(唯一索引带 `WHERE deleted=0` 条件),删除 `a.txt` 后可立即新建同名 `a.txt`,两者互不影响
* 批量删除上限:单次 2000 条(顶层条目数),超出分批
* **重复删除同一个条目**:以 `deleted=0` 为条件,已在回收站的条目不会被二次处理 —— 否则会把 `origin_parent_id`(原位置)与 `del_owner_uid`(谁删的)覆盖掉,这条回收站记录等于过户给了后删的人
* 权限:个人空间仅本人可删;公共空间任意登录用户可删(§2.3)
* 审计:记录被删条目的完整相对路径、类型、大小;目录额外记录子树条目数与总字节数(子树规模在删除时统计一次并写入审计 detail,供"彻底删除"预估耗时)
* 删除前**不做**物理删除确认(由前端二次确认弹窗承担);服务端不引入"删除确认令牌"

#### 3.7.2 回收站

**可见范围(按"谁删的"划分,不再按空间划分)**

| 角色 | 可见与可操作范围 |
| --- | --- |
| 普通用户 | **只看得见自己删除的条目**(`del_owner_uid == 自己`):可恢复、可彻底删除、可清空(只清自己的这一批) |
| 管理员(权限点 `filehubAdmin`) | 在文件中心管理中可见**全量回收站列表**(跨用户、跨空间),可做**整体清空** |

> 这样划分解决了"一个人清空回收站,毁掉全员误删内容"的问题:普通用户点"清空"只销毁自己删的那批,不会碰到别人的。
> 空间对个人空间无实质影响:个人空间本就只有本人能删,所以"自己删的"就是全部。该规则对公共空间与个人空间一致,不需要分支。
> 恢复与彻底删除的**对象校验**:接口必须校验目标条目的 `del_owner_uid == 操作者`(管理员例外),否则返回 404(与"不存在"同构,不泄露他人回收站内容)。

**列表**

* 字段:名称、类型、原路径(`origin_parent_id` 沿 parent 链组装,父目录已被删时标记为"原目录已删除")、大小(目录为子树条目数与字节数)、删除时间、删除者(`del_owner_uid` 快照)
* 排序:按删除时间倒序(默认);支持名称排序
* 分页:同普通列表(默认 200)
* 顶部展示:**我删除的条目**占用(条目数与字节数;不是该空间回收站的全部占用)、保留期说明(30 天)
  * 与之对应,空间用量接口返回的"回收站占用"也按**当前用户自己删的**口径给用户侧(管理端另给全量口径);两者都不影响 `spaces.used_size` 的记账 —— 配额始终按空间全部占用算
* 同名条目:回收站内允许多个同名条目并存(来自不同目录),列表用"原路径"区分

**可用操作(回收站内为只读 + 三个动作)**

| 操作 | 说明 |
| --- | --- |
| 恢复 | 恢复到原位置;原位置被占用或原父目录已被删除 → 恢复到空间根,并自动重命名 `name (1)`、`name (2)` 直至无冲突 |
| 彻底删除 | 物理删除,顺序**必须先物理、后删行**(按顶层条目逐个处理):① 展开子树收集物理路径 → ② 先做物理删除 → ③ 物理删成功才删掉这棵子树的全部行并释放配额;失败则整条保留(行一行都不动) |
| 清空回收站 | 对当前空间内全部回收站条目执行彻底删除;需二次确认(前端展示"将永久删除 N 个条目,共 X GB");在**工作池**异步执行,复用传输任务(类型=回收站清理),前端展示进度 |

* 回收站内**不支持**重命名、移动、复制、新建、上传(避免"回收站内的条目又被引用"的复杂状态)
* 恢复**不涉及配额校验**:回收站条目本就计入 `used_size`(§4.5),恢复只是把它重新变为可见,总量不变
* 恢复与彻底删除均记审计(`restore` / `purge`)
* 接口的对象校验:`ids` 中任一条目的 `del_owner_uid != 操作者` 且操作者非管理员 → 该条返回 404 `TRASH_ITEM_NOT_FOUND`,不区分"不存在"与"不是你的"

**保留期与清理**

* 保留期 **30 天**:超过 30 天的回收站条目由每日周期任务物理删除(§3.14)
* 回收站内条目**占用空间配额**(直到彻底删除);回收站页面明确展示这部分占用,避免用户"删了却没释放空间"的困惑
* 彻底删除失败(文件被其它进程占用):该条目标记失败并**保留在回收站**(不丢行),响应返回失败清单;下轮周期清理重试
* **为什么必须先物理、后删行**:若先删行再删物理文件,一旦物理删除失败,磁盘上的文件就成了"库中无记录"的孤儿 —— 而下一次一致性同步以磁盘为准,会把它**补建回来**。结果是删了个寂寞,且补建出来的记录归属显示为"系统"。所以回滚单位是**顶层条目**:物理没删干净,这棵子树的行就一行都不动

**一致性校验的配合**(重要)

软删条目的物理文件仍在磁盘上,同步时必须避免误判,否则回收站会被补建出重复条目:

* **磁盘 → 库**(补建方向):比对"库中是否已有"时,`deleted=1` 的行**同样计入已登记**,不补建
* **库 → 磁盘**(删行方向):只对 `deleted=0` 的行判定"磁盘缺失"并删行;`deleted=1` 的行**跳过**(物理缺失属正常,由彻底删除或保留期清理收尾)
* 同步的用量重算:计入 `deleted=1` 占用(与 §4.5 的"回收站占用"规则一致)

### 3.8 上传

#### 3.8.1 任务模型

* 每次"选择文件"产生 N 个上传任务(每文件一个任务),统一记入 `transfer_tasks`(见 §5.6)
* 前端队列:并发上限 3,超出排队;队列顺序即用户选择顺序
* 任务可取消(进行中/排队中均可)、可重试(失败任务)
* 文件夹上传:先按相对路径**批量建目录**(`dirs/ensure_batch`,幂等),再把各文件派生成上传任务;同一批共享一个批次号,便于任务面板归组展示。批量建目录的校验规则见 §4.1"相对路径"行

#### 3.8.2 两种上传途径

| 途径 | 触发条件 | 说明 |
| --- | --- | --- |
| 单请求上传 | 文件 ≤ 8MB | 一次 POST 发送完整文件体,服务端流式落临时文件后入位 |
| 分片上传 | 文件 > 8MB | 初始化 → 逐片上传 → 完成合并;支持断点续传与秒传 |

分片参数:分片固定 8MB;分片总数 ≤ 2560(对应单文件上限 20GB)。分片大小与阈值均可配置。

#### 3.8.3 分片上传流程

1. **初始化** `POST /filehub/upload/init`
   * 入参:空间、目标目录 id、文件名、文件总大小、客户端整文件哈希(可选)
   * 服务端:校验权限与名称、**预检**同名冲突(仅回传冲突信息供前端提示,不在此时裁决)、创建上传会话(`upload_sessions`),在缓存区建分片目录
   * 冲突的**最终裁决在 `complete` 阶段、目录写锁内**执行(§2.4):上传期间目标目录可能被他人改动,提前裁决会作出过期判断
   * 若同名上传会话已存在(同用户同目录同名)且未过期:**复用该会话**,响应携带 `uploaded:[已完成的片号]`,前端只补传缺片(断点续传)
   * 响应:`{upload_id, chunk_size, chunk_total, uploaded, expire_time}`
2. **上传分片** `PUT /filehub/upload/chunk`
   * 入参:`upload_id`、片号、原始二进制体
   * 服务端:校验片号范围、写入 `<缓存区>\chunk\<upload_id>\<片号>.part`、登记 `upload_chunks`
   * 分片可乱序、可重复上传(重复上传覆盖该片),前端并发上传 3 片
   * 单片校验:比对实际字节数与声明长度,不一致返回 400 `CHUNK_SIZE_MISMATCH`
3. **完成合并** `POST /filehub/upload/complete`
   * 服务端:校验全部片到齐 → 按序合并为临时文件 → 可选校验整文件哈希 → 原子改名入位(§2.7)→ 落 `nodes` 行 → 更新父目录时间戳与空间用量 → 清理分片目录 → 任务置完成
   * 合并与入位在工作池执行,期间任务状态为"进行中",完成度按已合并字节数上报
   * 哈希不一致 → 400 `HASH_MISMATCH`,删除临时文件,保留分片供重试
   * **入位成功但落 `nodes` 行失败 → 必须删除刚入位的物理文件**(回滚)。否则磁盘上多一个库中无记录的文件,下次一致性同步(以磁盘为准)会把它**补建成一条 `owner_uid=0` 的记录**,表现为"上传失败的文件自己冒出来了"
4. **取消** `DELETE /filehub/upload/{upload_id}`:删除分片目录与上传会话,任务置已取消

#### 3.8.4 秒传(同内容去重)

* 初始化时若客户端提供了整文件哈希,服务端在**同一空间内**查找 `nodes` 中 `hash` 相同且 `size` 相同的文件:
  * 命中 → **先做同名冲突裁决(定下最终文件名),再按裁决结果 `CopyFile` 到位**,不再传输字节,响应 `instant=true`
    (顺序不可颠倒:先复制再裁决的话,`rename` 策略下文件会落在错误的名字上)
  * 未命中 → 走正常分片流程
* **不用硬链接**(虽然省一次本地复制):硬链接会让"删除一个副本不释放空间""配额按逻辑大小算两份"这两件事变得难以解释,而且删除/覆盖/彻底删除的语义都要额外区分。秒传的收益是**省掉网络传输**,本地复制一次的成本很小,不值得为它引入共享 inode 的复杂度
* 秒传命中仍需做同名冲突裁决与配额校验;审计日志记录"秒传"来源
* 去重范围为**同空间内**;跨空间不秒传(个人空间之间互相不可见,不泄露他人文件存在性)
* `nodes.hash` 为**整文件 SHA-256**,上传/秒传时写入;一致性同步补建的条目哈希为空(不主动计算)

#### 3.8.5 文件上传名称与覆盖规则

* 文件名净化:仅去掉路径分隔符与控制字符,不做其他改写;校验规则见 §4.1
* 同名冲突(`conflict` 参数,语义同 §3.6):`ask`(默认,返回 409) / `skip` / `rename` / `overwrite`
* `overwrite` 为**原子替换**:新内容写好并校验通过后,一次性改名覆盖,读方不会读到半成品;替换前的旧文件保留至新文件入位成功为止
* 0 字节文件**允许上传**(与旧实现不同,旧实现返回 400);空目录同样允许(文件夹上传时自然产生)

#### 3.8.6 限额与校验

| 项 | 规则 |
| --- | --- |
| 单文件大小 | ≤ 20GB(可配置);超出 413 `FILE_TOO_LARGE` |
| 单文件名称长度 | ≤ 255 字节 |
| 文件夹上传条目数 | 单批 ≤ 5000 个文件 / 1000 个目录;超出 400 提示分批 |
| 上传会话有效期 | 24 小时;过期后分片目录由周期清理回收,任务置"已中断" |
| 配额 | 个人空间校验(§4.5);超配额 403 `QUOTA_EXCEEDED` |
| 并发 | 单用户进行中的上传任务 ≤ 3;超出 429 `TOO_MANY_UPLOADS` |

#### 3.8.7 进度与失败处理

* 进度:单请求上传由浏览器上报 `progress` 事件;分片上传按"已完成片数 × 片大小"计算,前端的进度为客户端视角,服务端任务的 `done_size` 在合并阶段更新
* 失败重试:网络中断的分片上传,重走 `init` 得到缺失片清单继续;单请求上传则整体重传
* 页面刷新/关闭后:未完成的会话保留,用户再次上传同名同大小文件时复用会话续传
* 上传中若目标目录被他人删除:完成时返回 404 `DIR_NOT_FOUND`,任务置失败

### 3.9 下载(单文件)

#### 3.9.1 直链与下载令牌

* 单文件下载不直接暴露文件 id 与物理路径,统一走**短时下载令牌**:
  1. 前端 `POST /filehub/download/token`(入参:待下载条目 id 列表)换取令牌
  2. 令牌响应返回可直接使用的下载地址:`/zimo/api/filehub/dl/{token}/{urlencoded_filename}`
  3. 该地址**不依赖 Cookie**,可交给浏览器、IDM 等外部下载器
* 令牌属性:随机 32 字符;有效期 10 分钟;与 `(uid, node_id)` 绑定;可重复使用(支持 Range 多段并发);同一令牌最多服务 5 个并发连接
* **并发连接的计数必须成对**:响应开始 +1、响应结束 -1,且结束那次要挂在响应完成回调上 —— 客户端中途断开/发送失败也必须能减回去。否则一次断连就吃掉一个名额,令牌在剩余有效期内再也下不动
* 令牌只授权"下载"这一动作,不授权列目录与其它条目
* 文件在令牌有效期内被删除 → 404 `FILE_NOT_FOUND`

#### 3.9.2 响应头与断点续传

| 头 | 值 |
| --- | --- |
| `Content-Type` | 按扩展名映射;未知类型 `application/octet-stream` |
| `Content-Length` | 完整文件字节数(64 位) |
| `Accept-Ranges` | `bytes` |
| `Content-Disposition` | `attachment; filename="ASCII 回退名"; filename*=UTF-8''<百分号编码>`(中文名走 RFC 5987) |
| `ETag` | `"<node_id>-<size>-<mtime>"`(弱校验,用于 `If-Range`) |
| `Last-Modified` | 文件修改时间 |

* Range 语义完整实现:`bytes=a-b` → 206 + `Content-Range`;`bytes=-n`(后缀)→ 206;超出范围 → 416 + `Content-Range: bytes */<size>`;多段 Range 按单段处理(只返回首个区间,不做 multipart/byteranges)
* `If-Range` 命中 ETag/时间 → 206,未命中 → 200 完整内容
* 大文件:偏移与长度全部使用 64 位整数,>4GB 文件正常下载与续传

#### 3.9.3 传输与限制

* 文件发送走 drogon 文件响应(`HttpResponse::newFileResponse`):由 trantor 在**事件循环**上分块读盘并写出,**不占用工作池线程**
* 注意:Windows 下没有 `sendfile` 系统调用(trantor 的 `FileBufferNodeWin` 走 `ReadFile` 分块读取,`use_sendfile` 配置仅 Linux 生效),因此大文件高并发下载会消耗事件循环时间
* **必须有全局并发下载闸门**:§3.9.1 的"同一令牌 ≤ 5 并发"只管得住单个令牌,拦不住"1000 个不同令牌同时下载"。需在响应路径上做全局计数(进入 +1、响应结束 -1),上限取 §2.8 的基线值,实现后按实测标定;超出排队或返回 503
* 下载**防交错**:下载过程中文件被改名/移动 → 令牌失效,返回 410 `TOKEN_EXPIRED`(不返回半旧半新的内容)
* 下载条目不产生 `transfer_tasks` 记录(浏览器/下载器自带进度,服务端不重复展示);但**记入审计日志**(`file_logs`,动作 `download`,含条目路径、字节数、IP、User-Agent)
* 限速:本期不实现(见 §8.3);如需可后续在响应发送路径上按用户维度做令牌桶限速

### 3.10 zip 打包下载

#### 3.10.1 触发与范围

* 触发方式:多选条目 → "打包下载";或在目录上直接"下载此目录"
* 打包范围:所选条目及其全部子孙(目录递归);单次上限 5000 条目 / 20GB,超出 400 `PACK_TOO_LARGE`(前端在发起前先展示"将打包 N 个文件,共 X GB",由统计接口预估)
* 空目录:打包结果保留该目录项(不丢层级)

#### 3.10.2 压缩包命名与存放

* 存放:`<exe>\modules\filehub\space_cache\<space>\zip\`
* 命名:`<uid>_<yyyyMMddHHmmss>_<6 位随机串>.zip`(随机串保证同一用户并发打包不撞名)
* 压缩包内路径结构:
  * 多选文件(同目录)→ 直接以文件名平铺在 zip 根
  * 多选含目录 → 以各条目的名称为一级目录保留层级
  * 目录打包 → 该目录名作为 zip 根的顶级目录名
  * 全部路径使用 `/` 分隔符(zip 规范),条目名保持 UTF-8
* 编码:zip 条目名以 UTF-8 存储并置通用标志位 bit 11(EFS),保证 Windows 资源管理器与 Linux `unzip` 均不乱码;不写非 UTF-8 的本地编码回退名

#### 3.10.3 打包执行

* 打包在**工作池**异步执行,任务类型 `type=3`(打包下载)记入 `transfer_tasks`
* 进度:按"已处理条目数 / 总条目数"上报(`done_items`/`total_items`),同时上报已处理字节数与压缩包当前大小
* 压缩算法:zlib deflate 级别 1(优先吞吐);对已压缩格式(`.zip .gz .7z .rar .jpg .jpeg .png .gif .webp .mp4 .mov .mp3 .flac .docx .xlsx .pptx`)使用 **store 不压缩**,只做封装,显著提速
* 并发:全局同时进行 ≤ 2 个打包任务,超出排队。**限的是任务数而非线程数** —— 工作池自动扩容(`ZmThreadPool`,初始 8、全忙时自动新建 worker、上限 128),不存在"钉死占用 N 个线程"的做法;限并发的真正理由是打包吃 CPU(deflate)与磁盘 IO
* 取消:任务标记取消 → 打包线程在下一个条目边界退出 → 删除半成品压缩包 → 置已取消
* 失败:读取某条目失败(被占用/已删除)→ 跳过该条目并记入 `detail`,打包继续;若压缩包无法写入 → 任务失败并清理

#### 3.10.4 下载与清理

* 打包完成 → 任务记录压缩包路径与大小 → 前端在任务面板给出"下载"按钮 → 换取下载令牌(§3.9.1)→ 直链下载
* 清理规则(**以空闲超时为准,避免误删多线程下载器的分片请求**):

| 场景 | 行为 |
| --- | --- |
| 用户取消打包 | 立即删除半成品压缩包 |
| 打包失败 | 立即删除半成品压缩包 |
| 下载完成 | 不立即删除:压缩包最后一次被访问后**空闲 3 小时**由清理器删除(多线程下载器会并发发起多个 Range 请求,按"请求结束即删"会误删)。每次下载都会把"最后访问时间"推到现在,相当于续期 |
| 用户删除记录 | 任务面板提供"删除"按钮,**只删任务记录、不动压缩包**:产物是缓存,由上面的空闲回收与下面的兜底统一处理(与"清除历史"同一口径) |
| 服务重启/中断 | 启动时把所有"进行中"的打包任务置为"已中断",其半成品压缩包由周期清理删除 |
| 兜底 | 每日周期清理扫描 `space_cache`,删除超过 24 小时的任何文件(含上传遗留分片) |

* 缓存区容量保护:`space_cache` 总占用超过阈值(默认 500GB)时,周期清理按"最久未访问优先"删除压缩包,直到回落到阈值的 80%
* 产物保留期(3 小时空闲 / 24 小时兜底)短于任务记录保留期(终态 7 天):记录仍在历史里、但产物可能已被回收,此时点"下载"提示已被清理、需重新打包 —— 这是"产物即缓存"定位下的预期行为

### 3.11 传输任务队列

* 上传、打包下载、跨空间批量复制、回收站清空统一记入 `transfer_tasks`(见 §5.6);**单文件直链下载不建任务**(理由见 §3.9.3)
* 任务状态机:

```
排队中(1) ──→ 进行中(2) ──→ 已完成(3)
                  │              │
                  ├──→ 失败(4)   ├──→ 已取消(5)
                  └──→ 已中断(6) ←┘(服务重启时对进行中任务置位)
```

* 任务字段对外暴露:`task_no`(随机串,不暴露自增 id)、类型、名称、目标路径、大小、完成度、状态、错误信息、创建/开始/结束时间
* 接口能力:列表(按类型/状态/时间筛选,分页默认 20)、详情(单任务轮询)、取消、重试、清除历史
* 前端任务面板:工作区右下角悬浮入口,显示"进行中任务数"徽标;展开后按"进行中 / 已完成"两个页签展示,进行中项显示进度条与取消按钮,失败项显示原因与重试按钮
* 进行中页签的**上传由客户端上传队列呈现**(带字节级进度与取消):服务端的上传任务行不在该页签重复列出(否则一次上传会出现"排队中/进行中"与"上传中"两条),只作为历史留档(可在历史页签重试)
* 轮询策略:面板打开或存在进行中任务时,每 1.5s 轮询一次进行中任务列表;无进行中任务时停止轮询(避免常驻请求)。页面切走后停止轮询,回到前台立即刷新一次
* 中断标记:服务启动时执行一次"僵尸任务清理",把状态为进行中(2)的任务置为已中断(6),错误信息"服务重启中断";对应的上传分片目录保留(会话未过期时可续传),打包半成品由周期清理删除
* 保留期:已完成/已取消/已中断/失败任务保留 **7 天**,周期清理删除;进行中任务不清理
* 单用户进行中任务上限:上传 3(§3.8.6)、打包 2;超出返回 429

### 3.12 分享

#### 3.12.1 分享对象与链接

* 对象:单个文件或目录,或多选的一组条目(一条分享绑定选中的全部条目,须在同一空间;分享页顶层将其平铺为"虚拟根",目录条目可继续下钻浏览)
  * **条数口径**:按"选中的条目"计,**文件夹只算 1 条**,不计其内部文件数量;选中多少就绑定多少,**分享无专属条数上限**(与其他批量操作共用"单次 2000 条"的安全阈值)
* 链接:`https://<站点>/s/{token}`(页面端口 80/443,便于复制粘贴与二维码扫描)
* `token`:32 字符高熵随机串(不承载任何 id 信息,不可枚举、不可反推目标)
* 二维码:前端本地生成(不上传链接到第三方二维码服务),扫码直达分享页

#### 3.12.2 分享属性

| 属性 | 规则 |
| --- | --- |
| 提取码 | 可选;开启时为 4 位随机字符(去掉易混淆的 `0O1lI`);服务端只存哈希,创建时一次性下发明文供前端展示;校验时区分大小写 |
| 有效期 | 永久 / 1 天 / 7 天 / 30 天 / 自定义日期;到期自动失效(`status=3`) |
| 下载次数上限 | 0 = 不限;达到上限后自动失效 |
| 仅登录可见 | 开关;`login_only=1` 时未登录访问 → 302 到 `/login?redirect=/s/{token}`,登录后回跳;**个人空间分享创建时可选,默认关闭(即免登录)**;公共空间分享不提供该开关(公共空间本就是全员可见资源) |
| 浏览权限 | 本期仅"可浏览 + 可下载";"仅预览""可上传(收件箱)"不做(见 §8.3) |
| 分享范围 | 目录分享时,子目录与文件按当前实际内容实时反映(非创建时快照) |

#### 3.12.3 访问规则

* **默认免登录**:公共空间与个人空间的分享,**任何人持有链接即可打开**,不校验登录状态
* **例外**:创建者开启"仅登录可见"(`login_only=1`)的分享,未登录访问 → 302 到 `/login?redirect=/s/{token}`,登录后回跳;登录用户的身份**不用于鉴权**(任何登录用户凭链接均可访问,不做创建者关系校验)
* 分享页不进入门户壳,为独立全屏页面(顶部品牌 + 分享信息卡 + 条目列表 + 下载按钮)
* 需提取码的分享:先展示提取码输入框;校验通过后服务端签发**分享访问凭证**(短时 2 小时,存 Cookie 或前端内存 + 请求头),后续列表/下载请求携带凭证,避免每次明文传提取码
* 提取码校验失败 5 次 → **该 `(IP, token)` 组合**冷却 10 分钟(计数落在 `write_limits` 表,见 §5.10),返回 429
  * 按 `(IP, token)` 而非只按 token:**否则任何人连打 5 次错码就能锁死别人的分享**(不需要知道提取码,只需发起请求)
* 分享目标被**移动/重命名** → **不影响分享**:分享绑定的是 `node_id` 而非路径,条目路径变化后分享照常可用
* 分享目标被**删除(进回收站)** → 分享行状态不变;因目标不可见(§2.4 可见树约定),访问时返回"分享内容不可用";**目标从回收站恢复后,分享自动恢复可用**(仍在有效期内的话)。这样误删文件不会连带毁掉已发出去的分享
  * **多选分享按条跳过**:部分目标不可见时,仅该条在分享页不出现(信息卡提示"另有 N 项暂不可用"),其余条目照常浏览与下载;**全部目标都不可见**才判定整条分享不可用
* 分享目标被**彻底删除**(回收站中清理或保留期到期) → 分享置为失效(`status=3`),`shares` 行保留至清理;访问页展示"分享已失效"
* 创建者取消分享 → `status=2`,立即不可访问

#### 3.12.4 我的分享

* 页面位置:文件中心内的"我的分享"标签页(非独立门户模块)
* 列表字段:分享名称(多选分享显示「主条目名 等 N 项」)、类型(多选分享显示「N 项」)、链接、提取码(创建时明文仅在创建后 1 次返回,后续列表只显示"已设置/未设置",支持"重置提取码")、有效期、浏览次数、下载次数、状态、创建时间
* 操作:复制链接、复制提取码、展示二维码、修改有效期与次数上限、取消分享
* 上限:单用户有效分享数 ≤ 200(一条多选分享算 1 条),超出 429 `TOO_MANY_SHARES`
* 分享只对自己可见:无法查看他人分享的列表(管理端可查,见 §3.13)

#### 3.12.5 分享访问日志

* 记录到 `share_logs`(见 §5.8):访问分享页、提取码校验(成功/失败)、列目录、下载单文件、打包下载
* 每条含:分享 id、token、动作、结果、登录用户 uid(免登录访问为 0)、IP、User-Agent、目标条目、时间
* 用途:创建者在"我的分享"中查看"最近访问记录"(脱敏展示:IP 段与 UA 摘要);管理端可查全量
* 保留 90 天,周期清理

#### 3.12.6 分享下载

* 分享页内的下载同样走短时令牌(§3.9.1),令牌绑定 `(share_token, node_id)`,不要求会话
* 目录分享的打包下载复用 §3.10 的打包能力;压缩包存放在**分享目标所在空间**的缓存区(即 `shares.space`,不是访问者所在空间)
* 多选分享:单项(单文件)仍换令牌直链;多条目与目录条目走打包。越权校验为"条目位于**任一**分享根的子树上",打包幂等键为 `token + ids`
* 分享下载计入 `shares.download_count`,用**单条原子自增**(`SET download_count = download_count + 1`),不做先读后写、也不为此开显式事务 —— 这是免登录接口,可能高并发命中同一行
* 次数上限的判定与自增之间存在竞态,允许**略微超发**(超过上限后的少数几次下载仍会成功);下载次数上限是使用配额而非安全边界,不为它引入行锁

### 3.13 文件中心管理

* 入口:系统管理 → "文件中心管理"子标签(权限点 `filehubAdmin`,与"用户管理"同级)
* 页面分为四个区:

**① 概览**

| 指标 | 说明 |
| --- | --- |
| 公共空间用量 | 条目数(目录/文件)、总字节数、其中回收站占用 |
| 个人空间用量 | 用户数、总字节数、Top 10 用户占用 |
| 回收站 | 各空间回收站条目数、占用字节数、将在 7 天内到期的条目数 |
| 缓存区占用 | `space_cache` 总大小、压缩包数量、分片目录数量 |
| 分享 | 有效分享数、今日访问/下载次数 |
| 任务 | 进行中任务数、今日完成/失败数 |
| 库文件大小 | `filehub.db` 物理大小 |

**② 一致性同步**

* 手动触发**全空间一致性同步**(公共 + 全部个人空间,以磁盘为准):

| 漂移情形 | 修复动作 |
| --- | --- |
| 磁盘存在、库无记录(文件) | 补建 `nodes` 行:`owner_uid=0`、`create_time=update_time=文件修改时间`、`size` 取文件大小、`hash` 留空 |
| 磁盘存在、库无记录(目录) | 先补建目录行,再递归处理其内部条目(自顶向下) |
| 库有记录、磁盘缺失 | 删除该行;**目录连同子树级联删除**(先递归删除子树行,再删自身) |
| 名称大小写不一致(库 `Report.txt` / 磁盘 `report.txt`) | 以磁盘为准更新 `nodes.name` |
| 库有记录、磁盘存在但类型不符(库为文件、磁盘为目录) | 以磁盘为准:删除原行,按磁盘类型重建 |

* 过程约束:
  * 同一时刻只允许一次同步任务运行(幂等);重复触发返回 409 `SYNC_RUNNING`
  * 同步期间的文件系统变动由目录级写锁(§2.7)保护;同步对单个目录加锁做"读盘 → 比对 → 落库",不长时间持锁
  * 同步不修改任何物理文件:只补库、只删行
  * **回收站配合**(详见 §3.7.2):补建方向的比对把 `deleted=1` 的行计入"已登记",避免为回收站里的物理文件补出重复行;删行方向跳过 `deleted=1` 的行;用量重算计入回收站占用
  * 同步产生的空间用量统计变化在结束时统一重算
* 结果报告:扫描目录数、扫描条目数、补建数、删除数、更新数、跳过数(权限不足/读取失败)、耗时;过程可查看进度(已扫描目录数 / 总数)
* 同步中可取消:取消后已完成部分保留(不回滚),状态置已取消

**③ 缓存与任务管理**

* 缓存区:列出压缩包与分片目录(所属用户、大小、创建时间、最后访问时间),支持单个删除与"全部清理"
* 回收站(管理员专属能力):
  * **全量列表**:跨用户、跨空间查看全部回收站条目(字段含删除者,可按空间/删除者/时间筛选)
  * **整体清空**:一次性物理删除全量回收站条目(需二次确认 + 展示将被永久删除的条目数与总字节数)
  * **立即执行保留期清理**:等价于把 §3.14 第 8 项提前跑一次
  * 管理端操作无论条目归属,均可恢复或彻底删除(不受 `del_owner_uid` 限制)
* 任务:全量任务列表(可按用户、类型、状态筛选),支持强制取消(含中断卡死任务)

**④ 审计日志**

* 查询 `file_logs`(见 §5.9):按用户、动作、空间、时间范围、关键词(条目名)筛选,分页展示
* 分享访问日志查询(§3.12.5 全量视图)

### 3.14 后台周期维护

* 复用用户系统的周期清理模式(`ZmDbModule::StartPeriodicCleanup` 同型):每日 03:00 执行,单表批次、异常隔离(单项失败只记日志,不中断整轮)
* 清理项:

| # | 项目 | 规则 |
| --- | --- | --- |
| 1 | 一致性校验 | **默认开启**:每日 03:00 全量扫描一次,等价于 §3.13 的同步(与其他清理任务同一时段);可配置关闭 |
| 2 | 分享日志清理 | `share_logs` 超过 90 天删除 |
| 3 | 业务审计日志清理 | `file_logs` 超过 90 天删除 |
| 4 | 传输任务清理 | 已完成/失败/已取消/已中断任务超过 7 天删除 |
| 5 | 上传会话清理 | `upload_sessions` 超过 24 小时未完成 → 状态置已过期,删除其分片目录与 `upload_chunks` 行 |
| 6 | 打包缓存清理 | 压缩包最后一次访问后**空闲 3 小时**删(每 10 分钟巡检);超 24 小时兜底删;总占用超阈值(**500GB**)时按最久未访问优先删至 80% |
| 7 | 失效分享清理 | `expire_time` 已过或 `download_count` 达上限的有效分享 → 置失效;失效超过 30 天的分享行删除(其 `share_logs` 一并删除) |
| 8 | 回收站保留期清理 | `deleted=1` 且 `delete_time` 超过 **30 天**的条目 → 物理删除(子树一起删,事务 + 物理递归);物理删除失败(文件被占用)保留该行,下轮重试 |
| 9 | 空目录行清理 | 不执行(空目录是合法条目,由用户自行删除) |

### 3.15 审计日志

* 落点:文件中心库内 `file_logs` 表(与用户系统的 `operation_logs` 分离,避免文件业务的高频写入污染用户库;管理端的文件中心管理操作同样落 `file_logs`,动作加 `admin_` 前缀)
* 记录动作清单:

| 动作 | 触发 | 关键 detail |
| --- | --- | --- |
| `upload` | 单请求/分片上传完成 | 目标路径、字节数、耗时、是否秒传 |
| `download` | 直链下载响应完成 | 条目路径、实际发送字节数、是否 Range |
| `pack` | 打包任务完成 | 压缩包名、条目数、压缩包大小、耗时 |
| `mkdir` / `rename` / `move` / `copy` / `delete` | 对应操作 | 源路径 → 目标路径 / 被删条目清单摘要 |
| `restore` / `purge` / `trash_clear` | 回收站恢复 / 彻底删除 / 清空 | 原路径与恢复后路径 / 被物理删除的条目数与字节数 |
| `share_create` / `share_cancel` | 分享创建/取消 | token、目标路径、有效期、是否设提取码 |
| `share_access` | 分享页访问与下载 | 见 `share_logs`(审计日志区做汇总查询) |
| `admin_sync` / `admin_cache_clean` | 管理操作 | 同步统计 / 清理项与字节数 |

* 字段:`uid` + `account` 快照(账号改名或删除后仍可追溯)、`action`、`space`、`node_id`、`node_name`、`detail`(JSON)、`ip`、`result`(1=成功 2=失败)、`create_time`
* **写入时机(审计不可丢)**:写操作(新建/改名/移动/复制/删除/恢复/彻底删除/上传入位/分享创建取消/管理操作)的审计**与业务改动在同一个数据库事务内** —— 有操作必有记录,要么都成要么都不成。下载、分享访问这类**只读行为**没有业务事务可加入,走独立异步写,失败只记警告
* 由上一项推出的必然结果:**整批失败并回滚的操作不会留下审计行**(日志随事务一起回滚),失败原因由接口响应告知;而"部分成功"的批量操作会提交,成功与失败逐条都有记录。详见设计文档 §3.12
* 批量操作的记录粒度:移动/复制记录**每一条**(便于追溯单个条目的去向);删除记录**一批一条**,detail 内含条目清单摘要(条目数 > 200 时只记前 200 条与总数)
* 失败也记录:权限不足、名称冲突、配额超限等失败路径记 `result=2` 与错误码(便于排查"为什么删不掉")
* 保留 90 天(§3.14)

## 4. 通用规则

### 4.1 名称与参数校验

| 项 | 规则 |
| --- | --- |
| 名称 | 非空、≤255 字节、不含 `<>:"/\|?*`、不含 ASCII 控制字符(0x00-0x1F)、不等于 `.` 与 `..`;允许 `.` 开头(隐藏);不以空格或 `.` 结尾(Windows 限制);名称中的首尾空格自动去掉 |
| 保留名 | 拒绝 Windows 保留设备名(不分大小写):`CON` `PRN` `AUX` `NUL` `COM1`-`COM9` `LPT1`-`LPT9`,以及带扩展名的形式(如 `CON.txt`) |
| Unicode | 不做规范化(NFC/NFD 不统一),按客户端原样存储;同名判定以文件系统为准(Windows 不区分大小写) |
| 路径深度 | ≤ 32 层;物理路径拼接后 ≤ 240 字符 |
| 分页参数 | `page ≥ 1`,`1 ≤ size ≤ 1000`(默认 200);任务列表默认 20 |
| 关键词 | 1~64 字符 |
| 批量参数 | `ids` 数组长度 ≤ 2000,元素去重后处理 |
| 空间参数 | `space` 必须为 0 或登录用户自己的 uid(否则 403) |
| 目录 id | 目标目录 id 必须存在于该空间且类型为目录(否则 404 `DIR_NOT_FOUND`) |
| 相对路径(`dirs/ensure` 的 `path` / `ensure_batch` 的 `paths[]`) | 这是**唯一**接受客户端路径字符串的入参,必须严格校验:以 `/` 分隔、逐段套用上面的"名称"规则、拒绝空段与 `.`/`..`、段数 + 当前深度 ≤ 32、单条总长 ≤ 1024 字符;**校验通过后仍是逐级查/建**,不把该字符串拼进任何物理路径。`ensure_batch` 单次 ≤ 2000 条,按段数从少到多排序后建(保证父先于子) |

### 4.3 排序、分页与筛选

* 列表统一返回 `{ total, page, size, list: [...] }`(与用户管理列表同型)
* 排序参数 `sort`(name/size/mtime/type)+ `order`(asc/desc);缺省 `sort=name&order=asc`
* 目录恒排在文件之前(服务端排序已保证,前端不重排)

### 4.4 同名冲突处理策略

* 统一入口参数 `conflict`,取值与语义见 §3.6;上传、复制、移动三个写操作共用同一语义
* 新建文件夹与重命名**不支持** `conflict`(恒为 `ask`):用户明确命名时不应被静默改名或覆盖
* 移动的 `conflict` 缺省为 `ask`(整批拒绝,不做部分成功);用户在前端选择后可按 `skip`/`rename`/`overwrite` 重试
* 冲突判定的比较键为 `(space, parent_id, name)`,**不区分大小写**;DB 唯一索引同步采用不区分大小写的排序规则,与文件系统行为一致

### 4.5 配额与限流

| 维度 | 规则 |
| --- | --- |
| 个人空间配额 | 默认**不限**;可对单用户设置配额(`spaces.quota`,0=不限);写入(上传/复制/跨空间移动入)前校验,超限 403 `QUOTA_EXCEEDED` |
| 空间用量维护 | `spaces.used_size` / `used_items` 在写操作事务内增量更新;一致性同步后统一重算 |
| 回收站占用 | 回收站内条目**计入** `used_size`(直到彻底删除);回收站接口单独返回这部分占用,前端分别展示"已用"与"其中回收站占用" |
| 并发上传 | 单用户 ≤ 3(§3.8.6) |
| 并发打包 | 单用户 ≤ 2,全局 ≤ 2(§3.10.3) |
| 分享创建 | 单用户有效分享 ≤ 200(§3.12.4) |
| 提取码校验 | 同 `(IP, token)` 连续错 5 次 → 该组合冷却 10 分钟(§3.12.3);计数落 `write_limits` |
| 接口限流 | **不设**(已确认):写操作不做频次限制。`write_limits` 表保留建表(留给后续可能的滥用场景),本期不写入、不校验 |
| 限速 | 本期不做(上传/下载/打包均不限速) |

## 5. 数据库需求

### 5.0 总述

* 独立库:`<exe 同目录>\db\filehub\filehub.db`,与 `user.db` 物理隔离
* 建库方式:首次启动全新建表 + 建索引(幂等 `CREATE TABLE IF NOT EXISTS`);后续结构变更由运维执行 SQL(与 `user.db` 现行做法一致)
* 时间戳统一为 **Unix 秒(INTEGER)**;`space` 为 BIGINT(0=公共,>0=uid)
* 目录与文件**同表**(`nodes`),以 `type` 区分:使 id 全局唯一,移动/复制/删除/分享/列表全部统一处理
* `parent_id = 0` 表示"位于空间根下"(空间根不是一条记录,而是 `spaces` 表里的一行元信息)

### 5.1 filehub.db 表清单

| 表 | 用途 |
| --- | --- |
| `spaces` | 空间元信息(公共空间一行 + 每位用户一行),含配额与用量 |
| `nodes` | 条目表(目录 + 文件),路径由 `parent_id` 链组装 |
| `upload_sessions` | 分片上传会话(断点续传与秒传的落点) |
| `upload_chunks` | 已上传分片登记 |
| `transfer_tasks` | 任务队列(上传/复制/打包/目录统计/一致性同步/回收站清理) |
| `shares` | 分享(多选分享的展示名取主条目) |
| `share_nodes` | 分享绑定的条目集合(多选分享;单条分享也写一行) |
| `share_logs` | 分享访问日志 |
| `file_logs` | 业务审计日志 |
| `write_limits` | 写操作限流计数(§4.5) |

### 5.2 `spaces`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK AUTOINCREMENT | |
| `space` | BIGINT NOT NULL UNIQUE | 0=公共空间;>0=uid |
| `quota` | BIGINT NOT NULL DEFAULT 0 | 配额字节;0=不限 |
| `used_size` | BIGINT NOT NULL DEFAULT 0 | 已用字节(增量维护) |
| `used_items` | BIGINT NOT NULL DEFAULT 0 | 条目数(增量维护) |
| `create_time` | INTEGER NOT NULL | |
| `update_time` | INTEGER NOT NULL | |

### 5.3 `nodes`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK AUTOINCREMENT | 全局条目 id(目录与文件共用) |
| `space` | BIGINT NOT NULL | 所属空间 |
| `parent_id` | BIGINT NOT NULL | 上级目录 id;0 = 空间根 |
| `type` | TINYINT NOT NULL | 1=目录 2=文件 |
| `name` | VARCHAR(255) NOT NULL | 显示名 |
| `size` | BIGINT NOT NULL DEFAULT 0 | 文件字节数;目录为 0 |
| `ext` | VARCHAR(32) NOT NULL DEFAULT '' | 扩展名(小写,无点);目录为空 |
| `hash` | VARCHAR(64) NOT NULL DEFAULT '' | 整文件 SHA-256(十六进制小写);目录与同步补建为空 |
| `owner_uid` | BIGINT NOT NULL DEFAULT 0 | 创建者 uid;0=一致性同步补建 |
| `items` | INTEGER NOT NULL DEFAULT 0 | 目录直接子项数(展示用);文件为 0 |
| `create_time` | INTEGER NOT NULL | |
| `update_time` | INTEGER NOT NULL | 子项增删改时父目录同步刷新 |
| `deleted` | TINYINT NOT NULL DEFAULT 0 | 软删标记:1=在回收站;**只标记被删的顶层条目**,子孙不改写(§3.7.1) |
| `delete_time` | INTEGER NOT NULL DEFAULT 0 | 删除时间(保留期起点);`deleted=0` 时为 0 |
| `origin_parent_id` | BIGINT NOT NULL DEFAULT 0 | 删除前所在目录 id(恢复时回到这里);`deleted=0` 时无意义 |
| `del_owner_uid` | BIGINT NOT NULL DEFAULT 0 | 执行删除者 uid(回收站列表展示"谁删的") |

索引与约束:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS idx_nodes_uniq
    ON nodes(space, parent_id, name COLLATE NOCASE)
    WHERE deleted = 0;                                 -- 同名判定不区分大小写,且回收站条目不占名
CREATE INDEX IF NOT EXISTS idx_nodes_dir
    ON nodes(space, parent_id, type, name)
    WHERE deleted = 0;                                 -- 列目录 + 排序(只走可见树)
CREATE INDEX IF NOT EXISTS idx_nodes_search
    ON nodes(space, name)
    WHERE deleted = 0;                                 -- 搜索名称匹配(只搜可见树)
CREATE INDEX IF NOT EXISTS idx_nodes_hash
    ON nodes(space, hash, size)
    WHERE deleted = 0;                                 -- 秒传查重(不命中回收站)
CREATE INDEX IF NOT EXISTS idx_nodes_trash
    ON nodes(space, deleted, delete_time);             -- 回收站列表 + 保留期清理
```

> 不使用 `UNIQUE(space,parent_id,name)` 表级约束:①BINARY 排序规则会把 `Report.txt` 与 `report.txt` 视为不同名,与 Windows 文件系统行为不一致,会导致"库中两行、磁盘一个文件"的漂移;②回收站条目不应占用同级名称,需要一个带 `WHERE deleted=0` 的**部分唯一索引**(SQLite 支持)。
> **查询约定(全模块统一)**:所有"可见条目"查询必须带 `deleted=0`;回收站查询带 `deleted=1`。子孙是否在回收站由**祖先链**决定,故删除/恢复/彻底删除/用量统计都按"以被删顶层条目为根的子树"处理。
> **注意**:`idx_nodes_dir` 等索引带 `WHERE deleted=0` 后,带了该条件的查询才能命中索引;实现时不得遗漏该条件,否则退化为全表扫描。

### 5.6 `transfer_tasks`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PK AUTOINCREMENT | |

## 6. 服务端接口设计(REST 端口 `/zimo/api`)

### 6.1 约定

* 路径前缀:`/zimo/api/filehub`;**所有接口除"分享公开面"(`/filehub/share/*`)与"下载令牌直链"(`/filehub/dl/*`)外均需会话**
* 权限点:`/filehub/admin/*` 要求 `filehubAdmin`;其余要求 `filehub`
* 命名遵循用户系统 §5.2:资源名词复数、动作资源化、请求体 snake_case、路径参数 `{id}`
* 成功:HTTP 200 + 裸业务 JSON;失败:`{code, message}`(§4.2)
* 路由注册:模块内 `RegisterRoutes()` 逐条注册;`ServicePortal::CreateModules()` 装配 `ZmFileHubModule`,并在 `RegisterRestfulRoutes()` 中调用其 `RegisterRoutes()`
* **门禁配合**(两处改动):

| 位置 | 改动 |
| --- | --- |
| `ZmAuthGateModule::RestfulGateAdvice` | 免鉴权接口白名单增加两条:`/zimo/api/filehub/share/`(分享公开面;`login_only` 的登录要求交由 handler 细判)、`/zimo/api/filehub/dl/`(下载令牌直链,令牌本身即凭证,不携带 Cookie 也能用) |
| `ZmAuthGateModule::IsWhitelistPagePath` | 页面白名单增加 `/s/`(分享页),使未登录用户能加载分享页壳 |
| `ZmAuthGateModule::ApiPermForPath` | 该函数已按"子功能独立授权"重构,内置子前缀映射(`/admin/users` → `userManage`,其余 `/admin` 兜底 `systemManager`),供后续管理子域按此模式扩展。**注意:截至本次核对它仍无调用点**,权限实际由各 handler 首行 `HasPermission` 完成 —— 本期沿用 handler 内校验,**不依赖**该函数;同时按既定模式在函数内补上文件中心两行映射,保持映射表完整:`/zimo/api/filehub/admin` → `filehubAdmin`(功能权限)、`/zimo/api/filehub` → `filehub`(门户模块) |

### 8.1.1 两条反面教材(本期设计的直接依据)

这两条来自对 Cloudreve v4 与 AList/OpenList 源码的核对,正好各自印证了本需求里的一处设计选择:

**① 分享 token 必须高熵随机,不能用可编码的自增 id**

Cloudreve 的分享 ID 是 **Hashids 编码的数据库自增 id**,而 `hash_id_salt` 默认为空串、`MinLength` 未设置 —— 结果是分享链接**短且可顺序枚举**,任何人可以从一个分享链接推算出相邻的分享。这是"用编码代替随机"的典型代价:`Hashids` 给人"看起来像随机串"的错觉,但它只是**可逆的双射**,不是熵。

本需求取 32 字符高熵随机 `token`(§3.12.1),且**不承载任何 id 信息**、不参与任何可逆变换。校验时按 token 精确查库,不做解码。

**② 用户可控的文件名/路径绝不能拼进物理路径**

AList 与 OpenList 在公开漏洞库中有**多起路径穿越(CWE-22)漏洞**,成因高度一致:**把请求里的文件名/路径段拼到已授权目录之后**,而 `..` 没有归一化并做包含性检查,用户因此能越出授权目录删改文件。已核实的两条:

* `CVE-2022-45969`(AList < v3.6.0,CVSS **9.8**,GHSA-pmg2-rph8-p8r6):目录穿越,已有公开利用
* `CVE-2026-25161`(Alist < v3.57.0,CVSS 8.8,GHSA-x4q4-7phh-42j9):`req.Names`、`renameObject.SrcName`、`renameObject.NewName` 经 `stdpath.Join()` 拼接,受认证用户可跨用户边界删/改名/复制同挂载内的文件

OpenList 分叉后还有若干同类公告(批量重命名的 `src_name` 穿越、离线下载工具中取 `Content-Disposition` 头作为临时文件名、**分享创建接口的路径前缀混淆导致任意文件读**),均属同一模式;具体编号以公开漏洞库为准。

本需求的 §2.4"路径一律由 DB id 沿 parent 链组装、不接受客户端原始路径"正是针对这一类问题的结构性防御:客户端只能给 **id**,物理路径完全由服务端从库里的 `name` 字段重新拼出,而 `name` 在写入时已按 §4.1 拒绝路径分隔符与控制字符。

唯一的例外是 `POST /filehub/dirs/ensure`(文件夹上传需要按相对路径建目录)与 `zip` 内的条目名,**这两处必须按 §4.1 新增的"相对路径"规则逐段校验**,且校验通过后仍然逐级查/建,不把字符串直接拼进物理路径。分享侧同理:分享只接受 `node_id`,并在访问时用递归 CTE 校验目标位于分享子树内(§6.9),不做任何路径前缀字符串比较。

### 8.2 回收站(已确认纳入本期)

**结论**:回收站**纳入本期实现**(软删除)。理由是公共空间任何登录用户都能删任何文件(§2.3),一次误操作即永久丢失公共资料;而回收站的实现成本很低——`nodes` 加 4 列 + 部分唯一索引即可,不改动其余业务逻辑。

**采用的方案**(细节见 §3.7):

| 决策点 | 取定做法 | 说明 |
| --- | --- | --- |
| 软删粒度 | **只标记被删的顶层条目**,子孙不改写 | 一次删除目录只写 1 行,不受子树规模影响;子孙由祖先链判定为不可见 |
| 名称占用 | 回收站条目不占用同级名称 | 唯一索引加 `WHERE deleted=0` 条件,删除后可立即新建同名条目 |
| 物理文件 | **原位不动** | 删除是纯 DB 操作,无 IO 开销;磁盘占用与配额在彻底删除时才释放 |
| 恢复 | 回原位置;原位置被占用或原父目录已删 → 回空间根并自动重命名 | 与 Nextcloud 一致 |
| 保留期 | **30 天**,到期由周期任务物理删除 | 不提供差异化配置(§1.3) |
| 权限 | 与删除权限对称:公共空间任意登录用户、个人空间仅本人 | 否则会出现"删了没人能恢复"的死区 |
| 回收站内操作 | 只读 + 恢复/彻底删除/清空 | 不支持重命名/移动/复制/上传 |

**与其它机制的交界**(实现时最易出错的三处):

1. **一致性同步**(§3.13):磁盘 → 库比对时 `deleted=1` 的行必须计入"已登记",否则会把回收站里的物理文件误判为漂移并**补建重复条目**;库 → 磁盘方向则跳过 `deleted=1` 的行
2. **配额统计**(§4.5):回收站占用计入 `used_size`,接口单列这部分,避免"删了却没释放空间"的困惑
3. **彻底删除的失败处理**:文件被其它进程占用时保留该行、保留在回收站,下轮周期清理重试(不能丢行,否则回收站与实际文件脱节)

### 8.3 其它后续增强(按建议优先级)

### 8.4 公共空间写权限(已确认保持现状)

**结论**:"公共空间任意登录用户可写"**为本期取定的策略**,不做收紧。

已知影响(记录在案,便于后续复盘):

* 任一普通用户可删除公共空间任意条目、可创建任意目录、可用垃圾文件占满磁盘
* 缓解措施:回收站(§3.7.2)使误删可恢复;审计日志(§3.15)记录完整条目清单与操作者,可事后追溯
* 后续若需收紧,两个备选方案(不需要改动现有表结构):

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| A | 新增 **type=1 功能权限点** `filehubWrite`(默认仅 developer/admin 拥有,可单人授权),公共空间的写操作要求该点 | 需新增权限点并调整角色种子;写权限与读权限解耦后,普通用户仍可浏览下载公共资源 |
| B | 公共空间允许"上传/新建",但"删除/重命名/移动"仅限本人创建的条目 | 实现简单,但公共空间仍可能被上传污染 |
