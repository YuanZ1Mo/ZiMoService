# 文件空间业务模块设计

> 状态:待审阅 · 版本:v1.1 · 日期:2026-09-16
> 修订:v1.1 2026-09-19 —— 回收站条目改为**物理搬出**。软删除把条目搬到 `space_trash\<space>\<node_id>\<原名>`,
>       恢复搬回(名字被占则自动改名),彻底删除从回收站区删;启动期补搬历史条目。
>       起因:物理路径由名字拼出而软删除不搬文件,同名新文件会覆盖回收站里那份,恢复即空壳
> 范围:双空间(公共/个人) + 回收站 + 上传/下载/打包 + 传输任务 + 分享 + 文件中心管理的服务端模块划分与接口设计

> 目标:确定业务层模块划分、职责边界、依赖关系、接口注册规范、数据结构与关键业务逻辑,作为本期实现与前端设计的基线

## 1. 设计目标与分层

### 1.1 目标

* 业务层按**单一职责**划分为独立模块,每模块在 `modules/` 目录下对应独立 `.h` / `.cpp` 文件(C++ 文件命名与现有模块一致:`module_file_*.h/.cpp`)
* 所有业务接口**注册到所属模块**,模块之间通过明确的服务方法交互,**不跨模块直接操作对方数据表**
* 数据访问收敛到 `ZmFileDbModule`,业务模块不直接拼写 SQL
* 鉴权、会话、权限为**全球横切**,复用用户系统既有的 `ZmAuthGateModule` / `ZmSessionModule` / `ZmPermissionModule`,文件中心**不新建鉴权链路**
* 文件系统操作收敛到 `ZmFileStoreModule`,业务模块不直接调用 `CreateDirectory` / `MoveFileEx` / `CopyFile`
* 耗时的文件系统与压缩操作一律走**工作池**,事件循环不阻塞

### 1.2 分层

| 层 | 构成 | 职责 |
| --- | --- | --- |
| 平台层 | `ZmHttpServer` 家族(前端面 / JRPC 面 / RESTful 面) | 端口监听、路由分发、协议校验、静态资源、文件传输、CORS、协程调度、工作池 |
| 门禁层 | `ZmAuthGateModule`(用户系统,横切) | 全局鉴权拦截、白名单、force_change 边界、接口级权限 |
| 业务层 | `modules/module_file_*.cpp` | 文件中心的条目逻辑、存储、上传、下载、打包、分享、任务、管理 |
| 数据层 | `ZmFileDbModule`(业务层内数据访问) | `filehub.db` 建表/种子/事务/DAO、周期清理 |
| 物理层 | 本地文件系统 | `<exe>\modules\filehub\` 下三个平级区:`space\<space>\...`(在用)、`space_cache\<space>\...`(缓存)、`space_trash\<space>\...`(回收站) |

装配入口仍为 `ServicePortal::CreateModules()`:在用户系统各模块之后创建文件中心模块集(文件中心依赖会话与权限模块),`RegisterRestfulRoutes()` 中调用 `ZmFileHubModule::RegisterRoutes()` 与 `ZmFileAdminModule::RegisterRoutes()`。

### 1.3 与用户系统的关系(边界约定)

| 维度 | 约定 |
| --- | --- |
| 数据库 | **独立库** `db\filehub\filehub.db`,与 `user.db` 物理隔离;文件中心**不读写** `user.db` 的任何表 |
| 用户信息 | 展示层需要账号/昵称时,经 `ZmUserModule` 的服务方法取(只读),不直连 user.db |
| 会话 | 复用 `ZmSessionModule::AuthAndTouch` 与 `ZmAuthGateModule::CheckCtxSync`,不重复实现 |
| 权限 | 复用 `ZmPermissionModule::HasPermission`;权限点 `filehub`(门户模块)/ `filehubAdmin`(功能权限)由文件中心负责登记到 `user.db` 的种子(新增行,见 §6.3) |
| 审计 | `operation_logs`(管理操作)与 `login_logs` 归用户系统的 `ZmAuditModule`;文件中心的高频业务日志落**自己的** `file_logs` + `share_logs`,由 `ZmFileAuditModule` 承载,两者互不写入 |
| 限流 | **本期不做写操作限流**(§10.5);`write_limits` 同时充当**通用计数表**,本期承载提取码失败冷却(§7.7)。不复用 `user.db` 的 `rate_limits`,避免跨库耦合 |

> * `ZmDirLock` 是纯工具类(无状态、不落库),不参与依赖图的服务调用,只被 `ZmFileNodeModule` 与 `ZmFileUploadModule` 使用

## 3. 各模块详细设计

### 3.1 数据访问模块 `ZmFileDbModule`(module_file_db.h/.cpp)

**职责范围**

* SQLite 持久化(`filehub.db`):连接模型与用户系统 `ZmDbModule` 同型(写连接单写队列串行 + 读连接池多读并发,WAL + `busy_timeout`),所有 SQL 经工作池执行,事件循环不阻塞
* **全新建表初始化**:启动时按全新表结构建库建表(9 张表 + 索引 + **部分唯一索引**),写入公共空间行(`spaces.space=0`),创建 `space\0` 物理目录
* 通用 DAO 助手:占位参数绑定(全部按文本绑定)、结果行→`ZMJSON` 转换
* 事务封装:`WithTx(callback)` —— 回调在专用写线程执行,回调内只能调用本模块的 `*Sync` 方法,**不得再 `co_await`**(与 `ZmDbModule::WithTx` 同一约束)
* `spaces` 表读写服务方法(空间列表、配额设置、用量增减)
* `write_limits` **通用计数表**的读写服务方法:`(scope, dim_key, window_start, count)` 的自增与查询。本期唯一用途是提取码失败冷却(scope=`share_pwd_fail`);写操作限流(scope=`write`)本期不启用(§10.5),表结构已可承载
* 周期清理任务:注册事件循环启动回调,挂每日 03:00 的清理任务(§3.1.3)

**3.1.1 建表清单**

`spaces` / `nodes` / `upload_sessions` / `upload_chunks` / `transfer_tasks` / `shares` / `share_nodes` / `share_logs` / `file_logs` / `write_limits`,DDL 见 §6.1。

**3.1.2 关键约束(实现时不可省略)**

| 约束 | 说明 |
| --- | --- |
| 部分唯一索引 | `nodes(space,parent_id,name COLLATE NOCASE) WHERE deleted=0` —— 同名判定不区分大小写,且回收站条目不占用同级名称 |
| 部分查询索引 | `idx_nodes_dir` / `idx_nodes_search` / `idx_nodes_hash` 均带 `WHERE deleted=0`;**查询必须带该条件才能命中索引**,漏写则退化为全表扫描 |
| 回收站索引 | `idx_nodes_trash ON nodes(space, deleted, delete_time)` 供回收站列表与保留期清理 |
| 时间戳 | 统一 Unix 秒 INTEGER;由 `ZmFileDbModule::Now()` 提供(与 `ZmDbModule::Now()` 同实现) |
| 表结构变更 | 首次建库后不做迁移;后续变更由运维手工执行 SQL(与 `user.db` 现行做法一致) |

**3.1.3 周期清理(每日 03:00,单表批次、异常隔离)**

| # | 项目 | 规则 |
| --- | --- | --- |
| 1 | 上传会话清理 | `upload_sessions` 超过 24 小时未完成 → 置已过期,删除其分片目录与 `upload_chunks` 行 |
| 2 | 任务清理 | 已完成/失败/已取消/已中断的 `transfer_tasks` 超过 7 天删除 |
| 3 | 回收站保留期清理 | `deleted=1` 且 `delete_time` 超过 30 天 → 删掉回收站区该条目的目录(子树一起删);删除失败保留该行,下轮重试 |
| 4 | 打包缓存清理 | 压缩包最后一次访问后空闲 **3 小时**删(每 10 分钟巡检);超 24 小时兜底删;总占用超阈值(**500GB**)时按最久未访问优先删至 80% |
| 5 | 失效分享清理 | 过期或达次数上限的有效分享置失效;失效超过 30 天的分享行删除(其 `share_logs` 一并删除) |
| 6 | 分享日志清理 | `share_logs` 超过 90 天删除 |
| 7 | 审计日志清理 | `file_logs` 超过 90 天删除 |
| 8 | `write_limits` 过期行清理 | 窗口已过期的计数行删除(本期该表只有提取码冷却在用,必须清理否则会无限增长) |
| 9 | 一致性校验 | **默认开启**;每日全量扫描一次,复用 §7.8 的同步算法(可配置关闭)。与其他清理任务同为 03:00,注意两项都会长时间占用磁盘,必要时错开时段 |

* 第 1/4 项涉及物理文件删除(分片目录、压缩包),由 `ZmFileStoreModule` 提供删除方法,`ZmFileDbModule` 回调注入以避免反向依赖(见 §4.1 的依赖倒置说明)
* **清理任务直接操作所有表**(含 `file_logs` / `share_logs`),不绕经归属模块 —— 与用户系统 `ZmDbModule::CleanupOnce()` 的现行做法一致:`ZmFileDbModule` 是 SQL 的**唯一出处**,归属模块负责的是"业务写入与查询",两者不冲突

### 3.2 物理存储模块 `ZmFileStoreModule`(module_file_store.h/.cpp)

**职责范围**

* **逻辑路径 → 物理路径映射**:由 `space` + 沿 `parent_id` 链的 `name` 逐级拼出;拼接结果统一加 `\\?\` 前缀绕过 Windows `MAX_PATH`
* 物理文件操作:创建目录、原子改名入位、复制文件、递归复制目录、递归删除目录树、枚举磁盘目录(一致性扫描用)
* 缓存区管理:`space_cache\<space>\zip\`(压缩包)与 `space_cache\<space>\chunk\<upload_id>\`(分片)目录的创建、统计、清理
* 回收站区入口:`space_trash\<space>\<node_id>\<原名>`(条目被删时的落脚处,恢复时搬回在用目录);**属用户数据,不随缓存清理删除**
* 路径长度与深度校验(拼接结果 ≤ 240 字符、深度 ≤ 32 层)

**关键方法(签名示意)**

```cpp
/// @brief 由条目 id 组装物理绝对路径(目录/文件通用)
/// @param nodeId 条目 id;0 表示空间根(返回 space 根目录路径)
drogon::Task<std::string> PhysicalPath(int64_t nodeId);

/// @brief 临时文件 + 原子改名入位(覆盖已存在文件)
ZmStoreResult AtomicPlace(const std::string& tmpPath, const std::string& finalPath);

/// @brief 递归复制目录树(工作池上下文内调用)
ZmStoreResult CopyTreeSync(const std::string& src, const std::string& dst);

/// @brief 自底向上递归删除目录树(只读属性先清除)
ZmStoreResult RemoveTreeSync(const std::string& path);

/// @brief 枚举磁盘目录(返回名称/类型/大小/修改时间)
ZmStoreResult ScanDirSync(const std::string& path, std::vector<ZmDiskEntry>& out);
```

**设计要点**

* **物理名与逻辑名严格一致**:条目名即磁盘名(不含路径分隔符、已在写入时校验),这是"文件系统是事实源、一致性校验以磁盘为准"成立的前提
* **原子入位**:上传/覆盖/复制统一走"写临时文件 → 校验 → `MoveFileEx` 改名替换",读方永远看不到半成品;`overwrite` 语义由此天然成立
* **不持有业务语义**:本模块不查库、不判权限、不做同名裁决,只接收已确定的物理路径;所有"该不该做"的判断都在上层
* **统一结果结构体**(不用 `bool` + 出参错误串):物理操作失败的原因必须能一路传到 HTTP 响应,`bool` + 出参只能带一句文本,无法让上层按错误码分支。约定:

```cpp
/// @brief 物理操作结果(成功/失败原因/可读消息)
struct ZmStoreResult
{
    bool        ok   = false;
    int         code = 0;       ///< 0=成功;非 0 = 业务错误码(ZmErrCode 枚举)
    std::string message;        ///< 可读消息(中文,可直接回给客户端)
};

/// @brief 物理层错误码(与 HTTP 层错误码的对应关系见下)
enum class ZmErrCode : int
{
    Ok               = 0,
    NotFound         = 1,       ///< 文件/目录不存在        → 404 NODE_NOT_FOUND
    Locked           = 2,       ///< 被其它进程占用          → 409 FILE_LOCKED
    AccessDenied     = 3,       ///< 权限不足/只读           → 409 FILE_LOCKED
    PathTooLong      = 4,       ///< 超 240 字符              → 400 PATH_TOO_LONG
    DiskFull         = 5,       ///< 磁盘空间不足            → 507 INSUFFICIENT_STORAGE
    IoError          = 6,       ///< 其它 IO 错误            → 500 INTERNAL
};
```

* **Win32 错误码在此层收敛**:`ERROR_SHARING_VIOLATION`/`ERROR_LOCK_VIOLATION` → `Locked`;`ERROR_ACCESS_DENIED` → `AccessDenied`;`ERROR_FILE_NOT_FOUND`/`ERROR_PATH_NOT_FOUND` → `NotFound`;`ERROR_DISK_FULL` → `DiskFull`。上层只认 `ZmErrCode`,不再出现 `GetLastError()` 的分支
* 批量操作对每个条目收集一个 `ZmStoreResult`(批量移动/复制/删除天然是"部分成功"),与响应体的 `{success:[], failed:[{id,name,code}]}` 直接对应

### 3.3 条目逻辑模块 `ZmFileNodeModule`(module_file_node.h/.cpp)

**职责范围**

* **可见树查询**:列目录(排序、分页、文件夹恒在前)、面包屑、单条目详情、递归搜索(当前目录及子目录)
* 结构变更:新建目录、重命名、移动、复制、软删除、恢复、彻底删除
* **可见树校验**:任何按 id 取条目都校验 `deleted=0` 且祖先链上无 `deleted=1`;命中即返回"不存在",不泄露回收站内容
* 配额记账:`spaces.used_size` / `used_items` 的增减(在写操作事务内)
* 目录 `items` 计数与父目录 `update_time` 随动

**关键方法(签名示意)**

```cpp
/// @brief 列目录(可见树;文件夹恒在前)
drogon::Task<ZMJSON> List(int64_t space, int64_t dirId, const ZmListQuery& q);

/// @brief 递归搜索当前目录及子目录(名称模糊匹配,上限 500 条)
drogon::Task<ZMJSON> Search(int64_t space, int64_t dirId, const std::string& keyword,
                            const ZmListQuery& q);

/// @brief 面包屑(空间根 → 当前目录的祖先链)
drogon::Task<ZMJSON> Breadcrumb(int64_t space, int64_t dirId);

/// @brief 批量移动(可跨空间);conflict 策略见 §7.2
drogon::Task<ZMJSON> Move(const std::vector<int64_t>& ids, int64_t targetSpace,
                          int64_t targetDirId, const std::string& conflict, int64_t opUid);

/// @brief 软删除(只标记顶层条目,子孙不改写;文件搬进回收站区)
drogon::Task<ZMJSON> SoftDelete(const std::vector<int64_t>& ids, int64_t opUid, int64_t now);

/// @brief 回收站列表 / 恢复 / 彻底删除
drogon::Task<ZMJSON> TrashList(int64_t space, const ZmListQuery& q);
drogon::Task<ZMJSON> Restore(const std::vector<int64_t>& ids, int64_t opUid);

/// @brief 把历史回收站条目的文件补搬进回收站区(启动期调用;幂等)
ZMJSON MigrateTrashLayout();
```

**设计要点**

* **路径不接受客户端输入**:所有入参是 `id`,物理路径一律由 `ZmFileStoreModule` 从库中 `name` 重新拼出 —— 这是对"用户可控文件名拼进路径"这一类漏洞的结构性防御(需求 §8.1.1)
* **唯一的例外**:`dirs/ensure` 接受相对路径字符串,必须在**进入本模块之前**逐段校验(§7.1.3)
* 子树操作统一用 `WITH RECURSIVE` 展开,不递归查库;移动/复制/彻底删除都走这一条路径
* `owner_uid` 语义恒为"创建者",移动不改写(需求 §3.5)

### 3.4 目录锁 `ZmDirLock`(dir_lock.h/.cpp)

**职责范围**

* 目录级写锁:键 = `(space, parent_id)`,同键串行、异键并发
* 多键有序加锁:一次涉及多个目录时(移动 = 源目录 + 目标目录;跨空间 = 两个空间的目录),**按桶号排序去重后加锁**(不是按 key 排,原因见下)
* 提供 RAII 句柄(`std::lock_guard` 同型),异常路径自动释放

**关键方法(签名示意)**

```cpp
/// @brief 目录级写锁;按桶散列,桶数固定(如 256)
class ZmDirLock
{
public:
    /// @brief 单目录写锁的 RAII 句柄
    class Guard
    {
    public:
        Guard(ZmDirLock& lock, int64_t space, int64_t dirId);
        ~Guard();
        Guard(const Guard&) = delete;
        Guard& operator=(const Guard&) = delete;
    };

    /// @brief 一次锁多目录(内部按**桶号**排序去重后加锁,见下方"加锁顺序")
    std::vector<Guard> LockAll(const std::vector<std::pair<int64_t, int64_t>>& keys);

private:
    /// @brief (space, dir_id) → 桶下标;**必须先定桶、再排序**
    static size_t BucketOf(int64_t space, int64_t dirId);

    std::array<std::mutex, 256> m_buckets;
};
```

**加锁顺序(实现时必须按此,否则会死锁)**

互斥的单位是**桶**而不是 key,所以排序必须按**桶号**做,不能按 key 做:

```
1) 把每个 (space,dir_id) 映射成桶号 b = BucketOf(space, dirId)
2) 对桶号**排序 + 去重**
3) 按桶号升序逐个加锁;析构时逆序释放
```

**为什么不能按 key 排序**:两个不同的目录可能哈希到同一个桶 —— 按 key 排序时它们不相邻,于是会对**同一把 `std::mutex` 加两次锁**。`std::mutex` 不可重入,直接死锁。按桶号排序去重后,同一把锁只会被加一次,且全局加锁顺序一致,不会出现环路等待。

**设计要点**

* 桶数固定(如 256);哈希冲突时两个无关目录会短暂互斥,只影响并发度、不影响正确性
* **锁只覆盖裁决窗口,不覆盖 IO**:在锁内完成"冲突检查 + DB 写入",物理操作(复制/删除大目录)在锁外或只在单目录粒度上短持有(见 §7.2)
* 进程内结构:本期为单进程部署;若将来多进程,需改用文件锁或数据库行锁(记入非目标)

### 3.5 任务队列模块 `ZmFileTaskModule`(module_file_task.h/.cpp)

**职责范围**

* 任务落库(`transfer_tasks`)与状态机流转,统一对外暴露 `task_no`(随机串,**不暴露自增 id**)
* 进度上报:`done_size` / `done_items` / `total_items`(由执行方在推进时调用)
* 取消与重试:取消标记 + 执行方在边界处观察;重试生成新任务(不复活旧行)
* 列表查询:用户侧(按类型/状态筛选、分页)、管理侧(全量、可按 uid)
* **启动期僵尸任务清理**:把所有 `status=2`(进行中)的任务置为 `status=6`(已中断),错误信息"服务重启中断"

**状态机**

```
排队中(1) ──→ 进行中(2) ──→ 已完成(3)
                  │              │
                  ├──→ 失败(4)   ├──→ 已取消(5)
                  └──→ 已中断(6) ←┘(服务启动时对进行中任务置位)
```

**设计要点**

* 任务类型:`1=上传 2=复制 3=打包下载 4=目录统计 5=一致性同步 6=回收站清理`
* 取消语义分两级:**排队中**直接置已取消;**进行中**置取消标记,由执行方在"下一个条目边界 / 下一个分片边界"观察到后自行收尾(清理半成品)再置位 —— 服务端不会强杀正在写盘的线程
* 进度上报**限流写库**:执行方按字节/条目累积,每 500ms 或每完成 5% 才写一次,避免高频 UPDATE 打满单写队列
* 前端轮询走 `GET /filehub/tasks/active` 单接口(见 §5.2),不逐任务查询

### 3.6 上传模块 `ZmFileUploadModule`(module_file_upload.h/.cpp)

**职责范围**

* 小文件单请求上传(≤ 8MB):流式落临时文件 → 原子入位
* 分片上传会话:初始化(含秒传判定与会话复用)、分片接收与登记、完成合并
* 秒传:按整文件 SHA-256 在同空间内查重,命中则直接 `CopyFile`(不用硬链接,理由见需求 §3.8.4)
* 冲突裁决的执行(在 `complete` 阶段、目录锁内)
* 配额校验与用量记账

**关键方法(签名示意)**

```cpp
/// @brief 初始化上传会话(含秒传判定与断点续传复用)
/// @return {upload_id, chunk_size, chunk_total, uploaded[], instant?, node_id?, task_no}
drogon::Task<ZMJSON> Init(const ZmUploadInit& in, int64_t uid);

/// @brief 接收一个分片(原始字节)
drogon::Task<ZMJSON> PutChunk(const std::string& uploadId, int32_t index,
                              const char* data, size_t len);

/// @brief 完成合并:校验片齐 → 合并 → 校验哈希 → 锁内冲突裁决 → 原子入位 → 落 nodes
drogon::Task<ZMJSON> Complete(const std::string& uploadId, int64_t uid);
```

**设计要点**

* **冲突裁决时机**:`init` 只**预检**并回传冲突信息(供前端提示),**不裁决**;最终裁决在 `complete` 阶段、目标目录写锁内执行 —— 上传期间目标目录可能被他人改动,提前裁决会作出过期判断(需求 §3.8.3)
* **会话复用**:`upload_sessions` 上有部分唯一索引 `(uid,space,parent_id,name) WHERE status=1`,同名同目录重复上传时复用会话,响应携带 `uploaded[]` 供前端补传缺片
* **分片落盘**:`space_cache\<space>\chunk\<upload_id>\<index>.part`;分片可乱序、可重复(覆盖),单片长度与声明不符直接拒绝
* **合并在工作池**:逐片读入写出,合并阶段按已合并字节数上报进度
* **任务状态**:`init` 建任务后立即置"进行中"(分片随即开始传输),`complete` 收尾置完成 —— 与单请求上传/秒传路径一致;漏置会让任务在整个上传期间停在"排队中"
* **哈希校验可选**:客户端提供 `hash` 才校验;不提供则跳过(服务端仍写 `nodes.hash` 为空,不参与后续秒传)

### 3.7 打包模块 `ZmFilePackModule`(module_file_pack.h/.cpp)

**职责范围**

* 展开待打包条目集合(含子树),预估条目数与总字节数
* 用 **minizip-ng** 在工作池构建 zip,边写边上报进度
* 压缩算法选择:deflate 级别 1;对已压缩格式走 **store**(不压缩只封装)
* UTF-8 条目名 + 通用标志位 bit 11(EFS),保证 Windows 资源管理器与 Linux `unzip` 均不乱码
* 取消:在条目边界观察取消标记并清理半成品
* 压缩包命名与清理:空闲超时删除、主动清理、启动期孤儿清理

**关键方法(签名示意)**

```cpp
/// @brief 创建打包任务(入队);返回 task_no
drogon::Task<ZMJSON> Create(int64_t space, const std::vector<int64_t>& nodeIds, int64_t uid);

/// @brief 打包执行体(工作池线程内)
void RunPack(const std::string& taskNo);

/// @brief 清理压缩包(用户主动 / 空闲超时 / 启动期孤儿)
drogon::Task<bool> CleanZip(const std::string& taskNo);
```

**设计要点**

* **先压缩好再直链下载**(而非流式打包):压缩包是稳定文件,可 `Content-Length`、可 Range 断点续传、可交给 IDM;流式打包(chunked、无长度)两者都做不到 —— 这是需求取定该方案的原因
* **并发闸门**:全局同时进行 ≤ 2 个打包任务,超出排队。注意工作池是**自动扩容**的(`ZmThreadPool`,初始线程数只是起点,全忙时自动新建 worker,上限 `ZM_POOL_MAX_THREADS = 128`),所以约束只能表达为"同时进行的任务数",**不存在"占用 N 个线程"这种钉死线程的做法**;限制并发数的真正理由是打包吃 CPU(deflate)与磁盘 IO,而不是抢线程
* **清理以空闲超时为准**:最后一次被访问后空闲 3 小时才删,而不是"响应结束即删" —— 多线程下载器会并发发起多个 Range 请求,按请求结束即删会误删(需求 §3.10.4)
* **上限前置**:创建任务前校验"条目数 ≤ 5000、总字节 ≤ 20GB",超出直接 400,不进入排队

### 3.8 下载令牌模块 `ZmFileTokenModule`(module_file_token.h/.cpp)

**职责范围**

* 短时下载令牌的签发与校验:随机 32 字符、有效期 10 分钟、绑定 `(uid, node_id)` 或 `(share_token, node_id)`
* 直链路径的响应构造:`Content-Type` / `Content-Length` / `Accept-Ranges` / `Content-Disposition`(RFC 5987 中文名)/ `ETag` / `Last-Modified`
* Range 解析与状态码:`bytes=a-b` → 206;`bytes=-n` → 206;超出 → 416;`If-Range` 未命中 → 200
* 令牌并发连接计数(同一令牌最多 5 个并发)

**关键方法(签名示意)**

```cpp
/// @brief 签发下载令牌(单文件)
drogon::Task<ZMJSON> Issue(int64_t uid, int64_t nodeId, int ttlSec = 600);

/// @brief 校验令牌并返回目标条目(校验失败返回空)
drogon::Task<ZMJSON> Resolve(const std::string& token);

/// @brief 构造带 Range 语义的文件响应
drogon::HttpResponsePtr BuildFileResponse(const ZMJSON& node,
                                          const drogon::HttpRequestPtr& req);
```

**设计要点**

* **令牌存储走抽象接口,本期只实现内存版**(已确认预留 Redis 分支):

```cpp
/// @brief 下载令牌的存储后端(本期只有内存实现;多进程部署时补 Redis 实现)
class ZmTokenStore
{
public:
    virtual ~ZmTokenStore() = default;
    virtual void Put(const std::string& token, const std::string& payload, int ttlSec) = 0;
    /// @return 令牌校验通过时的载荷;不存在/已过期返回空
    virtual std::string Get(const std::string& token) = 0;
    /// @brief 连接计数 +1;超过 maxConn 返回 false
    virtual bool  OpenConn(const std::string& token, int maxConn) = 0;
    /// @brief 连接计数 -1;**必须在响应结束时无条件调用**(成功/客户端断开/异常都要)
    virtual void  CloseConn(const std::string& token) = 0;
    virtual void  Erase(const std::string& token) = 0;
};
```

  * 本期:`ZmTokenStoreMemory`(进程内 LRU + TTL),装配时注入 `ZmFileTokenModule`
  * 预留:`ZmTokenStoreRedis`(键前缀 `zimo:filehub:token:*`,TTL 交给 Redis)—— 多进程部署时新增实现即可,**调用方代码不动**
  * 抽象**只看这一处**:令牌的签发/校验/响应构造逻辑不感知存储形态
  * **计数必须成对**:`OpenConn` / `CloseConn` 要在响应的开始与结束各调一次,且结束那次挂在**响应完成回调**上 —— 客户端中途断开、发送失败、协程异常都必须能走到 `CloseConn`。若只在发送成功的分支里减计数,一次断连就会把这个令牌的并发名额永久占掉,令牌在剩余 TTL 内再也下不动
* 令牌**不落库**:10 分钟的生命周期不值得为它建表 + 加清理任务;存储抽象只是为将来换后端留口子,不是现在就上 Redis
* 令牌**可重复使用**:支持下载器的多段并发 Range;靠"并发连接数 ≤ 5 + 10 分钟 TTL"限制滥用
* **防交错**:令牌绑定 `node_id`,而 `node_id` 在改名/移动后不变;若文件被替换(`overwrite` 产生新内容),`ETag` 含 size+mtime,`If-Range` 会自然失效,不会拼出半旧半新的内容
* 该模块只做"凭证 + 响应",不查权限(权限在签发时已校验),因此直链路径可挂到免会话白名单

### 3.9 分享模块 `ZmFileShareModule`(module_file_share.h/.cpp)

**职责范围**

* 分享创建/修改/取消:token 生成、提取码哈希、有效期与次数上限、`login_only`
* 提取码校验:哈希比对、连续失败计数与冷却
* 公开面访问:分享信息、目录浏览(子树校验)、下载令牌签发
* 分享访问日志(`share_logs`)写入与查询
* 失效判定:过期 / 达次数上限 / 取消 / 目标被彻底删除

**关键方法(签名示意)**

```cpp
/// @brief 创建分享;返回 {share_id, token, url, pwd?, expire_time}
drogon::Task<ZMJSON> Create(int64_t uid, const ZmShareCreate& in);

/// @brief 校验提取码 → 签发分享访问凭证(Cookie zm_share,2 小时)
drogon::Task<ZMJSON> Verify(const std::string& token, const std::string& pwd,
                            const std::string& ip);

/// @brief 列出分享目录(须先校验:分享有效 + 凭证有效 + dir_id 在分享子树内)
drogon::Task<ZMJSON> ListDir(const std::string& token, int64_t dirId,
                             const ZmListQuery& q);
```

**设计要点**

* **token 为 32 字符高熵随机串**,不承载任何 id、不参与可逆变换、校验时精确查库 —— 与"Hashids 编码自增 id"这类做法相反(需求 §8.1.1)
* **子树校验用递归 CTE,不做路径前缀字符串比较**:`dir_id` 必须能沿 `parent_id` 上溯到分享目标;这是对"分享创建接口路径前缀混淆"类漏洞的防御
* **多选分享(一条分享绑定选中的全部条目)**:绑定关系落 `share_nodes`(单条分享也写一行,读路径统一);`shares.node_id/node_type/name` 保留为主条目 + 展示名,兼容旧行与列表;旧行(改造前创建)无关联行时按 `shares.node_id` 单条兜底
  * 子树校验改为"**任一根**命中即通过";公开面 `dir_id=0` 对多根返回**虚拟根**(平铺各条目,面包屑只有分享名一级),进入某条目目录后沿用原 CTE 面包屑
  * **无分享专属条数上限**:按选中的条目计(文件夹只算 1 条,不计其内部文件),仅沿用批量操作共用的 `kBatchMaxIds=2000` 安全阈值;多选分享在"有效分享数 ≤ 200"里算 1 条
  * 部分条目不可见(回收站/已彻底删除)只跳过该条(信息卡提示"另有 N 项暂不可用"),全部不可见才判整条不可用
* 提取码**只存哈希**(复用 `ZM_FILE_HUB_HMAC_KEY`),创建时明文一次性下发
* **失败冷却必须按 `(IP, token)` 二维计数,不能只按 token 计**:

  | 方案 | 后果 |
  | --- | --- |
  | 只按 token 计(存在 `shares` 行上) | 任何人连打 5 次错码就能把这条分享**锁死 10 分钟** —— 攻击者不需要知道提取码,只需发起请求,构成 DoS |
  | **按 `(IP, token)` 计(取定)** | 每个 IP 各自计数、互不影响:单 IP 爆破被挡,别人正常访问不受影响 |

  * 落点:复用 `write_limits` 表(本期不做写限流,该表闲置),改造成通用计数表:
    `scope='share_pwd_fail'`、`dim_key='<ip>|<token>'`、`window_start`、`count`
  * 因此 `shares` 表**不再需要** `fail_count` / `lock_until` 两列(冷却状态不在分享行上)
* **分享与回收站的关系**:目标在回收站期间返回"内容暂不可用"(404 `SHARE_UNAVAILABLE`),**恢复后自动可用**;只有彻底删除才置失效 —— 避免误删文件连带毁掉已发出去的分享

### 3.10 文件中心模块 `ZmFileHubModule`(module_file_hub.h/.cpp)

**职责范围**

### 3.11 文件中心管理模块 `ZmFileAdminModule`(module_file_admin.h/.cpp)

**职责范围**

* 概览统计:公共/个人空间用量、回收站占用、缓存区占用、分享数与访问量、任务数、库文件大小
* **一致性同步**:全空间扫描(磁盘为准修复漂移)、进度上报、取消、结果报告(§7.8)
* 缓存管理:压缩包与分片目录列表、单个/全部清理
* 任务管理:全量任务列表、强制取消(含卡死任务)
* **回收站全量管理**(管理员专属):跨用户/跨空间的回收站列表、恢复任意条目、彻底删除任意条目、整体清空
* 日志查询:审计日志 `file_logs`、分享访问日志 `share_logs`
* 空间配额:列表与设置

**关键方法(签名示意)**

```cpp
/// @brief 触发一致性同步(dry_run 只报告不修复);返回 task_no
drogon::Task<ZMJSON> StartSync(bool dryRun, int64_t opUid);

/// @brief 同步执行体(工作池线程内;按空间逐目录推进,可取消)
void RunSync(const std::string& taskNo, bool dryRun);

/// @brief 概览统计
drogon::Task<ZMJSON> Stats();
```

**设计要点**

* **同步只补库、只删行,不动物理文件**(需求 §3.13)
* **与回收站的交界**:回收站条目的文件已搬出在用目录(在 `space_trash\<space>\<node_id>\`),在用区扫描不会遇到它们,`deleted=1` 的行因此不占"已登记"名额;库→磁盘方向仍跳过 `deleted=1` 的行
* **回收站区尚未纳入扫描(待补)**:`space_trash\` 目前不被遍历 —— 该区缺文件(条目恢复不出内容)、多出无对应行的目录时无人纠偏。补扫时磁盘→库方向要补成**回收站行**(`deleted=1`),不能补成在用文件
* **互斥**:同一时刻只允许一次同步(重复触发 409 `SYNC_RUNNING`);取消后已完成部分保留、不回滚
* **锁粒度**:对单个目录加锁做"读盘 → 比对 → 落库",不整段持锁,避免同步期间用户完全无法操作

### 3.12 审计模块 `ZmFileAuditModule`(module_file_audit.h/.cpp)

**职责范围**

* `file_logs`(业务审计)与 `share_logs`(分享访问日志)的**唯一写入方**,对其他模块暴露语义化的 `Record*` 方法
* 日志查询服务:按用户/动作/空间/时间/关键词筛选与分页(供 `ZmFileAdminModule` 的日志页面调用)
* 日志保留期清理的执行方(§3.1.3 第 6/7 项)

**关键方法(签名示意)**

审计写入分**两个入口**,按"这次操作有没有业务事务"选:

```cpp
// ── 入口一:参与调用方事务(写操作)**已确认采用** ──
// 在 WithTx 回调内调用,与业务改动同事务:有操作必有日志,要么都成要么都不成。
// 显式接收 ZmSqliteDb& 而不是自取连接 —— 表明"加入你的事务",避免误解为另开事务。

/// @brief 记录文件业务审计(与调用方同事务)
/// @param db     调用方事务的 ZmSqliteDb(来自 WithTx 回调形参)
/// @param action upload/mkdir/rename/move/copy/delete/restore/purge/trash_clear/share_create/share_cancel
/// @param result 1=成功 2=失败(失败也记,便于回答"为什么删不掉")
/// @return true 写入成功;false 时**调用方应让事务整体失败**
bool RecordFileOpSync(ZmSqliteDb& db, int64_t uid, const std::string& account,
                      const std::string& action, int64_t space, int64_t nodeId,
                      const std::string& nodeName, const std::string& detail,
                      const std::string& ip, int result);

/// @brief 批量审计(移动/复制逐条、删除一批一条;条目数 > 200 时 detail 只记前 200 条与总数)
bool RecordBatchSync(ZmSqliteDb& db, int64_t uid, const std::string& account,
                     const std::string& action, int64_t space, const ZMJSON& items,
                     const std::string& ip, int result);

// ── 入口二:独立异步写(只读行为的日志) ──
// 下载、分享访问这类行为没有业务事务可加入,走独立写入;失败只记警告,不反噬用户。

/// @brief 记录下载审计(action=download)
drogon::Task<bool> RecordDownload(int64_t uid, const std::string& account, int64_t space,
                                  int64_t nodeId, const std::string& nodeName,
                                  int64_t bytesSent, bool ranged, const std::string& ip, int result);

/// @brief 记录分享访问(action 1=访问 2=提取码校验 3=列目录 4=下载 5=打包下载)
drogon::Task<bool> RecordShareAccess(int64_t shareId, const std::string& token, int action,
                                     int result, int64_t uid /* 0=免登录 */,
                                     const std::string& ip, const std::string& ua,
                                     const std::string& detail);
```

**两个入口的划分(实现时按此归类,不要随手选)**

| 行为 | 有无业务事务 | 走哪个入口 |
| --- | --- | --- |
| 新建/重命名/移动/复制/删除/恢复/彻底删除/清空回收站 | 有(改 `nodes` + `spaces`) | **`*Sync`(同事务)** |
| 上传完成入位 | 有(落 `nodes` + 算配额) | **`*Sync`(同事务)** |
| 打包完成(记 `pack` 动作) | 有(改任务状态) | **`*Sync`(同事务)** |
| 创建/取消分享 | 有(改 `shares`) | **`*Sync`(同事务)** |
| **下载** | **无**(纯读,不改库) | 异步 `RecordDownload` |
| **分享访问/提取码校验/列目录** | **无**(纯读) | 异步 `RecordShareAccess` |
| 管理端同步/缓存清理 | 有(改 `nodes` / 删文件) | **`*Sync`(同事务)** |

**事务如何跨模块共享(实现要点)**

关键前提:**全模块共享同一个 `ZmFileDbModule` 实例**(装配时由 `ServicePortal` 创建唯一实例再分发给各模块)。因此:

* `WithTx` 的事务开在 `ZmSqliteDb` 的**写连接**上,该连接用 `std::recursive_mutex` 保护
* 业务模块在事务回调内调用 `m_audit->RecordFileOpSync(db, ...)`,方法内部执行 `db.ExecSync("INSERT INTO file_logs ...")` —— 同一线程重入同一个 `recursive_mutex`,**落在当前已开启的事务里**,不会有第二个连接、也不会另起事务
* 这也是 `RecordFileOpSync` **显式接收 `ZmSqliteDb&`** 的原因:拿到哪个连接写、进哪个事务,在调用点一眼可见,不靠"模块内部藏着哪个 db 指针"的隐式约定

**设计要点**

* **为什么单独成模块**(而不是塞进 `ZmFileAdminModule`):对齐用户系统的分层 —— `ZmAuditModule` 是**数据服务模块**,而 `ZmUserAdminModule` 是**编排模块**。日志是"被多处调用的写入服务",属于数据服务层;若归到管理编排模块,会出现"上传模块依赖管理模块"这种反向且语义错乱的依赖
* **写入方不知道表结构**:各业务模块只描述"谁对什么做了什么",字段拼装、JSON 序列化、失败码落库都在本模块内完成 —— 日志格式要改时只改一处
* **审计不可丢(本模块与用户系统的差异点)**:**已确认**写操作的审计与业务同事务。用户系统的审计是异步不阻塞业务的,文件中心在此有意收紧 —— 代价是每次写操作多一次写库、且日志写失败会让业务操作失败;换来的是"有操作必有记录",删改类操作事后可完整追溯(公共空间任何登录用户都能删,审计是唯一的事后手段,见需求 §8.4)
* **失败路径怎么记(同事务带来的一个必然后果)**

  日志进了业务事务,就意味着**事务回滚时日志也一起回滚** —— "整批失败的操作"无法在事务内留下记录。因此按失败发生的阶段分两种处理:

  | 失败阶段 | 典型场景 | 记法 |
  | --- | --- | --- |
  | **事务之前**(预检) | 权限不足、名称冲突、配额超限、目标不存在、参数非法 | 此时还没有事务 → **事务外异步补记**一条 `result=2`,与需求 §3.15"失败也记"一致 |
  | **事务之内**(批量部分失败) | 移动/复制/删除时个别条目物理操作失败 | 事务仍会**提交**(成功的部分要保留)→ 在事务内逐条记:成功记 `result=1`、失败记 `result=2` |
  | **事务之内**(整批失败) | 目录锁内冲突裁决后整批拒绝 | 事务**回滚** → 日志一并回滚,此项不产生审计行;失败原因由**接口响应**告知调用方 |

  一句话:**"这次操作到底有没有生效"决定了日志留不留得下** —— 生效了(哪怕只有部分条目)就有日志,整批没生效就没有。这与"审计反映实际发生的数据变更"的语义是一致的。
* **脱敏在写入侧**:查询"我的分享"日志时展示 IP 段与 UA 摘要,脱敏规则放在本模块的查询方法里,不依赖调用方自觉

### 4.2 关键交互流程

**分片上传(含秒传与断点续传)**

```
POST /filehub/upload/init {space, dir_id, name, size, hash?, conflict}
  → Hub: 会话 + CheckCtxSync + HasPermission("filehub")
  → Upload.Init:
      1) Node 校验目标目录可见且为目录
      2) 配额预检(个人空间)
      3) hash 命中同空间同 size 的 nodes(deleted=0)→ 秒传,**顺序不可颠倒**:
         锁内冲突裁决(定下最终文件名)→ 按裁决结果 Store.CopyFile 到位
           (先复制再裁决是错的:`rename` 策略下文件会落在错误的名字上)
         → 落 nodes 行 → 配额记账 → 返回 {instant:true, node_id}
      4) 否则:查同名进行中的 upload_sessions → 命中则复用(返回 uploaded[])
         未命中则创建会话 + 建分片目录
         → **创建上传任务(status=进行中)→ 返回 task_no**
         → 返回 {upload_id, chunk_size, chunk_total, task_no}
  ← 200 {...}

PUT /filehub/upload/chunk   (头 X-Upload-Id / X-Chunk-Index,体为原始字节)
  → Upload.PutChunk: 校验片号 → 写 <index>.part → 登记 upload_chunks → 更新 chunk_done
  ← 200 {received, chunk_done, chunk_total}

POST /filehub/upload/complete {upload_id}
  → Upload.Complete(工作池):
      1) 校验片齐 → 按序合并到临时文件(进度按已合并字节上报)
      2) 校验整文件哈希(客户端提供时)
      3) DirLock 锁目标目录 → 按 conflict 最终裁决 → Store.AtomicPlace 入位
      4) 落 nodes 行、写 hash、父目录时间戳/items 随动、配额记账
      5) 清理分片目录 → Task 把 **init 时创建的同一个任务**置完成
         (任务在 init 建、complete 收尾,两次响应的 task_no 相同;不是两个任务)
  ← 200 {node_id, task_no}
```

**单文件下载(令牌直链)**

```
POST /filehub/download/token {ids:[...]}
  → Hub: 会话 + 权限
  → ids 为单个文件 → Token.Issue → ← 200 {url:"/filehub/dl/<token>/<name>", expire_time}
  → ids 含目录或多个 → Pack.Create → ← 200 {task_no}

GET /filehub/dl/{token}/{filename}          ← 免会话(门禁白名单)
  → Token.Resolve(token): 查进程内令牌表 → 重新校验目标可见树
  → Token.BuildFileResponse(node, req):
      解析 Range / If-Range → 计算 206/200/416 → 组装头部
  → drogon 文件响应(事件循环上分块读盘,不占工作池)
  → 异步记审计(file_logs, action=download)
```

**打包下载**

```
POST /filehub/pack {space, ids:[...]}
  → Pack.Create: 展开子树预估(条目数 ≤ 5000、总字节 ≤ 20GB)
  → 全局打包闸门(≤ 2)未满 → 立即入队;已满 → 排队
  → WorkPool 执行 RunPack:
      创建 space_cache\<space>\zip\<uid>_<时间戳>_<随机>.zip
      逐条目写入(minizip-ng,已压缩格式走 store)→ 每条目检查取消标记
      每 500ms 上报 done_items/done_size
  → 完成 → Task 记录 zip 路径与大小 → 前端任务面板出现"下载"按钮
  → 换取下载令牌 → 直链下载(同单文件流程)
  → 清理:空闲 3 小时 / 超 24 小时兜底 / 容量阈值 / 启动期孤儿
```

**删除 → 回收站 → 恢复**

```
⚠ 回收站为什么必须独立存放文件:
   在用目录的物理路径由名字拼出,而"进/出回收站"若只改库不搬文件,同名新文件按同一
   规则算出的落点会正好压在回收站那份上(原子入位是覆盖式),恢复时又只改库名不搬磁盘,
   结果恢复出来是打不开的空壳,甚至静默串成新文件的内容。把条目搬进 space_trash 之后,
   "在用目录的名字空间"与磁盘严格一一对应,上述情形不再可能。

POST /filehub/nodes/delete {ids:[...]}
  → Node.SoftDelete:
      DirLock 锁各条目所在目录 → 逐条校验可见树
      物理侧先行(逐条):把条目从在用目录搬到 space_trash\<space>\<id>\<原名>
        搬不动(被占用/权限不足)→ 该条本轮不删,库行原样保留,计入 failed 下轮重试
        源文件本就不在 → 照常进回收站(该条目无内容),记警告,留给一致性同步兜底
      UPDATE nodes SET deleted=1, delete_time=now, origin_parent_id=父目录, del_owner_uid=op
      WHERE id IN (所选 id) AND deleted = 0    ← 只改顶层条目,子孙不动
                                               ← `deleted=0` 守卫不可省:重复删除同一个 id
                                                 会覆盖 origin_parent_id 与 del_owner_uid
                                                 （第二次删的人会"抢走"这条回收站记录）
      父目录 items/update_time 随动;**配额不变**(回收站仍占用)
      Audit.RecordBatchSync(db, action=delete, ...):完整相对路径、类型、大小、子树条目数
        ← 与上面同事务:数据改了日志就一定在,事务回滚则两者都不留
        ← 事务回滚时,按搬移记录把已搬走的文件搬回原位
  ← 200 {success:[], failed:[]}

POST /filehub/trash/restore {ids:[...]}
  → Node.Restore: 逐条
      原父目录可见 → 直接恢复(仍占用配额,无需校验)
      原父目录不可见 → 恢复到空间根,并在锁内自动重命名 name (1)、name (2)…
      物理侧先行:space_trash\<space>\<id>\<原名> → 目标路径
        名字被占用时 finalName 已是新名,搬过去即完成改名,不留"库名变了、磁盘还在旧名"
        回收站区没有内容 → 拒绝恢复(kTrashItemNotFound),不给"恢复成功"的空壳
      事务失败 → 把刚搬回的文件送回回收站;成功后删掉腾空的回收站条目目录
      UPDATE nodes SET deleted=0, delete_time=0, ...
      审计:restore(记录恢复后的实际路径)
  ← 200 {restored:[{id,name,path}], failed:[]}

POST /filehub/trash/purge {ids:[...]}   （彻底删除；保留期到期时由周期任务走同一逻辑）
  → Node.Purge **按顶层条目逐个处理**（顺序不可颠倒）:
      对每个 id:
        1) WITH RECURSIVE 展开该条目的子树 → 得配额扣减量与审计清单
        2) **先做物理删除** —— 删的是回收站区该条目的目录 Store.RemoveTreeSync(TrashEntryDir)
        3) 物理删成功 → 事务内删掉该条目的全部子树行 + 减配额
           物理删失败 → **整条保留**（行不删），计入 failed 清单，下轮重试
  ← 200 {success:[], failed:[{id,name,code}]}

  ⚠ 为什么不能"先删行再删物理文件"：
     那样一旦物理删除失败，行已经没了 → 磁盘上的文件成了孤儿
     → 下一次一致性同步（以磁盘为准）会把它**补建回来**，删了个寂寞。
     所以回滚单位必须是"顶层条目"：物理没删干净，这棵子树的行就一行都不动。

**历史条目的补搬(启动期一次)**

```
ServicePortal::CreateModules → Node.MigrateTrashLayout()
  ← 软删除曾经只改库不搬文件,老条目的文件还留在原位置;恢复与彻底删除都以回收站区
    为准,不补搬就恢复不出内容。条件(三条全中才搬):
      ① 回收站区没有该条目的文件(否则=已迁过) 
      ② 原位置还在
      ③ 原位置没有被在用条目占用 ← 防呆:同名新文件已落在原位置时,那份文件不属于它
    搬完条件即不再成立,重复调用无副作用
```

**跨空间移动**

```
POST /filehub/nodes/move {ids:[], target_space, target_dir_id, conflict}
  → Node.Move:
      1) 预检:目标存在且为目录;环路检测(沿目标 parent 链上溯,命中任一源 id → 400 MOVE_INTO_SELF)
         批量中含"祖先与子孙同时移动"→ 折叠为只移动祖先
      2) 权限:源空间可写 + 目标空间可写(个人空间两侧都要求 opUid == space)
      3) 配额:目标为个人空间时预检
      4) 加锁 (源space,源dir) 与 (目标space,目标dir)(内部按桶号排序去重,§3.4)
      5) 冲突裁决(默认 ask → 409;前端重试时带 skip/rename/overwrite)
      6) Store:同盘 MoveFileEx;跨盘走 CopyTree + 校验 + RemoveTree
         → 物理失败:中止该条(不进入步骤 7),计入 failed
      7) 事务内改库,**顶层与子孙的改法不同**:
           UPDATE nodes SET space=?, parent_id=? WHERE id IN (所选顶层条目)   ← 顶层:换空间 + 换父目录
           UPDATE nodes SET space=?           WHERE id IN (展开的子孙)        ← 子孙:只换空间
             (子孙的 parent_id 不变 —— 它们跟着父目录走)
           配额:源空间减、目标空间加
      8) Audit.RecordBatchSync(db, action=move, ...) ← 同事务,每条的源路径与目标路径

  ⚠ 步骤 7 失败的回滚:物理已经搬完了,库却没改 → 必须把物理搬回去
     (反向 MoveFileEx / CopyTree),搬不回去则记 ERROR 并标记该条目待一致性同步修复
     —— 这是"先物理后 DB"顺序的固有代价,回滚路径必须实现,不能只写 happy path
  ← 200 {moved:[], skipped:[]}
```

## 5. 接口注册与命名规范

### 5.1 注册位置

* 文件中心模块集在 `ServicePortal::CreateModules()` 中按依赖顺序创建:`ZmFileDbModule` → `ZmFileStoreModule` → `ZmDirLock` → `ZmFileNodeModule` / `ZmFileTaskModule` → `ZmFileUploadModule` / `ZmFilePackModule` / `ZmFileTokenModule` / `ZmFileShareModule` → `ZmFileHubModule` / `ZmFileAdminModule`
* `ServicePortal::RegisterRestfulRoutes()` 中在用户系统各模块之后调用 `m_fileHub->RegisterRoutes()` 与 `m_fileAdmin->RegisterRoutes()`
* 门禁 advice **仍必须先注册**(在 `SetupRestfulGate` 之后、业务模块之前),保证鉴权裁决先于业务 handler 注册的其他 advice
* **路由注册入口按有无路径参数二选一**(平台约定,选错会静默错绑或直接 `exit(1)`):

| 路由形态 | 注册入口 | 取参方式 |
| --- | --- | --- |
| 无路径参数(如 `/filehub/list`) | `RegisterCoro` | 参数一律从 query / body 解析 |
| 含路径参数(如 `/filehub/node/{1}`、`/filehub/dl/{1}/{2}`) | **`RegisterCoroWithPathParams`** | `{1}` → 第 1 个形参,由 drogon 原生绑定,**不走正则**、精确匹配 |

* 两个硬约束(`zm_net_http_server.h:398-420`):
  * **路径参数的形参必须用 `std::string`**,并在 handler 内自行解析校验 —— 用 `int` 等类型时 drogon 转换失败会**抛异常 → 500**,而不是返回 400
  * 形参个数必须与 `{N}` 个数一致;守卫在编译期(`arity==0`)与运行期(路径无 `{N}`)双向拦截,问题不会拖到线上
* 背景:`RegisterCoro` 的 handler 被擦成单参 `std::function`,`paramCount()==0`,含 `{N}` 的路由会让 drogon 的 `addHttpPath` 校验失败(`HttpControllersRouter.cc:368`)直接 `exit(1)`;它只能绕道 `registerHandlerViaRegex`,而 `getParameter("1")` **恒为空**,于是被迫手工解析路径。文件中心全部带参路由都用 `RegisterCoroWithPathParams`,不手工解析
* 所有 handler 首参须**按值** `HttpRequestPtr`(协程特化的匹配要求)
* 跨面注册被拒:路由路径的归属前缀必须属于所注册的面

### 5.2 命名规范

| 项 | 规范 | 示例 |
| --- | --- | --- |
| 路径 | `/zimo/api/filehub` 根前缀;资源名词复数;动作资源化 | `/filehub/nodes/move`、`/filehub/trash/restore` |

| 原体上传 | 分片与单请求上传用**请求头**传元数据、请求体传原始字节(避免 multipart 解析开销与内存峰值) | `X-Upload-Id` / `X-Chunk-Index` |

### 5.3 响应标准

* 成功:HTTP 200 + 业务 JSON(无冗余信封)

* 批量操作返回 `{success:[], failed:[{id,name,code}]}`,**不做部分成功回滚**:失败的逐条列出原因,成功的保留

**`nodes` 表的四条硬约束(实现不可省)**

```sql
-- ① 部分唯一索引:回收站条目不占名;同名判定不区分大小写(对齐文件系统)
CREATE UNIQUE INDEX idx_nodes_uniq
    ON nodes(space, parent_id, name COLLATE NOCASE) WHERE deleted = 0;

-- ② 查询索引一律带 WHERE deleted=0 —— 查询漏写该条件会退化为全表扫描
CREATE INDEX idx_nodes_dir    ON nodes(space, parent_id, type, name) WHERE deleted = 0;
CREATE INDEX idx_nodes_search ON nodes(space, name)                  WHERE deleted = 0;
CREATE INDEX idx_nodes_hash   ON nodes(space, hash, size)            WHERE deleted = 0;

-- ③ 回收站索引
CREATE INDEX idx_nodes_trash  ON nodes(space, deleted, delete_time);
```

**`owner_uid` 语义**:恒为"创建者",跨空间移动**不改写**;一致性同步补建的条目为 0(展示为"系统")。

**`deleted` 语义**:只标记**被删的顶层条目**,子孙不改写;子孙是否在回收站由**祖先链**判定。

### 6.2 空间的物理映射

| 项 | 路径 |
| --- | --- |
| 条目本体 | `<exe>\modules\filehub\space\<space>\<沿 parent 链的 name 逐级拼接>`(0=公共,uid=个人) |
| 回收站条目 | `<exe>\modules\filehub\space_trash\<space>\<node_id>\<条目原名>`(删除时的落脚处) |
| 打包产物 | `<exe>\modules\filehub\space_cache\<space>\zip\<uid>_<时间戳>_<随机串>.zip` |
| 上传分片 | `<exe>\modules\filehub\space_cache\<space>\chunk\<upload_id>\<index>.part` |
| 数据库 | `<exe>\db\filehub\filehub.db` |

* 物理目录名与逻辑名严格一致(可被运维直接浏览、备份)
* 拼接结果 ≤ 240 字符、深度 ≤ 32 层;统一加 `\\?\` 前缀绕过 `MAX_PATH`
* 空间根不是一条记录,而是 `spaces` 表里的一行元信息;`parent_id = 0` 表示"位于空间根下"
* 回收站区**按条目 id 分一层目录**再接原名:回收站里同名是常态(不同目录下各删一个
  `a.txt`),不隔开就会撞;保留原名则是让运维与"条目行丢失后的重建"都能认出它是什么
* 回收站区与 `space\`、`space_cache\` 平级而非嵌套:在用区扫描的根是 `space\<space>\`,
  回收站放进去会被当成陌生文件补建;平级则天然隔离,且名字本身说明"不是缓存、别随手清"

## 7. 关键业务逻辑说明

### 7.1 路径组装与可见树

**7.1.1 路径组装**

* 客户端**永远只给 id**,物理路径由服务端从库中 `name` 重新拼出 —— 路径穿越在机制层消失
* `name` 在写入时已按需求 §4.1 校验(不含 `<>:"/\|?*` 与控制字符、非保留设备名、非 `.`/`..`),拼接后不可能越界
* 子树操作(移动/复制/彻底删除/搜索)统一用 `WITH RECURSIVE` 从 `dir_id` 展开,走 `(space, parent_id)` 索引

**7.1.2 可见树**

* 所有常规操作只作用于 `deleted=0` 的条目;**祖先链上有 `deleted=1`** 的条目同样不可寻址
* 判定方式:查条目时同时校验自身 `deleted=0` 且**沿 parent 链上溯不遇 `deleted=1`**
* 常规接口命中不可见条目 → 返回 404(与"不存在"同构,不泄露回收站内容)
* 全模块统一:浏览/搜索/上传/新建/改名/移动/复制/分享/下载的查询都必须带 `deleted=0`

**7.1.3 `dirs/ensure` 与 `ensure_batch` 的例外处理**

这是**唯一**接受客户端路径字符串的入参(文件夹上传需要按相对路径逐级建目录)。**已确认走批量接口 `ensure_batch`**(见 §10.1 第 9 条):

```
POST /filehub/dirs/ensure_batch { space, parent_id, paths: ["项目A/资料", "项目A/资料/2026", "项目A/图片", ...] }
```

* 单次路径数 ≤ 2000;按"段数从少到多"排序后逐级建,保证父目录先于子目录
* 已存在的段直接复用(幂等),不多查一遍库 —— 同一批次内先建好的段在内存里记下 id
* 响应返回 `{created: N, reused: M, root_ids: {...}}`,前端据根目录 id 派发文件上传任务

**每一条路径的校验(逐段)**:

1. 按 `/` 切分,拒绝空段与 `.`/`..`
2. 每段套用名称校验规则(长度、非法字符、保留名、首尾空格)
3. 段数 + 当前深度 ≤ 32;单条总长 ≤ 1024 字符
4. **校验通过后仍逐级查/建**,不把该字符串拼进任何物理路径
5. 类型不符(同名条目是文件)则该条报错,不静默跳过

`ensure`(单条)保留,供零散场景使用;两条路径共用同一套段校验函数。

### 7.2 目录级写锁与冲突裁决

**锁模型**

* 键 = `(space, parent_id)`;同键串行、异键并发
* 实现为按桶散列的互斥量数组(固定 256 桶),不引入全局大锁
* 涉及多目录时**按桶号排序去重后加锁**(不是按 key 排序 —— 哈希碰撞时按 key 排会重复锁同一把锁而死锁,详见 §3.4)

**锁的持有范围(重要)**

| 操作 | 锁内做的事 | 锁外做的事 |
| --- | --- | --- |
| 新建/重命名/软删 | 冲突检查 + DB 写入 | 物理操作(建目录/改名) |
| 移动(同盘) | 冲突检查 + DB 写入 + `MoveFileEx` | 无(同盘改名是原子的) |
| 移动/复制(跨盘) | 冲突检查 + DB 写入 | 数据搬运 + 校验 + 回滚 |
| 上传完成 | 冲突裁决 + DB 写入 + 原子入位 | 分片合并(在锁外先做好) |
| 大目录删除 | 事务内删行 | 物理递归删除 |

* 原则:**锁只覆盖"裁决窗口",不覆盖长耗时的 IO**;物理操作失败时再回锁内做补偿(或在事务外回滚 DB)

**冲突裁决**

* 判定键 `(space, parent_id, name)`,**不区分大小写**(与文件系统一致)
* 策略:`ask`(默认,409 + 冲突清单)/ `skip` / `rename`(`name (1).ext` 递增)/ `overwrite`(仅文件,目录按 `rename`)
* 新建与重命名恒为 `ask`(用户明确命名时不应被静默改名或覆盖)
* **批量操作的粒度分两个阶段,不要混为一谈**:

  | 阶段 | 粒度 | 行为 |
  | --- | --- | --- |
  | **冲突裁决**(前置) | **整批** | 发现任一冲突 → 整批 409 + 冲突清单,一个都不动。理由:用户选择了"ask",应该看到完整冲突再决定,而不是先改一半 |
  | **执行**(裁决通过后) | **逐条** | 逐条执行,某条物理操作失败(被占用/超长)只标记该条失败,其余继续。响应 `{success:[], failed:[{id,name,code}]}` |

  两阶段不矛盾:§5.3 说的"不做部分成功回滚"指的是**执行阶段不回滚已经成功的条目**,不是"整批全成全败"。
* 执行阶段的逐条独立性,靠 **per-item SAVEPOINT** 实现:每条 `SAVEPOINT sp` → 失败 `ROLLBACK TO sp` → 下一条;全部走完再 `COMMIT`。没有 SAVEPOINT 时,一条语句失败会让整个事务处于不确定状态

### 7.3 软删除与回收站

**软删的粒度选择**

* **只标记被删的顶层条目**(写 1 行),子孙不改写;子孙随祖先的软删而不可达
* 好处:删大目录只写 1 行,不受子树规模影响
* 代价:三处需要按"以被删条目为根的子树"处理 —— **恢复、彻底删除、用量统计**

**四个字段的写入**

```
UPDATE nodes SET deleted=1, delete_time=?, origin_parent_id=?, del_owner_uid=?
WHERE id=? AND deleted=0
```

`AND deleted=0` **不可省略**:没有它,重复删除同一个 id 会覆盖 `origin_parent_id` 与 `del_owner_uid`,把这条回收站记录"过户"给后删的人。

**恢复**

* 原父目录可见 → 回原目录;原父目录不可见 → 回空间根
* 目标位置已有同名条目 → 在锁内自动重命名 `name (1)`、`name (2)`…
* 文件从 `space_trash\<space>\<id>\<原名>` 搬回目标路径;名字被占时直接搬到新名字下,
  不留"库名变了、磁盘还在旧名"的空壳
* 回收站区没有内容 → **拒绝恢复**,不给"恢复成功"的空壳(内容已丢就如实报失败)
* 恢复**不涉及配额校验**(回收站条目本就占着配额,恢复只是让它重新可见)

**保留期与清理**

* 30 天,由每日 03:00 任务物理删除(子树一起删)
* 物理删除失败(文件被占用)保留该行、留给下轮重试 —— **不能丢行**,否则回收站与实际文件脱节

**与一致性同步的交界(最易出错)**

| 方向 | 规则 |
| --- | --- |
| 磁盘 → 库(补建) | 在用区扫描遇不到回收站条目(其文件已搬到 `space_trash\`,不在 `space\` 下),不存在"给回收站文件补出重复行"的问题;**回收站区本身尚未纳入扫描(待补)** |
| 库 → 磁盘(删行) | 只对 `deleted=0` 判定"磁盘缺失";`deleted=1` 的行跳过 |
| 用量重算 | **计入** `deleted=1` 的占用(与"回收站占配额"一致) |

### 7.4 分片上传与秒传

**分片参数**:分片 8MB;阈值 8MB(以下走单请求);总分片 ≤ 2560(对应 20GB);会话 TTL 24 小时

**断点续传**:靠 `upload_sessions` 上的部分唯一索引 `(uid,space,parent_id,name) WHERE status=1` 复用会话,响应回传 `uploaded[]`;前端补传缺片即可

**秒传**

* 客户端在 `init` 提供整文件 SHA-256 才启用
* 查同空间内 `hash` 与 `size` 均相同的条目 → 命中则 `CopyFile` 到目标目录
* **不用硬链接**:会让"删一个副本不释放空间""配额按逻辑大小算两份"难以解释;秒传收益是省网络传输,本地复制成本很小
* 去重范围**限同空间**:跨空间不秒传(避免泄露他人文件的存在性)

**合并入位顺序**(不可颠倒)

```
校验片齐 → 工作池合并到临时文件 → 校验整文件哈希 → 锁内冲突裁决
  → AtomicPlace 原子改名 → 落 nodes 行 + 写 hash → 父目录随动 + 配额记账
  → 清理分片目录 → 任务置完成
```

**任一步失败的处理(含一个易漏的回滚分支)**

| 失败位置 | 处理 |
| --- | --- |
| 合并 / 校验哈希 | 临时文件与分片**保留**(供重试),不落 `nodes` 行,不占配额 |
| 锁内冲突裁决拒绝 | 同上;分片保留,用户可改策略重试 |
| `AtomicPlace` 入位失败 | 同上,物理未变 |
| **入位成功、落 `nodes` 行失败** | **必须删除刚入位的物理文件**(回滚)—— 否则磁盘上多一个库中无记录的文件,下一次一致性同步(以磁盘为准)会把它**补建成一条 `owner_uid=0` 的记录**,用户看到"删除失败的文件自己回来了" |

### 7.5 打包与缓存清理

**为什么先压缩好再下载**(而非流式打包)

* 压缩包是**稳定文件** → 可 `Content-Length`、可 Range 断点续传、可交给 IDM 等外部下载器
* 流式打包是 chunked、无长度 → 断点续传与外部下载器都做不到
* 代价:多一次磁盘读写与一份临时占用,由缓存清理策略兜底

**压缩算法**:deflate 级别 1(偏吞吐);已压缩格式(图片/视频/常见归档/Office 文档)走 **store** 只封装

**并发闸门**:全局同时进行 ≤ 2 个打包任务(业务闸门,不是线程绑定——工作池自动扩容,见 §7.10)

**清理规则**(以空闲超时为准)

| 场景 | 行为 |
| --- | --- |
| 用户取消打包 | 立即删除半成品 |
| 打包失败 | 立即删除半成品 |
| 下载完成 | **不立即删**:最后一次被访问后空闲 3 小时由清理器删除(多线程下载器并发 Range,按"请求结束即删"会误删);每次下载会把"最后访问时间"推到现在,相当于续期 |
| 用户删除记录 | 任务面板"删除"按钮**只删任务记录、不动压缩包**(与"清除历史"同口径);产物按上面的空闲回收与下面的兜底处理 |
| 服务重启 | 启动时把进行中任务置已中断,半成品由周期清理删除 |
| 兜底 | 每日清理删除超过 24 小时的缓存文件;总占用超 **500GB** 时按最久未访问优先删至 80% |

### 7.6 下载令牌

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 形态 | 32 字符随机 | 不承载 id、不可枚举、不可反推 |
| TTL | 10 分钟 | 进程内存储,不落库;重启即失效 |
| 绑定 | `(uid, node_id)` 或 `(share_token, node_id)` | 只授权"下载这一个条目" |
| 复用 | 允许重复使用 | 支持下载器多段并发 Range |
| 并发上限 | 同令牌 ≤ 5 连接 | 限制滥用 |
| 失效 | 目标不可见 → 410 | 校验时复查可见树 |

**Range 语义**

* `bytes=a-b` → 206 + `Content-Range`;`bytes=-n`(后缀)→ 206;超出 → 416 + `Content-Range: bytes */<size>`
* 多段 Range 按单段处理(只返回首个区间,不做 `multipart/byteranges`)
* `If-Range` 命中 `ETag`(`"<node_id>-<size>-<mtime>"`)→ 206,未命中 → 200 完整内容
* 偏移与长度全部 64 位,>4GB 正常续传

**中文文件名**:`Content-Disposition` 用 RFC 5987 双写 —— `filename="ASCII 回退名"; filename*=UTF-8''<百分号编码>`

### 7.7 分享访问控制

**token 熵**:32 字符高熵随机,校验时精确查库;**不采用**"编码自增 id"(可逆变换不是熵,链接会短且可枚举)

**子树校验**:`dir_id` 必须能沿 `parent_id` 上溯到分享目标(**递归 CTE**),**不做路径前缀字符串比较** —— 这是对"分享创建接口路径前缀混淆"类漏洞的防御;多选分享为"上溯到**任一**分享根即通过"

**提取码**:只存 HMAC 哈希(`ZM_FILE_HUB_HMAC_KEY`),明文仅创建时下发一次;连续错 5 次按 `(IP, token)` 冷却 10 分钟

**与回收站的关系**

| 目标状态 | 分享行为 |
| --- | --- |
| 移动/重命名 | **不影响**(分享绑 `node_id` 而非路径) |
| 在回收站中 | 访问返回 404 `SHARE_UNAVAILABLE`;分享行状态不变;多选分享**只跳过该条**,其余照常 |
| 从回收站恢复 | **自动恢复可用**(仍在有效期内) |
| 被彻底删除 | 置失效(`status=3`),`shares` 行保留至清理;多选分享同样只跳过该条 |

### 7.8 一致性同步算法

**原则**:文件系统是事实源,数据库是索引;同步**只补库、只删行,不动物理文件**

| 漂移情形 | 修复动作 |
| --- | --- |
| 磁盘存在、库无记录(文件) | 补建 `nodes` 行:`owner_uid=0`、`create_time=update_time=文件 mtime`、`size` 取实际、`hash` 留空 |
| 磁盘存在、库无记录(目录) | 先补建目录行,再递归处理其内部条目(自顶向下) |
| 库有记录(`deleted=0`)、磁盘缺失 | 删除该行;**目录连同子树级联删除** |
| 库有记录(`deleted=1`)且磁盘缺失 | **跳过**(回收站条目的物理文件可能已被手工清理,不删行) |
| 名称大小写不一致 | 以磁盘为准更新 `nodes.name` |
| 类型不符(库为文件、磁盘为目录) | 以磁盘为准:删原行,按磁盘类型重建 |

**执行约束**

* 同一时刻只允许一次同步(重复触发 409 `SYNC_RUNNING`);可取消,取消后已完成部分保留、不回滚
* **锁粒度**:对单个目录加锁做"读盘 → 比对 → 落库",不整段持锁(否则同步期间用户完全无法操作)
* **每个目录之间检查一次取消标记**(不是每个空间之间 —— 一个空间可能跑很久);进度按每 N 个目录上报一次
* 结束后统一重算各空间 `used_size` / `used_items`(含 `deleted=1`)
* 产出报告:扫描目录数/条目数、补建数、删除数、更新数、跳过数(权限不足/读取失败)、耗时

**为什么以磁盘为准**:物理文件是用户真正需要的东西;库只是索引,损坏可重建。反过来(以库为准)会把磁盘上多出来的文件当作垃圾删除,风险不可接受

### 7.9 配额与用量维护

* `spaces.used_size` / `used_items` **增量维护**在写操作事务内完成,不做实时全量统计
* 纳入统计:`deleted=0` + `deleted=1`(回收站占用)
* 释放时机:彻底删除 / 保留期清理
* 校验时机:上传完成前、复制前、跨空间移动入前;超限 403 `QUOTA_EXCEEDED`
* 默认不限(quota=0);一致性同步后统一重算,修正漂移
* 前端分别展示"已用"与"其中回收站占用",避免"删了却没释放空间"的困惑。**注意展示口径**(§10.4):`used_size` 是**空间级**的(含所有人的回收站);给用户看的"回收站占用"是**他本人删的那部分** —— 两者口径不同,不要混用同一个字段

### 7.10 工作池与并发控制

**哪些操作走工作池**(经 `ZmHttpServer::WorkPool()`;线程池**自动扩容**:初始线程数是起点,全忙时自动新建 worker,上限 `ZM_POOL_MAX_THREADS = 128`)

| 操作 | 占用 | 说明 |
| --- | --- | --- |
| 分片合并 | 短时 | 20GB 合并约数秒到数十秒 |
| 打包 | 同时 ≤ 2 个任务 | 长耗时且吃 CPU(deflate)与磁盘 IO;限的是**任务数**,不是线程数 |
| 跨盘复制/移动 | 短时 | 数据搬运 |
| 大目录物理删除 | 短时 | 递归删除 |
| 一致性同步 | 同时 ≤ 1 个任务 | 全量扫描耗时最长,且与用户操作竞争磁盘 |
| SQL 执行 | `RunOnPool` 投递 | **与上表共用同一个池** —— `ZmHttpServer::RunOnPool` 就是投到 `WorkPool()`。所以 SQL、打包、同步、分片合并全在一个池里排队,靠自动扩容(上限 128)吸峰,真正的争用是 CPU 与磁盘而不是线程数 |

**不走工作池**:单文件下载的读盘发送 —— 由 trantor 在事件循环上分块读取(Windows 下无 `sendfile`,`use_sendfile` 仅 Linux 生效)

**因此需要一道"全局并发下载闸门"(设计缺口,须实现)**:

* 现有约束只有**令牌级**的"同令牌 ≤ 5 连接"(§7.6),它拦不住"1000 个不同令牌同时下载" —— 而每个下载都在事件循环上分块读盘,并发数一高就会把事件循环堵住,连带影响所有接口
* 需补:**全局同时进行的直链下载数上限**(建议从 100 起,实现后按实测标定),超出的请求排队或返回 503
* 闸门放在 `ZmFileTokenModule` 的响应路径上,按"进入响应 → 计数 +1,响应结束 → 计数 -1"实现,与 §3.8 令牌连接的计数方式一致

**并发上限汇总**

| 维度 | 上限 | 超限行为 |
| --- | --- | --- |
| 单用户上传任务 | 3 | 429 `TOO_MANY_UPLOADS` |
| 单用户打包任务 | 2 | 排队 |
| 全局打包任务 | 2 | 排队 |
| 全局一致性同步 | 1 | 409 `SYNC_RUNNING` |
| 单用户有效分享 | 200 | 429 `TOO_MANY_SHARES` |
| 同令牌并发下载连接 | 5 | 拒绝新连接 |

* 上传进度为客户端视角(已完成片数 × 片大小),服务端进度在合并阶段更新 —— 两者不必严格一致,前端以客户端进度为主

  * 拖拽上传的高亮与进度反馈只用 `transform`/`opacity`
  * 轮询在无任务时停止(不常驻请求)

##### A. 拆成两个独立组件,不打成一个包

| 新文件 | 类 | 内容 |
| --- | --- | --- |
| `ZiMoPublic/util/zm_util_sqlite.h/.cpp` | `ZmSqliteDb` | 连接模型、事务、DAO 助手、`Now()` |

**为什么分开**:文件中心**不需要 Redis**(下载令牌在进程内、无跨进程共享缓存),不该被迫把 hiredis 依赖一起拉进来。合成一个 `ZmDbModule` 式的"什么都有"基类,等于把用户系统的历史包袱原样复制给文件中心。

##### B. 用继承而非组合

```cpp
class ZmDbModule : public ZmSqliteDb   // 用户系统
class ZmFileDbModule : public ZmSqliteDb   // 文件中心
```

理由:**`WithTx` 回调内的代码可以零改动**。现有写法是

```cpp
co_await m_db->WithTx([&](ZmDbModule& db) -> bool { db.ExecSync(...); ... });
```

继承后 `ExecSync` 由基类提供,调用形式不变;组合则要写成 `db.Db().ExecSync(...)` 或为每个方法加一层转发。

**唯一要改的是回调形参类型**,共 **3 处**(`module_session.cpp:72`、`module_user.cpp:132`、`module_user.cpp:319`):

```cpp
co_await m_db->WithTx([&](ZmSqliteDb& db) -> bool { ... });   // 形参由 ZmDbModule& 改为 ZmSqliteDb&
```

`WithTx` 签名相应改为 `std::function<bool(ZmSqliteDb&)>`。业务代码里 `db.ExecSync` / `db.QueryRowSync` 等调用(共 9 处)完全不动。

##### C. `ZmSqliteDb` 的接口

```cpp
class ZmSqliteDb
{
public:
    /// @param dbPath    库文件绝对路径
    /// @param readCount 读连接数(默认 4,与现状一致)
    bool Init(const std::string& dbPath, int readCount = 4);
    void Close();

    // ── 协程接口(经 RunOnPool 离核,事件循环不阻塞) ──
    drogon::Task<bool>   Exec(const std::string& sql, const std::vector<std::string>& params = {});
    drogon::Task<ZMJSON> QueryRows(const std::string& sql, const std::vector<std::string>& params = {});
    drogon::Task<ZMJSON> QueryRow(const std::string& sql, const std::vector<std::string>& params = {});

    /// 事务:回调在专用写线程执行,回调内只能调 *Sync 方法,不得再 co_await
    drogon::Task<bool> WithTx(const std::function<bool(ZmSqliteDb&)>& fn);

    // ── 同步接口(仅 WithTx 回调 / RunOnPool 上下文内调用) ──
    bool   ExecSync(const std::string& sql, const std::vector<std::string>& params);
    ZMJSON QueryRowSync(const std::string& sql, const std::vector<std::string>& params);
    ZMJSON QueryRowsSync(const std::string& sql, const std::vector<std::string>& params);
    bool   BeginTxSync();
    bool   CommitTxSync();
    bool   RollbackTxSync();

    /// @return 当前 unix 秒
    static int64_t Now();
    bool IsReady() const;
};
```

#### 10.1.2 一致性同步的取消(已确认)

**取消的对象**:管理员手动触发的**那一轮全量一致性同步任务**(扫所有空间、比对磁盘与库、补建/删行)。它是长耗时操作,大空间下可能跑几分钟到几十分钟,期间应能中途叫停。

**取定的两件事**:

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 检查点位置 | **在每个目录之间查一次取消标记**(不在空间之间) | 同步是"按空间 → 按目录"两层循环;只在空间之间查的话,一个大空间可能跑很久才响应。每目录一次原子读,开销可忽略 |
| 已完成的工作 | **不回滚** | 已补建/已删除的行是正确的结果,回滚反而制造新的不一致 |

**与进度上报解耦**:取消标记**每个目录**查(保证响应快),进度上报**每 N 个目录**写一次库(避免高频 UPDATE 打满单写队列)。两者不是同一件事,不要绑在一个计数上。

> 上一版此处写的"只支持整轮取消,还是支持跳过当前空间继续下一个"是表述失误 —— 那两个选项描述的是两件事,不是一对互斥选项,已按上表重述。

### 10.3 单目录条目上限:不设(已确认)

**为什么原本设了 10000**:防"目录爆炸",即某个目录被塞进海量条目后拖慢列表与子树操作。

**为什么取消**:逐条核对下来,原来担心的代价其实都不成立 ——

| 顾虑 | 实际情况 |
| --- | --- |
| 列目录返回太多 | 列表**本来就分页**(默认 200/页),不一次性返回 |
| `COUNT(*)` 算总数慢 | `(space, parent_id, ...)` 有索引,计数走索引 |
| 子树操作(移动/复制/删除)展开量大 | 走 `WITH RECURSIVE` + 索引,**与"单目录条目数"无关**,取决于子树总规模 |
| 打包该目录 | 打包有**独立的 5000 条上限**,会先撞上 |

也就是说,真正的瓶颈不在"单目录条目数",而在**子树总规模**(打包、目录复制、彻底删除各有自己的上限)。多设一道"禁止新建"的闸门,只会在用户不知道为什么建不了文件夹时添堵。

**保留的约束**:路径深度 ≤ 32 层、物理路径 ≤ 240 字符(这两条是 Windows 文件系统的硬约束,不是策略)。

**若将来真撞上问题**:先看是哪一类 —— 列表慢加索引或调分页,打包慢调打包上限;不要急着回来加"单目录上限"。

### 10.4 回收站归属:按"谁删的"划分(已确认)

**原设计的问题**:回收站是**空间级**的,公共空间回收站对所有登录用户可见可清空 —— 任何一个人点"清空",全员误删的内容全部永久消失。而删除权限本身就是开放的(§2.3),等于**误删的自救手段被别人的一次点击毁掉**。

**取定的划分**:

| 角色 | 可见范围 | 可做的操作 |
| --- | --- | --- |
| 普通用户 | **只有自己删除的条目**(`del_owner_uid == 自己`) | 恢复、彻底删除、清空(**只清自己删的那批**) |
| 管理员(`filehubAdmin`) | 全量(跨用户、跨空间) | 全量列表、恢复任意条目、彻底删除任意条目、**整体清空** |

**实现要点(必须在 SQL 层强制,不能只在前端过滤)**

```sql
-- 用户侧四个接口(trash / restore / purge / clear)的查询一律带：
WHERE space = ? AND deleted = 1 AND del_owner_uid = ?
-- 管理端走独立的 /filehub/admin/trash* 接口，不带 del_owner_uid 条件
```

* 用户侧接口**不接受任何可绕过该条件的参数** —— 不是"默认过滤、可传参放开",而是常量条件写死在 SQL 里
* 越权访问(拿到别人的条目 id)→ 返回 404 `TRASH_ITEM_NOT_FOUND`,**不区分"不存在"与"不是你的"**,避免探测他人回收站内容
* 个人空间天然满足该条件(只有本人能删),因此**两条空间规则统一,不需要分支**

**顺带解决的两个细节**:

1. **"回收站占用"的展示口径**:用户侧展示的应是"**我删的**"占用,不是该空间回收站的全部占用。`spaces.used_size` 的记账口径**不变**(仍是空间全部占用,含所有人的回收站),两者不冲突 —— 一个是对用户展示的视角,一个是配额计算的口径。
2. **保留期清理与归属无关**:每日 03:00 的到期物理删除是**系统行为**,不管条目是谁删的,到 30 天一律清理 —— 归属只决定"谁能提前手动清",不决定保留期。

### 10.5 写操作限流:不设(已确认)

原设计里有一张 `write_limits` 表(按 `(uid, 动作)` 计每分钟次数)。**取定不做写操作限流**(该表已改作通用计数表,承载提取码失败冷却,见 §7.7):

* 文件中心是本平台内部使用的模块,用户是已认证的账户,不存在公网匿名滥用场景
* 真正需要防的是**磁盘被写满**与**任务数爆炸**,这两件事已经各有闸门:配额(§7.9)、并发上传 ≤ 3、并发打包 ≤ 2、分享数 ≤ 200
* 限流阈值(每分钟 300 次)本来就是拍脑袋值,没有真实流量依据,先设了反而可能在正常批量操作时误伤

**保留的动作**:表结构改造成通用的 `(scope, dim_key, window_start, count)` 后,写限流只是多一个 `scope='write'` —— 将来若真出现滥用(如某账户高频刷接口),补上写入与校验即可,不必再改表。

**仍需保留的限流**:提取码校验的失败冷却(§3.9,按 `(IP, token)` 5 次/10 分钟)—— 这条**不是**接口频次限流,而是口令防爆破,继续保留。
