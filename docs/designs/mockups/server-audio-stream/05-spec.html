播放链路与规格

界面只有一屏,难度全在播放器:用 MediaSource 喂分片、交给媒体元素播 —— 写错一处就失去后台/锁屏续播能力
零新依赖:原生 MSE + <audio> + MediaSession
起播链路(顺序不能变)
1
握手 GET /init

自写 fetch + credentials:'include'、不设超时(不走 client.js:它强制 JSON 且默认 15s)。响应体 = 二进制初始化段;流描述在响应头:X-Stream-Id / X-Segment-Ms / X-Start-Seq / X-Live-Seq / X-Sample-Rate / X-Channels / X-Bitrate。失败:503 / 401 / 403。

2
建媒体元素与 MediaSource

new MediaSource() → audio.src = URL.createObjectURL(ms) → 等 sourceopen(once)→ addSourceBuffer('audio/webm; codecs="opus"')。能力检测在点开始之前:MediaSource.isTypeSupported(...)。

3
追加初始化段

sb.appendBuffer(init),等 updateend 再进下一步。追加前确认 mediaSource.readyState === 'open'。

4
拉片循环 GET /segment

参数 stream / seq / count(≤5) / keepalive / client;seq 从 X-Live-Seq 起(不是 X-Start-Seq:那会先听到十秒前的声音)。响应体拆批:[片数 u32 LE][长度 u32 LE][片字节] × N;N 可为 0(正常)。响应头给 X-Live-Seq / X-Edge-Ms / X-Next-Poll-Ms。

5
串行追加分片

逐片 appendBuffer,等上一片 updateend 再追加下一片(并发追加抛 InvalidStateError);seq += N,到边缘则按 X-Next-Poll-Ms 等待。

6
起播

缓冲够 2~3 片后:audio.currentTime = audio.buffered.start(0)(晚加入时缓冲起点不是 0)→ play(),且必须在用户手势内调用。随后挂 MediaSession 元数据与动作。

延迟口径与缓冲目标
已播 currentTime
已缓冲(已拉未播)
直播边缘 X-Edge-Ms
采集起点 0同一时间基(毫秒)片号 × 片长
延迟(ms) = X-Edge-Ms − audio.currentTime × 1000 · 每秒刷新一次进入参数行;200~500ms 属正常
场景目标缓冲countkeepalive节奏
前台播放2~3 片(≈300ms)35按 X-Next-Poll-Ms
切后台 / 锁屏15~30s545拉到目标后每 3~5s 一轮
回到前台削回 2~3 片35丢弃超出目标的已缓冲数据
暂停—160不拉片,保留流
停止——0离场并释放媒体元素
削缓冲退化:sourceBuffer.remove() 与 append 交错报错时,退化为"保留数据、把 currentTime 跳到边缘附近"—— 体验优先,不为削缓冲把播放搞崩。X-Next-Poll-Ms 规则:取完边缘=片长(100ms);取满 count=0(继续追平);落后超窗口一半=0,由客户端自行重排。
播放状态机(界面文案的唯一来源)
idle 聆听服务器 —点击开始→ connecting 连接中… —playing 事件→ playing 正在播放
paused 已暂停 ↔ 暂停 / 恢复(保留流,不重新握手)
reconnecting 连接中断,重连中… ←拉片连续失败— playing
no-device 服务器无可用音频设备 ←握手或拉片 503— · 回到空闲可重试
为什么"暂停"不是第六个状态 · 需求把 paused 归入 playing 的缓冲策略(keepalive=60 保留流), 界面只多一行副文案"保留连接 · 60 秒内可无缝续听";状态机仍按五态实现,便于与验收表逐条对齐。
切走(keep-alive)不销毁页面:播放必须继续,onDeactivated 只停特效动画,onActivated 恢复并重算画布。
释放路径固定:ms.endOfStream() → audio.removeAttribute('src') → URL.revokeObjectURL() → audio.load()。
硬约束速览(违反即打回)
路由 = 目录名:modules/server-audio-stream/ 自动挂 /portal/server-audio-stream;权限点 serverAudioStream。
声音必须交给 <audio> 元素(MSE 喂分片);不许 WebCodecs 自解码。
禁止 AudioContext / createMediaElementSource / AnalyserNode —— 接进 WebAudio 后台播放直接失效。
/init 与 /segment 不走 api/client.js:自写 fetch 拿二进制与响应头,不设超时。
appendBuffer 串行 + 追加前确认 readyState==='open';起播用 buffered.start(0) 定位。
切后台是降频续拉(不是停止);keepalive 按档位传:前台 5 / 后台 45 / 暂停 60 / 停止 0。
必须设 MediaSession 元数据与 play/pause/stop 动作;不设 setPositionState。
本模块不引第三方库;只改 frontend/ 下的文件;交付前 npm run build 必须通过。
特效按播放时间驱动(画布,DPR 计算);prefers-reduced-motion 时不动画,功能不变。
侧边栏图标在 PortalLayout.icoOf() 补 serverAudioStream 分支(声波/喇叭,见下)。
联调风险(最先排查):自定义响应头读出来是 null
页面在 80/443、接口在 39441,属同站跨端口 —— 浏览器的 CORS 判定仍然生效。基座的 CORS 回显只下发 Access-Control-Allow-Origin 与 Allow-Credentials; X-Stream-Id 这类自定义头属"非安全列头",没有 Access-Control-Expose-Headers 时前端读到 null 且不报错。
排查方向:先抓包确认响应里有没有该头,不要加本地代理"绕过";缺口按交接文档 §8 记录,由服务端侧补齐,前端不改契约、不改服务端代码。
前端侧的自保:握手成功后若 X-Stream-Id 为空,视为"契约未就绪"直接报错并给出可诊断的提示(不静默继续),避免表现成"播放没反应"。
服务端未就绪时的开发脚手架
向服务端要里程碑 1 产出的样例:init.webm + 一串簇文件,放 frontend/mock-audio/。
开发用 Node 静态服务(约 60 行)按 §5 契约返回、响应头照抄、按 seq/count 切片。
mock 只是脚手架:不进交付物、不为迁就 mock 改契约,联调时切回真服务。
预算参考:单路 ≈8KB/s、16 路 ≈1Mbps;服务端内存 0.5MB(60s 环形缓冲)与听众数无关; 采集+编码+封装单线程,典型单核占用 <5%。这些数字用于联调时判断"是否异常",不是界面文案。
