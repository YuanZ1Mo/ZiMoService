# 用户系统业务模块设计(第一期 · 第一版)

> 状态:待审阅 · 版本:v1 · 日期:2026-09-05
> 范围:注册 / 登录 / 强制重置密码 / 门户(用户主页、系统管理-用户管理)的服务端模块划分与接口设计
> 前置:从通用设计出发,不参考历史业务与代码;以《2026-09-05-用户系统业务需求.md》为需求依据、《2026-09-05-用户数据库表结构设计.md》为数据结构依据
> 目标:确定业务层模块划分、职责边界、依赖关系、接口注册规范与关键业务逻辑,作为本期实现与后续设计(页面/流程)的基线

***

## 1. 设计目标与分层

### 1.1 目标

* 业务层按**单一职责**划分为独立模块,每模块在 `modules` 目录下对应独立 `.h` / `.cpp` 文件
* 所有业务接口**注册到所属模块**,模块之间通过明确的服务方法交互,不跨模块直接操作对方数据表
* 数据访问收敛到统一数据访问模块,业务模块不直接拼写 SQL
* 鉴权为全局横切:会话校验、强制改密边界、权限拦截统一由门禁模块承载,业务 handler 内不重复实现

### 1.2 分层

| 层 | 构成 | 职责 |
| --- | --- | --- |
| 平台层 | `ZmHttpServer` 家族(前端面 / JRPC 面 / RESTful 面) | 端口监听、路由分发、协议校验、静态资源、文件传输、CORS、限流基座、协程调度 |
| 业务层 | `modules/` 下的业务模块 | 认证、会话、权限、用户数据、用户管理、门户、安全防护、审计等业务逻辑与接口 |
| 门禁层 | `module_gate`(业务层内横切) | 全局鉴权拦截、白名单、强制改密访问边界、接口级权限判定 |
| 数据层 | `module_db`(业务层内数据访问) | SQLite 连接、建表迁移、种子数据、事务封装 |

业务模块的装配入口为 `ServicePortal::Init()`:创建各模块实例,先装配门禁,再按依赖顺序让各模块注册自身接口。

## 3. 各模块详细设计

### 3.1 数据访问模块 `ZmDbModule`(module_db.h/.cpp)

**职责范围**
* SQLite 持久化(`user.db`):连接池或等价并发控制,保证事件循环线程不阻塞、阻塞操作走工作池;事务封装与通用 DAO 助手(占位参数绑定、结果行→JSON 转换)
* **全新建表初始化**:启动时按全新表结构建库建表(12 表 + `verify_codes` + `permissions.index` 列)并写入种子数据(3 个内置角色、门户模块权限点:用户主页 index=1、系统管理 index=-1 等),**不做旧数据迁移**;后续表结构变更由运维手工执行 SQL
* **Redis 缓存/共享状态**:基于 drogon RedisClient(`app().getRedisClient()`),提供缓存读写与共享状态服务,供业务模块使用

**对外服务方法**
* `bool Init(dbPath)`:打开库,**全新建表 + 种子**,幂等(仅首次建库)
* `Task<bool> Exec(sql, params)`:执行写语句(内部工作池)
* `Task<ZMJSON> QueryRows(sql, params)`:查询多行 → JSON 数组
* `Task<ZMJSON> QueryRow(sql, params)`:查询单行 → JSON 对象(无行返回空对象)
* `Task<bool> WithTx([...])`:事务封装,回调内写操作原子提交/回滚
* Redis:`Task<bool> RSet(key, val, ttlSec?)` / `Task<ZMJSON> RGet(key)` / `Task<bool> RDel(key)` / `Task<int64_t> RIncr(key, ttlSec?)` 等封装(drogon RedisClient 命令级访问,键统一按 `zimo:` 前缀命名空间)

**设计要点**
* 所有 SQL 经占位符绑定,杜绝拼接注入
* 时间一律 unix 秒 INTEGER;文本 NFC 归一化在入库前由业务模块完成
* **初始化策略:全新表**,不做版本化迁移脚本、不做增量迁移;表结构变更由运维手工执行 SQL(经 `Init` 幂等只建首次库,后续结构变更不影响既有数据)
* Redis 键规范:`zimo:<业务域>:<维度>:<键值>`,如 `zimo:perm:modules:{uid}`(模块清单缓存)、`zimo:policy:version`(策略变更版本号);缓存项均带 TTL,与心跳/会话续期周期对齐刷新
* Redis 定位为**缓存与共享状态**,不承载持久事实(持久数据一律在 SQLite);Redis 不可用回退到直接查库/进程内值,不阻塞主流程
* **周期清理任务(本模块唯一归属)**:每日 03:00 统一执行表清理(见《数据库表结构设计》§6:会话/令牌过期即清、锁定/限流 7 天、安全事件 90 天、审计 30~90 天、验证码过期即清),单表批次、异常隔离互不影响
* **SQLite 运行配置**:WAL 模式 + busy_timeout(写冲突等待而非立即失败)+ **单写队列**(写事务在专用工作池内串行执行,规避多写者锁竞争);读走连接池;事件循环不阻塞

### 3.2 用户数据模块 `ZmUserModule`(module_user.h/.cpp)

**职责范围**(数据归属:`users`、`user_profile`)
* 账号规则校验:4-30 位 `[a-z0-9_-]`、首尾非 `_`/`-`、统一小写;昵称 1-20 码点、不含空白、选填默认同账号
* 登录标识归一化与查询:account 小写 / email 小写 / phone 去格式 → `login_key` 定位用户
* uid 分配(10000001 起递增)、用户建行(含 profile 同步建行)
* 用户状态(停用/删除)、`force_change`、`role_code`、`last_login_*` 字段读写
* 用户列表查询(分页/搜索/角色/状态筛选,供用户管理)

**对外服务方法**(节选)
* `bool ValidateAccount(account, &errMsg)`:账号格式与唯一性
* `Task<bool> IsAccountUnique(account)`
* `Task<ZMJSON> FindByLoginKey(loginKey)`:归一化登录标识查用户
* `Task<ZMJSON> FindByUid(uid)`:含 profile 合并结果
* `Task<ZMJSON> CreateUser(account, nickname, passSalt, passHash, ip, roleCode)`:建 users + user_profile(角色由注册流程按规则传入)
* `Task<ZMJSON> ListUsers(page, size, search, role, status, includeDeleted)`
* `Task<bool> UpdateUserRow(uid, colWhitelist, patch)`:仅允许列白名单内字段
* `Task<bool> SetStatus(uid, status)` / `SetDeleted(uid, deleted)`
* `Task<ZMJSON> GetColumnsMeta()`:用户表列元数据下发(列名/顺序/显示名/可否排序/可编辑/置灰标记),驱动列表展示与属性编辑表单

**设计要点**
* 密码盐/哈希写入不在此模块计算,只落库;`pass_salt`/`pass_hash`/`temp_pass_*`/`id`/`uid` 属于**不可改列**,由模块内列白名单强制
* **列配置决策(已确认)**:列表展示列与属性编辑表单共用 `GetColumnsMeta()` 下发的一份列元数据——列表按"可展示列"渲染,表单按"可编辑/置灰"渲染;改列只改服务端元数据,不动前端

### 3.3 密码安全模块 `ZmPasswordModule`(module_password.h/.cpp)

**职责范围**(数据归属:`users` 的密码列,经 UserModule 落库)
* 密码哈希与校验:PBKDF2-HMAC-SHA256,600k 迭代,16B 随机盐,dklen 32;**哈希串带参数格式落库**(`pbkdf2$sha256$600000$salt$hash`),参数迭代可演进,历史哈希不失效
* 密码强度服务端复核(8-64 位、不含空格/控制字符、强度达标;**服务端为准,采用等效规则集**:长度 + 字符类别 + 弱口令黑名单 + 键盘序列,允许略严于前端 zxcvbn,不追求逐分对齐)
* 临时密码生成与置位:生成一次性临时密码、写 `temp_pass_*`、置 `force_change=1`
* `force_change` 位查询/清除、密码更换(含临时密码消费)

**对外服务方法**
* `Task<ZMJSON> HashPassword(password)`:返回 {salt, hash}
* `Task<bool> VerifyPassword(password, salt, hash)`:恒定时间比较,防时序侧信道
* `bool VerifyStrength(password, &errMsg)`
* `Task<string> GenerateTempPassword()`
* `Task<bool> ApplyPasswordChange(uid, newSalt, newHash, clearForceChange)`:更新哈希、清临时密码、按需清 force_change

### 3.4 会话模块 `ZmSessionModule`(module_session.h/.cpp)

**职责范围**(数据归属:`sessions`)
* 会话签发:生成 32B 随机明文 token,SHA-256 落库;cookie `zm_session` 值 = 明文 token,`HttpOnly` + `SameSite=Lax`(跨端口同站可携带)+ `Secure`(HTTPS 面)+ Max-Age 与绝对过期对齐;HTTP 80 明文面禁用 `SameSite=None`
* 会话校验:解析 cookie → 哈希查询 → 校验滑动/绝对双上限 → 返回会话上下文(uid、账号、force_change 等)
* 会话续期:活跃续期(滑动 30 天),并刷新 `last_active`;**续期写库节流**:`last_active` 每 ≥5 分钟落库一次,窗口内仅内存/Redis 判定滑动过期——10s 心跳"只读不写",网络轮询与写库解耦
* LRU 上限:每账号活跃会话上限 5,超出按 `last_active` 踢最旧
* 吊销:单会话吊销、按 uid 全量吊销(停用/强制重置时用)

**对外服务方法**
* `Task<ZMJSON> Issue(uid, ip, ua, forceChange)`:签发并 Set-Cookie,内含 LRU 清理
* `Task<ZMJSON> AuthAndTouch(cookieValue, ip)`:校验 + 续期;无效返回空(调用方判 401)
* `Task<bool> Revoke(cookieValue)`
* `Task<int> RevokeAllByUid(uid)`
* `Task<ZMJSON> ParseContext(req)`:从请求解析出会话上下文(供门禁与各模块取用)

### 3.5 权限模块 `ZmPermissionModule`(module_permission.h/.cpp)

**职责范围**(数据归属:`roles`、`permissions`、`user_permissions`)
* 角色数据访问(按 code 查角色、level、permission_codes)
* 权限点数据访问(按 code 查权限点、`module`、`url`、`index`、`type`)
* 单人授权读写(授予/拒绝,`UNIQUE(uid, perm_code)` 覆盖)
* 有效权限推导:角色默认 ∪ 授予 − 拒绝(拒绝优先),按会话缓存(Redis)、随心跳/续期刷新;**失效双保险:管理操作变更角色/权限/状态时主动 RDel 缓存键 + 递增 `policyVersion`;心跳仅比对版本号,不一致按需拉取详情**
* 门户模块清单:按推导结果 + `permissions.index`(正数升序在前、负数区在后)排序输出
* 等级查询:uid → role_code → level

**对外服务方法**
* `Task<bool> HasPermission(uid, permCode)`:有效权限判定(模块级/资源级)
* `Task<ZMJSON> GetModuleList(uid)`:门户模块清单 [{code,name,url,index}]
* `Task<int> GetLevel(uid)`
* `Task<bool> ChangeRole(operatorLevel, targetUid, newRoleCode, &errMsg)`:等级压制校验
* `Task<bool> SetUserPermission(uid, permCode, grantType, grantBy)`

### 3.6 安全防护模块 `ZmSecurityModule`(module_security.h/.cpp)

**职责范围**(数据归属:`login_locks`、`rate_limits`、`security_events`)
* 登录阶梯锁定:每 5 次失败升一档;档 1 锁 15 分钟、档 2+ 锁 60 分钟;锁定中不校验密码、不计数;成功清零
  * 锁定键双维度:能解析出用户 → `uid`(防换标识绕过);解析不出 → `login_key`(防账号枚举);查询先按 uid 再按 login_key
* 多维限流:场景(register / reset / login / verify_code)× 维度(ip / uid / login_key / device)滑动窗口(60s 默认 20 次),任一超限拒绝;落库持久化,重启不丢
* 安全事件记录:`login_anomaly` / `brute_force` / `admin_reset` / `force_change` / `permission_denied` 等落 `security_events`

**对外服务方法**
* `Task<ZMJSON> CheckLocked(loginKey, uid, ip)`:返回 `{locked, retryAfter}`(剩余秒),供前端展示"锁定剩余时间"
* `Task<ZMJSON> RecordLoginFail(loginKey, uid, ip)`:失败计数 + 档位推进
* `Task<bool> ClearLock(uid, ip)`
* `Task<bool> CheckLimit(scope, dimension, dimKey)` / `Task<bool> BumpLimit(scope, dimension, dimKey)` / `Task<bool> ResetLimit(...)`
* `Task<bool> RecordEvent(uid, account, eventType, ip, ua, detail)`

### 3.7 审计模块 `ZmAuditModule`(module_audit.h/.cpp)

**职责范围**(数据归属:`operation_logs`、`login_logs`)
* 管理操作审计:操作者(uid + account 快照)、动作、目标类型/id、变更详情 JSON、ip 落 `operation_logs`
* 登录日志:成功/失败、失败原因、ip、ua 落 `login_logs`(量大,保留期短)

**对外服务方法**
* `Task<bool> RecordOperation(operatorUid, action, targetType, targetId, detail, ip)`
* `Task<bool> RecordLogin(uid, account, result, failReason, ip, ua)`

### 3.8 认证模块 `ZmAuthModule`(module_auth.h/.cpp)

**职责范围**:注册、登录、登出、强制重置密码、心跳触达的**流程编排**与接口
* 注册:校验账号规则与唯一 → 密码强度 → **角色分配(首个用户 developer,后续用户 user,见 §7.8)** → 创建用户 + profile → 签发会话 → 登录日志/事件 → 响应(自动登录直进门户)
* 登录:归一化 login_key → 限流/锁定预检 → 查用户 → 状态校验(停用/删除) → 密码校验 → 失败走阶梯锁定 + 日志;成功清零锁定、签发会话、更新 last_login、force_change 判定 → 日志/事件
* 登出:吊销当前会话、清 cookie、不跳转(前端处理)
* 强制重置密码:校验新密码强度 → 更新哈希 + 清临时密码 + 清 force_change → **吊销旧会话并签发新会话(已确认)** → 跳门户
* 心跳:会话触达 + 服务端策略/变更推送(**轮询应答**:心跳响应携带变更版本号,客户端比对后按需拉取详情;推送通道本期预留)

**HTTP 接口**(全部 RESTful,根前缀 `/zimo/api`)

| 方法 | 路径 | 鉴权 | 请求体 | 说明 |
| --- | --- | --- | --- | --- |
| POST | `/auth/register` | 免(限流) | `{account, password, nickname?}` | 注册并自动登录 |
| POST | `/auth/login` | 免(限流+锁定) | `{account, password}` | 登录 |
| POST | `/auth/logout` | 需 | 无 | 登出 |
| POST | `/auth/force-reset` | 需 + force_change | `{newPassword}` | 强制重置密码 |
| POST | `/auth/heartbeat` | 需 | 无 | 心跳(触达 + 策略变更版本号,轮询应答) |

### 3.9 用户管理模块 `ZmUserAdminModule`(module_user_admin.h/.cpp)

**职责范围**:系统管理-用户管理的**全部管理操作编排**与接口;可见权限点 `userManager`
* 列表/表格:分页、搜索、角色/状态筛选(数据来自 UserModule)
* 列配置下发:列表展示列与属性编辑表单共用 `GetColumnsMeta()` 的列元数据(列名/顺序/显示名/可否排序/可编辑/置灰),改列不动前端
* 提权/降权:等级压制(操作者 level > 目标;提升最高到自己的下一级;不可操作自己)
* 模块授权/解除:单人覆盖 `user_permissions`(授予/拒绝)
* 停用/启用:停用置 status=2 + 吊销该用户全部会话;**按钮按状态切换:已停用用户显示"启用",正常用户显示"停用"(已确认)**
* 删除/恢复:软删除(deleted=1);不可登录、列表默认不显示;**按钮按状态切换:已删除用户显示"恢复",不显示删除(已确认)**
* 强制重置密码:生成临时密码 + 置 `force_change=1` + 吊销会话
* 每次操作联动审计 + 安全事件

**HTTP 接口**(全部需 `userManager` 权限;根前缀 `/zimo/api`)

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/admin/users` | 用户列表(page/size/search/role/status) |
| GET | `/admin/users/columns` | 用户表列元数据(可展示/可编辑/置灰标记) |
| GET | `/admin/users/{uid}` | 用户详情 |
| PATCH | `/admin/users/{uid}` | 修改主表属性(白名单) |
| POST | `/admin/users/{uid}/role` | 提权/降权 `{roleCode}` |
| POST | `/admin/users/{uid}/permissions` | 模块授权/解除 `{permCode, grantType}` |
| POST | `/admin/users/{uid}/disable` | 停用(吊销全部会话) |
| POST | `/admin/users/{uid}/enable` | 启用 |
| DELETE | `/admin/users/{uid}` | 软删除 |
| POST | `/admin/users/{uid}/restore` | 恢复(已删除用户,本期提供) |
| POST | `/admin/users/{uid}/reset-password` | 强制重置(临时密码 + force_change + 吊销会话) |

### 3.10 门户模块 `ZmPortalModule`(module_portal.h/.cpp)

**职责范围**:门户壳的服务端支撑与用户主页数据
* 模块清单:按会话缓存的有效权限推导,输出按 `permissions.index` 全序排序(正数升序在前,负数区 -1 最先)
* 用户主页:基本信息(昵称/账号)+ 角色定位(角色名/等级)+ 拥有的模块清单
* 心跳数据:与认证模块心跳接口合并(见 3.8)

**HTTP 接口**(全部需会话;根前缀 `/zimo/api`)

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/portal/modules` | 门户模块清单(侧边栏/路由驱动) |
| GET | `/portal/home` | 用户主页数据(基本信息 + 角色 + 模块) |

### 3.11 鉴权门禁模块 `ZmAuthGateModule`(module_gate.h/.cpp)

**职责范围**:全局鉴权横切,装配于 `ServicePortal::Init()`
* 前端面(80/443):除白名单(`/login`、`/register`、`/reset`、`/404`、静态资源)外,未带有效会话 → 302 跳 `/login`(可带 redirect);已登录访问 `/login` → 跳 `/portal`
* RESTful 面(39441):未带有效会话 → 401(前端统一跳登录并记录回跳地址)
* 强制改密边界:`force_change=1` 会话仅允许访问 `/force-reset` 页面与 `/auth/logout`、`/auth/force-reset`、心跳;其余业务页面/接口 → 403
* 接口级权限:按权限点拦截(如 `/admin/*` 需 `userManager`),无权限 403
* 会话上下文解析结果写入请求 attributes,业务 handler 直接取用,不重复查会话

**装配方式**:前端面 `RegisterPreRouting` + RESTful 面 `RegisterPreRouting`/Filter;白名单表、权限点→路径映射表由本模块持有,**权限点→路径映射由 `permissions` 表(module/url/type)数据驱动生成,新增模块只加数据不改门禁代码**

### 4.2 关键交互流程

**注册(自动登录)**
```
POST /auth/register
  → Gate:白名单免鉴权;SecurityModule.CheckLimit(register, ip)
  → AuthModule:
      1) UserModule.ValidateAccount + IsAccountUnique
      2) PasswordModule.VerifyStrength(password)
      3) PasswordModule.HashPassword(password)
      4) 角色分配:无任何用户 → developer(首个注册用户);否则 → user(admin 由管理操作授予,见 §7.8)
      5) UserModule.CreateUser(account, nickname, salt, hash, ip, roleCode):users + profile 建行放入**同一事务**(WithTx),中途失败整体回滚,不留半状态
      6) SessionModule.Issue(uid, ip, ua, forceChange=0)  → Set-Cookie
      7) AuditModule.RecordLogin(成功) + SecurityModule.RecordEvent(register)
  ← 200 {uid, account, nickname}
```

**登录(含锁定与限流)**
```
POST /auth/login
  → Gate:免鉴权;SecurityModule.CheckLimit(login, login_key/ip)
  → AuthModule:
      1) login_key 归一化(account 小写)
      2) SecurityModule.CheckLocked(login_key, uid?, ip)  → 锁定中返回 `{locked, retryAfter}`(429 语义)
      3) UserModule.FindByLoginKey → 无 → 阶梯锁定 login_key 维度(防枚举),统一提示"账号或密码错误"
      4) 状态校验:停用/软删除 → 拒绝"账号不可登录" + 事件
      5) PasswordModule.VerifyPassword → 失败:SecurityModule.RecordLoginFail(阶梯锁定) + AuditModule.RecordLogin(失败)
      6) 成功:SecurityModule.ClearLock + SessionModule.Issue + UserModule 更新 last_login
         + AuditModule.RecordLogin(成功);force_change=1 → 响应携带 forceChange=true
  ← 200 {forceChange: bool} (+ Set-Cookie)
```

**强制重置密码**
```
POST /auth/force-reset
  → Gate:会话有效且 force_change=1(否则 403 / 跳回门户)
  → AuthModule:
      1) PasswordModule.VerifyStrength(newPassword)
      2) PasswordModule.ApplyPasswordChange(uid, salt, hash, clearForceChange=true)
      3) 吊销旧会话 + SessionModule.Issue 新会话(保持已登录状态)
      4) SecurityModule.RecordEvent(force_change) + AuditModule.RecordLogin? (本期不改登录日志)
  ← 200 → 前端跳 /portal
```

**心跳(10s;轮询应答)**
```
POST /auth/heartbeat  (10s)
  → Gate:SessionModule.AuthAndTouch → 无效 401(前端立即下线);触达**只读不写库**,续期写按节流策略(见 3.4)
  → AuthModule:续期成功;响应携带策略变更版本号(policyVersion),客户端比对,不一致时按需拉取变更详情
  ← 200 {forceChange?, policyVersion?}
```

**用户管理操作链(以"强制重置密码"为例)**
```
POST /admin/users/{uid}/reset-password
  → Gate:会话有效 + HasPermission(uid, "userManager") 否则 403
  → UserAdminModule:
      1) PermissionModule.GetLevel(operatorUid) vs GetLevel(targetUid):操作者 level > 目标,不可操作自己
      2) PasswordModule.GenerateTempPassword + 置 force_change=1(经 UserModule 落库)
      3) SessionModule.RevokeAllByUid(targetUid)
      4) AuditModule.RecordOperation(operator, "reset_password", "user", uid, detail, ip)
      5) SecurityModule.RecordEvent(admin_reset)
  ← 200 {tempPassword}(管理员转交用户,仅本次返回)
```

## 5. 接口注册与命名规范

### 5.1 注册位置

* 各业务模块在 `ServicePortal::Init()` 中按序创建并注册自身接口;`ServicePortal` 只做装配与页面路由/CORS,不承载业务 handler
* 前端页面路由(80/443 页面别名、`/portal` SPA 回落、白名单页面)仍由 `ServicePortal` 注册;业务 API 一律由模块注册到 RESTful 面

### 5.2 命名规范

| 项 | 规范 | 示例 |
| --- | --- | --- |
| 路径 | 全小写,`/zimo/api` 根前缀;资源名词复数;动作资源化(动词路径限 auth/portal 这类动作域) | `/zimo/api/admin/users/{uid}/disable` |
| 方法 | 语义化:GET 读、POST 动作/创建、PATCH 局部改、DELETE 软删 | PATCH `/admin/users/{uid}` |
| 路径参数 | `{uid}` 等,与 drogon 路由占位符一致 | `/admin/users/{1}` |
| 请求体 | JSON(`Content-Type: application/json`),字段 snake_case,可选字段缺省 | `{account, password, nickname?}` |
| 错误码 | `模块前缀_语义`,随 HTTP 状态码返回 | `AUTH_LOCKED`、`USER_EXISTS`、`PERM_DENIED`、`RATE_LIMITED`、`PWD_WEAK` |
| 会话 | 业务接口一律经门禁取会话上下文,handler 不经 cookie 自行解析 | — |

### 5.3 响应标准

* 成功:HTTP 200 + 业务 JSON 数据(无冗余信封)
* 失败:HTTP 语义状态码(400 参数 / 401 未鉴权 / 403 无权限或强制改密边界 / 404 目标不存在 / 409 冲突 / 429 限流或锁定)+ `{"code":"XXX_YYY","message":"可展示文案"}`
* 401 统一由前端门禁行为处理(记录回跳 → 跳登录);403 按字段/表单级展示

## 7. 关键业务逻辑说明

### 7.1 密码哈希
* PBKDF2-HMAC-SHA256,600k 迭代,16B 随机盐,派生 32B;恒定时间比较
* 临时密码同样哈希落 `temp_pass_*`,登录强制改密通过后清空

### 7.2 登录锁定与限流
* 阶梯:每 5 次失败升一档;档 1 锁 15 分钟、档 2+ 锁 60 分钟(封顶);锁定中不校验密码、不计数
* 双维度防枚举:解析出用户按 `uid`(换登录标识也命中),解析不出按 `login_key`;查询先 uid 后 login_key
* 限流滑动窗口(60s 默认 20 次):register/login/reset/verify_code × ip/uid/login_key/device;任一超限拒绝;落库持久化

### 7.3 会话
* 每次登录/注册/强制改密签发全新 token;多会话并发,上限 5,Lru 踢 `last_active` 最旧
* 滑动 30 天 + 绝对 90 天双上限;cookie `zm_session` Max-Age 与绝对过期对齐,HttpOnly + SameSite
* 停用/强制重置 → 吊销全部会话;登出 → 吊销当前会话

### 7.4 权限推导与门户模块
```
有效权限 = roles(role_code).permission_codes ∪ user_permissions(grant_type=1) − user_permissions(grant_type=2)
```
* 拒绝优先级最高;登录后按会话缓存(经 Redis,键 `zimo:perm:modules:{uid}`),随心跳/续期刷新
* 侧边栏、用户主页"拥有的模块"、接口鉴权三者同源于此;模块排序按 `permissions.index`(正数升序在前、负数区 -1 最先)

### 7.5 等级压制
* 仅当操作者 level > 目标 level 允许停用/删除/重置/改角色等管理操作
* 角色提升最高到操作者的下一级;不可操作自己
* **developer(level 3)为最高等级,无更高等级操作者 → developer 用户不可被删除/停用/重置**(天然自我保护)

### 7.6 强制改密边界
* `force_change=1` 会话仅可达:`/force-reset` 页面、`/auth/force-reset`、`/auth/logout`、心跳;其余页面/接口 403
* 门户内鉴权命中 force_change → 引导至强制改密页;登录响应携带 `forceChange=true` 前端跳转

### 7.7 时间均衡
* 登录失败响应在账号不存在/密码错误两分支之间时间均衡,防账号枚举(结合 login_key 维度锁定)

### 7.8 角色分配(已确认)
* **首个注册用户 → `developer`**(level 3);判断依据:注册时 `users` 表无任何有效用户
* **后续注册用户 → `user`**(level 1),一律默认用户权限
* **`admin`(level 2)不通过注册获得**,由具备资格的管理员经提权操作授予(受等级压制约束:提升最高到操作者的下一级)

### 7.9 Redis 应用(已确认)
* 接入 drogon RedisClient,定位为**缓存与共享状态层**(键规范见 §3.1),不承载持久事实
* 本期落点:
  * 权限/模块清单缓存(`zimo:perm:modules:{uid}`):登录后写入,随心跳/续期刷新,避免每请求查库
  * 策略变更版本号(`zimo:policy:version`):管理操作(角色/权限/状态变更)时递增,心跳响应携带,客户端比对后按需拉取
  * 预留:验证码、找回密码令牌等短时效数据(下期)
* Redis 不可用时自动回退(直接查库/进程内值),不阻塞主流程

### 8.2 路由与模块映射(代码即清单)

* 命名映射:`permissions.code` 转小写 kebab-case → 路由与组件:`home`→`/portal/home`、`userManager`→`/portal/user-manager`
* `src/modules/` 目录与权限点一一对应,用 `import.meta.glob` 自动映射 code→组件(新增模块=新增目录+服务端权限点,无需改路由表)
* 路由职责分工:`router/index.js` 仅注册通用页(`/login` `/register` `/reset` `/force-reset` `/404`)与门户壳(`/portal` 布局);模块路由由 `import.meta.glob` 按 `src/modules/` 目录生成并挂载到门户壳下
* 服务端下发模块清单 `{code,name,url,index}`:侧边栏按 `index` 排序渲染;路由按清单**懒加载**;未授权模块不注册/不渲染(前端路由 + 服务端接口双重拦截)
* 工作区嵌入:PortalLayout 用 `<router-view v-slot><keep-alive>…</keep-alive></router-view>`,模块切走不销毁,激活/离开钩子用 `onActivated/onDeactivated`(音频等模块切走不中断)

### 8.3 鉴权与页面访问

* 服务端门禁:白名单(`/login` `/register` `/reset` `/404` + 静态资源 + index.html)免会话;非白名单路径无会话 → 302 `/login`(可带 redirect),有会话 → 回落 index.html
* 前端路由守卫:会话失效 → 记回跳地址跳 `/login`;`force_change=1` 会话仅允许 `/force-reset` 与登出,其余路由/接口 403;模块路由按模块清单权限校验
* API 请求统一经 `api/client.js`:携带 cookie、401 记录回跳跳登录、`{code,message}` 错误码映射到字段级报错

### 8.4 状态与心跳

* `stores/session.js`:会话/用户上下文/force_change;`stores/modules.js`:模块清单(登录后经 `/portal/modules` 获取,随心跳刷新)
* 心跳:PortalLayout 挂载后 10s 一次 `/auth/heartbeat`;响应携带 `policyVersion`,客户端比对后按需拉取变更;401 立即下线,网络中断提示不强制下线、恢复自动续

### 8.5 视觉与主题

* 亮/暗主题:跟随系统偏好 + 手动切换(令牌化,`styles/theme.css`)
* 页面/视觉/交互设计采用 **ui-ux-pro-max** skill 指导(青春活泼明亮基调、低 CPU 特效、骨架屏/Toast/抽屉等交互范式,见需求 §2.5)

### 8.6 构建与发布
